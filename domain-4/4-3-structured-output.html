4.3

المخرجات المنظمة عبر Tool Use والسكيما Structured output via tool use & JSON schemas

ليش هالموضوع مهم؟ لأن الأنظمة اللي بعدك في الخط (قواعد بيانات، APIs) ما ترحم: JSON مكسور أو حقل ملفق يعني فشل الخط كله — وtool_use هو الضمان الأوثق للهيكل. Why this matters: the systems downstream (databases, APIs) show no mercy — broken JSON or a fabricated field breaks the whole pipeline, and tool_use is the most reliable structural guarantee.

وش بتتعلمWhat you'll learn

  • ليش tool_use مع JSON schemas هو الأسلوب الأوثق لمخرجات ملتزمة بالسكيما — يلغي أخطاء الـ syntax لكنه لا يمنع الأخطاء الدلاليةWhy tool_use with JSON schemas is the most reliable route to schema-compliant output — it eliminates syntax errors but not semantic errors
  • الفرق بين tool_choice: "auto" (قد يرد نصاً)، "any" (لازم أداة من اختياره)، وأداة مفروضة بالاسمThe difference between tool_choice "auto" (may reply in text), "any" (must call some tool), and a forced named tool
  • تعريف أدوات استخراج بسكيما كمدخلات، وقراءة البيانات المنظمة من رد tool_useDefining extraction tools with schemas as inputs, and reading the structured data from the tool_use response
  • تصميم الحقول optional/nullable لما قد تغيب المعلومة من المصدر — لمنع تلفيق قيم لإرضاء الحقول الإلزاميةDesigning fields optional/nullable when the source may lack the information — preventing fabricated values to satisfy required fields
  • أنماط enum القابلة للتوسع: قيمة "unclear" للحالات الملتبسة، و"other" + حقل تفصيل للفئات الجديدةExtensible enum patterns: an "unclear" value for ambiguous cases, and "other" + a detail field for new categories
  • قواعد تطبيع التنسيق (تواريخ، مبالغ، أرقام هواتف) داخل البرومبت بجانب السكيما الصارمة لمعالجة تنسيق المصادر غير المتسقFormat normalization rules (dates, amounts, phone numbers) in the prompt alongside the strict schema to handle inconsistent source formatting

1 Tool Use: ضمان الهيكلTool use: the structure guarantee

لما تحتاج مخرجات منظمة من Claude، عندك طريقان: تطلب JSON في البرومبت وتدعي أنه يطلع سليماً، أو تعرّف أداة استخراج سكيمتها هي شكل البيانات المطلوب وتخلي النموذج "يستدعيها". الحيلة الذكية هنا أن الأداة مو أداة فعلاً — ما فيه دالة تنفَّذ. أنت فقط تستغل أن مدخلات الأدوات (input) ملزمة بالسكيما على مستوى الـ API نفسه، فتضمن بنية صالحة دائماً: لا فاصلة ناقصة، لا قوس مكسور، لا نص دردشة حول الـ JSON. هذا اللي يجعله الأسلوب الأوثق للمخرجات الملتزمة بالسكيما في الدليل الرسمي.

لكن انتبه للحد الفاصل — وهو أكثر نقطة يحبها الاختبار: السكيما الصارمة تلغي أخطاء الـ syntax فقط. الأخطاء الدلالية تبقى واردة تماماً: بنود فاتورة مجموعها 4,700 والإجمالي المستخرج 5,200، تاريخ استحقاق في خانة تاريخ الإصدار، رقم صحيح البنية في الحقل الغلط. السكيما تضمن الشكل، لا المعنى — والمعنى يحتاج طبقة تحقق برمجية (موضوع 4.4).

When you need structured output from Claude, there are two roads: ask for JSON in the prompt and pray it comes out intact, or define an extraction tool whose schema is the shape of the data you want and let the model "call it". The clever trick: the tool is not really a tool — no function ever executes. You are exploiting the fact that tool input is schema-enforced at the API level itself, so you always get valid structure: no missing comma, no broken bracket, no chatty text wrapped around the JSON. That is what makes it the most reliable approach to schema-compliant output in the official guide.

But watch the boundary — the exam's favorite point: a strict schema eliminates syntax errors only. Semantic errors remain entirely possible: invoice line items summing to 4,700 while the extracted total says 5,200, a due date sitting in the issue-date field, a structurally valid number in the wrong place. The schema guarantees shape, not meaning — and meaning needs a programmatic validation layer (topic 4.4).

WHAT TOOL_USE SCHEMAS DO — AND DO NOT — ELIMINATE

ELIMINATED: SYNTAX ERRORS
missing commas / broken brackets
prose wrapped around the JSON
wrong types (string where number)
missing required keys
STILL POSSIBLE: SEMANTIC ERRORS
line items don't sum to the total
value placed in the wrong field
fabricated value for a required field
internally inconsistent data
schema = shape guarantee  |  semantic validation (4.4) = meaning guarantee

السكيما تضمن الشكل وتلغي أخطاء الـ syntax — والأخطاء الدلالية تبقى مسؤولية طبقة التحقق The schema guarantees shape and kills syntax errors — semantic errors remain the validation layer's job

تعريف أداة استخراج: required وnullable وenum + "other" و"unclear" في سكيما واحدة: An extraction tool definition: required, nullable, and enum + "other" and "unclear" in one schema: 

{
  "name": "record_invoice",
  "description": "Record structured invoice data extracted from the document.",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": { "type": "string" },
      "issue_date":     { "type": "string", "description": "ISO 8601 (YYYY-MM-DD)" },
      "total_amount":   { "type": "number" },
      "currency": {
        "type": "string",
        "enum": ["USD", "SAR", "EUR", "other"],
        "description": "Use 'other' when the currency is none of the listed codes."
      },
      "currency_detail": {
        "type": ["string", "null"],
        "description": "Required free-text detail when currency = 'other'; null otherwise."
      },
      "po_number": {
        "type": ["string", "null"],
        "description": "null when the document contains no PO number. NEVER guess one."
      },
      "payment_status": {
        "type": "string",
        "enum": ["paid", "unpaid", "partial", "unclear"],
        "description": "Use 'unclear' when the document is ambiguous about payment."
      }
    },
    "required": ["invoice_number", "issue_date", "total_amount",
                 "currency", "payment_status"]
  }
}

الاستدعاء ثم قراءة البيانات من بلوك tool_use في الرد: Calling, then reading the data from the tool_use block in the response: 

from anthropic import Anthropic

client = Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2048,
    tools=[record_invoice_tool],
    tool_choice={"type": "tool", "name": "record_invoice"},  # forced
    messages=[{"role": "user", "content": f"Extract the invoice data:\n\n{document}"}],
)

# the "tool call" IS the structured output — no function ever runs
tool_use = next(b for b in response.content if b.type == "tool_use")
data = tool_use.input          # dict, guaranteed schema-compliant
print(data["invoice_number"], data["total_amount"])

مفهوم أساسيKey concept

في الاستخراج المنظم، "الأداة" قالب بيانات مو دالة: استدعاء record_invoice هو نفسه المخرج المنظم. القاعدة للاختبار: tool_use + سكيما = يلغي syntax errors، ولا يمنع semantic errors.
In structured extraction, the "tool" is a data template, not a function: the record_invoice call itself is the structured output. The exam rule: tool_use + schema = eliminates syntax errors, does not prevent semantic errors.

2 أوضاع tool_choice الثلاثةThe three tool_choice modes

مقدار "الإجبار" على استدعاء الأدوات تتحكم فيه معامل tool_choice بثلاثة أوضاع، والاختبار يحب يلعب على الفروقات بينها. auto: النموذج حر — يستدعي أداة إذا شاف داعياً أو يرد نصاً عادياً. ممتاز للمحادثة، لكنه ما يضمن مخرجات منظمة. any: لازم يستدعي أداة، لكن يختار أي واحدة من المتاح — هذا الضمان المطلوب لما عندك عدة سكيمات استخراج ونوع المستند غير معروف مسبقاً. الأداة المفروضة {"type": "tool", "name": "extract_metadata"}: لازم يستدعي هذي الأداة بعينها — تستخدمها لما خط المعالجة يتطلب أن استخراجاً معيناً يتم قبل خطوات الإثراء اللاحقة.

How hard the model is pushed toward tools is controlled by the tool_choice parameter's three modes, and the exam loves probing their differences. auto: the model is free — call a tool if warranted, or reply in plain text. Great for conversation, but it does not guarantee structured output. any: it must call a tool, but picks whichever fits — the guarantee you want when you have several extraction schemas and the document type is unknown up front. Forced tool {"type": "tool", "name": "extract_metadata"}: it must call that specific tool — used when your pipeline requires a particular extraction to run before later enrichment steps.

CHOOSING A TOOL_CHOICE MODE

NO — text replies OK

YES — always structured

{"type": "auto"}

شجرة القرار: auto للحرية، any لضمان أداةٍ ما، والأداة المسماة لفرض استخراج محدد Decision tree: auto for freedom, any to guarantee some tool, a named tool to force a specific extraction

الأوضاع الثلاثة في نداءات الـ API: The three modes as API calls: 

# 1) auto — the model MAY answer in text OR call a tool (no guarantee)
response = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=2048,
    tools=[extract_invoice, extract_contract, extract_receipt],
    tool_choice={"type": "auto"},
    messages=msgs,
)

# 2) any — the model MUST call one of the tools, its choice.
#    Guaranteed structured output with multiple schemas + unknown doc type.
response = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=2048,
    tools=[extract_invoice, extract_contract, extract_receipt],
    tool_choice={"type": "any"},
    messages=msgs,
)

# 3) forced — the model MUST call THIS tool.
#    Ensures extract_metadata runs before any enrichment step.
response = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=2048,
    tools=[extract_metadata],
    tool_choice={"type": "tool", "name": "extract_metadata"},
    messages=msgs,
)

لمحة سريعةQuick insight

اسأل سؤالين وبس: "لازم يكون الرد منظماً؟" — لا: auto. نعم: "لازم أداة محددة بعينها؟" — لا: any، نعم: أداة مفروضة بالاسم.
Ask just two questions: "must the response be structured?" — no: auto. Yes: "must it be one specific tool?" — no: any; yes: force the named tool.

فخ الاختبارExam trap

لما يطلب السؤال "ضمان" مخرجات منظمة، auto مشتت دائماً — لأنه يسمح برد نصي حر. والعكس فخ أيضاً: فرض أداة واحدة بالاسم لما تكون أنواع المستندات متعددة يحشر كل شي في سكيما واحدة خاطئة. وكل خيار "اطلب JSON في البرومبت مع التشديد" يرجعك لأخطاء syntax اللي وُجد tool_use ليلغيها.
When the question demands a "guarantee" of structured output, auto is always a distractor — it permits a free-text reply. The reverse is a trap too: forcing one named tool when document types vary crams everything into one wrong schema. And any "request JSON in the prompt, firmly" option walks you back into the syntax errors tool_use exists to eliminate.

3 تصميم سكيما يمنع التلفيقSchema design that prevents fabrication

هنا أخطر قرار في تصميم السكيما: required أم nullable؟ القاعدة من الدليل: إذا كانت المعلومة قد تغيب عن بعض المستندات المصدرية، لازم يكون الحقل optional/nullable. ليش؟ لأن الحقل الإلزامي أمرٌ للنموذج: "لا ترجع بدون قيمة" — وإذا ما وُجدت قيمة، النموذج بيرضي السكيما بالطريقة الوحيدة المتبقية: يألّف وحدة. حقل nullable يعطيه مخرجاً صادقاً: null يعني "المعلومة غير موجودة في المصدر" — وهذي معلومة قيّمة، مو فشل.

وللحقول التصنيفية، نمطان يمنعان الحشر القسري: "unclear" ضمن قيم الـ enum للحالات الملتبسة فعلاً (مستند يذكر دفعة جزئية بصياغة غامضة؟ payment_status: "unclear" أصدق من تخمين)، و"other" + حقل تفصيل نصي للفئات القابلة للتوسع — فئة جديدة ما توقعتها؟ تنحفظ كـ other مع وصفها بدل ما تُحشر غلطاً في أقرب فئة. وأخيراً: السكيما الصارمة تحدد الشكل النهائي، لكن المصادر فوضوية التنسيق (تواريخ بعشر صيغ، مبالغ بفواصل وعملات ملتصقة) — فأضف قواعد تطبيع في البرومبت بجانب السكيما تشرح كيف يحوَّل كل تنسيق شائع للصيغة القياسية.

Here is the most dangerous schema decision: required or nullable? The guide's rule: if the information may be absent from some source documents, the field must be optional/nullable. Why? A required field is an order to the model: "do not come back without a value" — and when no value exists, the model satisfies the schema the only way left: it fabricates one. A nullable field gives it an honest exit: null means "the source does not contain this" — which is valuable information, not a failure.

For categorical fields, two patterns prevent forced cramming: "unclear" among the enum values for genuinely ambiguous cases (a document mentioning partial payment in vague terms? payment_status: "unclear" is more honest than a guess), and "other" + a free-text detail field for extensible categories — a new category you did not anticipate gets stored as other with its description instead of being wrongly squeezed into the nearest bucket. Finally: the strict schema fixes the output shape, but sources are formatting chaos (dates in ten styles, amounts with separators and glued currencies) — so add normalization rules in the prompt alongside the schema explaining how each common format maps to the canonical one.

SCHEMA ANATOMY — FOUR FIELD PATTERNS

REQUIRED

"invoice_number": {"type": "string"}

ONLY for fields every valid document is guaranteed to contain

NULLABLE / OPTIONAL

"po_number": {"type": ["string","null"]}

info may be absent -> null is honest; required would force fabrication

ENUM + "unclear"

"enum": ["paid","unpaid","partial","unclear"]

ambiguous source -> "unclear" beats a confident wrong guess

ENUM + "other" + DETAIL

"enum": [..., "other"] + "detail": string

unforeseen category -> captured with detail, not crammed into the nearest bucket

أنماط الحقول الأربعة: إلزامي للمضمون وجوده، nullable لما قد يغيب، وunclear/other للغموض والفئات الجديدة The four field patterns: required for guaranteed-present, nullable for maybe-absent, unclear/other for ambiguity and new categories

قواعد تطبيع التنسيق داخل البرومبت — بجانب السكيما الصارمة: Format normalization rules inside the prompt — alongside the strict schema: 

## Normalization rules — apply BEFORE filling the schema

- Dates: always ISO 8601 (YYYY-MM-DD).
  "3rd of March 2026" -> "2026-03-03" | "03/04/26" -> resolve using the
  document's locale; if the locale is unknowable, set date_ambiguous = true.
- Amounts: plain numbers, no thousands separators, dot decimal.
  "SAR 1,250.00" -> total_amount: 1250.00, currency: "SAR"
- Phone numbers: E.164. "050 123 4567" (Saudi) -> "+966501234567"
- Percentages: store as fractions. "15%" -> 0.15
- Missing values: null. Do NOT write "N/A", "unknown", or empty strings.

تنبيهWarning

كل حقل تجعله required وأنت مو متأكد من وجوده في كل مستند = مصنع تلفيق صغير داخل نظامك. قيمة ملفقة "شكلها سليم" أخطر بكثير من null صريح، لأنها تعبر التحقق وتستقر في قاعدة البيانات.
Every field you mark required without being certain it exists in every document = a small fabrication factory inside your system. A fabricated value that "looks valid" is far more dangerous than an explicit null, because it passes validation and settles into your database.

نصيحةTip

اكتب في وصف كل حقل nullable جملة صريحة مثل: "null when the document has no PO number — never guess". وصف الحقل جزء من البرومبت يقرأه النموذج فعلياً — استغله لترسيخ سلوك الصدق.
Write an explicit sentence in every nullable field's description, like "null when the document has no PO number — never guess". Field descriptions are prompt text the model actually reads — use them to anchor honest behavior.

مثال من الحياة: النموذج الحكومي الورقيReal-life example: the government paper form

روح لأي دائرة حكومية واطلب خدمة بدون نموذج — بس اكتب طلبك في ورقة بيضاء. النتيجة: كل متقدم يكتب بأسلوبه، نص ناقص وثاني مبعثر، والموظف يقضي يومه يفك الطلاسم. عشان كذا الحكومات اخترعت النماذج الرسمية: خانات مسماة بترتيب ثابت (هذي السكيما)، خانات النجمة الحمراء إلزامية (required)، وخانات اختيارية تتركها فارغة إذا ما تنطبق عليك (nullable) — والموظف يرفض أي "اجتهاد" خارج الخانات.

وشف ذكاء النماذج الورقية العريقة: قوائم الاختيار من متعدد فيها دائماً مربع أخير "أخرى — حدد: ______" (نمط enum + other + detail بالضبط)، وبعضها فيه خيار "غير متأكد" (unclear). وفوق النموذج تعليمات التعبئة: "التاريخ بصيغة يوم/شهر/سنة، المبلغ بالريال بدون فواصل" — هذي قواعد التطبيع. النموذج الورقي يضمن الشكل، لكن لو كتبت راتبك في خانة العمر، الورقة ما تعترض — الشكل مضمون والمعنى مسؤوليتك: بالضبط syntax مقابل semantics.

Walk into any government office and request a service without a form — just write your request on a blank page. The result: every applicant writes their own way, one text incomplete, another scattered, and the clerk spends the day deciphering. That is why governments invented official forms: labeled boxes in a fixed order (the schema), red-star boxes that are mandatory (required), and optional boxes you leave empty when they do not apply (nullable) — and the clerk rejects any "creativity" outside the boxes.

Notice the wisdom of the old paper forms: multiple-choice lists always end with "Other — specify: ______" (exactly the enum + other + detail pattern), and some include "not sure" (unclear). Above the form sit filling instructions: "date as DD/MM/YYYY, amount in riyals without separators" — those are the normalization rules. The paper form guarantees shape, but if you write your salary in the age box, the paper does not object — shape is guaranteed, meaning is your responsibility: precisely syntax versus semantics.

في الاختبارOn the exam

موضوع سيناريو S6 الأثير. توقع ثلاث زوايا:

  • "نحتاج ضمان مخرجات منظمة وعدة سكيمات ونوع المستند مجهول" — الجواب tool_choice: "any". "لازم استخراج معين قبل الإثراء" — أداة مفروضة بالاسم.
  • "النموذج يخترع قيماً للحقول الغائبة" — الجواب اجعل الحقل nullable/optional، مو "شدّد الوصف" ولا "أعد المحاولة".
  • استبعد أي خيار يوحي أن السكيما الصارمة تمنع الأخطاء الدلالية (المجاميع الخاطئة تعبر السكيما بنجاح) — وأي خيار "اطلب JSON نظيفاً في البرومبت" كبديل عن tool_use.

Scenario S6's favorite topic. Expect three angles:

  • "We need guaranteed structured output, several schemas, unknown document type" — answer tool_choice: "any". "A specific extraction must run before enrichment" — the forced named tool.
  • "The model invents values for absent fields" — answer: make the field nullable/optional, not "strengthen the description" or "retry".
  • Eliminate any option implying a strict schema prevents semantic errors (wrong sums pass the schema happily) — and any "just ask for clean JSON in the prompt" alternative to tool_use.

حقل vendor_tax_id إلزامي في سكيمتكم، لكن 30% من الفواتير الواردة ما تذكر رقماً ضريبياً أصلاً — والنموذج صار يكتب أرقاماً "معقولة الشكل" ملفقة. وش الإصلاح الجذري؟

The vendor_tax_id field is required in your schema, but 30% of incoming invoices contain no tax ID at all — and the model now writes plausible-looking fabricated numbers. What is the root fix?

صحيح. السبب الجذري أن الحقل الإلزامي يجبر النموذج على إرضاء السكيما بالتلفيق لما تغيب المعلومة — وnullable يعطيه مخرج الصدق. التحذير النصي يخفف ولا يمنع (البنية ما زالت تطالب بقيمة)، وفحص الصيغة يمسك الملفق سيئ الشكل فقط، والتقسيم المسبق يتطلب معرفة الجواب سلفاً. Correct. The root cause is that a required field forces the model to satisfy the schema by fabricating when the information is absent — nullable gives it the honest exit. A prose warning mitigates but does not prevent (the structure still demands a value), format validation only catches badly-shaped fabrications, and pre-splitting requires already knowing the answer.
الصحيح C: التصميم nullable هو حل الدليل لما قد تغيب المعلومة من المصدر — يمنع التلفيق من جذره. بقية الخيارات ترقيعات فوق سكيما تجبر النموذج على الاختراع. The answer is C: nullable design is the guide's fix when information may be absent from the source — it removes fabrication at the root. The other options are patches over a schema that forces invention.
3

تصنّفون مستندات واردة إلى فئات: contract / invoice / receipt. تظهر أحياناً أنواع جديدة (مذكرات تفاهم، عروض أسعار) والنموذج يحشرها غلطاً في أقرب فئة. وش تعديل السكيما الصحيح؟

You classify incoming documents into contract / invoice / receipt. New types occasionally appear (MOUs, quotations) and the model wrongly crams them into the nearest category. What is the right schema change?

صحيح. نمط "other" + حقل التفصيل يحافظ على صرامة الـ enum للفئات المعروفة ويفتح مخرجاً موثقاً للجديدة — وحقل التفصيل يخبرك متى تستحق فئة ترقية لقيمة enum رسمية. الإضافة المستمرة سباق لا ينتهي، والنص الحر يفقد الاتساق، والرفض المسبق يتطلب مصنفاً أصلاً. Correct. The "other" + detail pattern keeps the enum strict for known categories while opening a documented exit for new ones — and the detail field tells you when a category earns promotion to a formal enum value. Perpetual additions are an endless race, free text loses consistency, and pre-rejection requires a classifier in the first place.
الصحيح C: "other" + حقل تفصيل — نمط الدليل للفئات القابلة للتوسع. يمنع الحشر القسري بدون التضحية بصرامة الـ enum ولا الدخول في سباق تحديثات. The answer is C: "other" + a detail field — the guide's pattern for extensible categories. It prevents forced cramming without sacrificing enum strictness or entering an update race.

خلاصةTakeaway

  • tool_use مع JSON schema = الأسلوب الأوثق للمخرجات المنظمة: يلغي أخطاء syntax، ولا يمنع الأخطاء الدلالية (المجاميع، الحقول المتبادلة).tool_use with a JSON schema = the most reliable structured-output approach: eliminates syntax errors, does not prevent semantic ones (sums, swapped fields).
  • tool_choice: auto = قد يرد نصاً؛ any = لازم أداة من اختياره (الضمان مع تعدد السكيمات)؛ الأداة المسماة = فرض استخراج محدد قبل خطوات لاحقة.tool_choice: auto = may reply in text; any = must call some tool (the guarantee with multiple schemas); named tool = force a specific extraction before later steps.
  • أي معلومة قد تغيب من المصدر = حقل nullable — الحقل الإلزامي بلا مبرر يصنع قيماً ملفقة.Any information that may be absent from the source = a nullable field — an unjustified required field manufactures fabricated values.
  • "unclear" للالتباس، و"other" + حقل تفصيل للفئات الجديدة — صدق المخرجات أهم من امتلاء الخانات."unclear" for ambiguity, "other" + detail for new categories — honest output beats filled-in boxes.
  • قواعد التطبيع في البرومبت (تواريخ ISO، مبالغ بلا فواصل، E.164) ترافق السكيما الصارمة لمعالجة فوضى تنسيق المصادر.Normalization rules in the prompt (ISO dates, separator-free amounts, E.164) ride alongside the strict schema to tame messy source formatting.
