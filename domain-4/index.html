Domain 4

هندسة البرومبت والمخرجات المنظمة Prompt Engineering & Structured Output

كيف تكتب برومبتات دقيقة بمعايير صريحة، تضمن مخرجات ملتزمة بسكيما محددة، تبني حلقات تحقق وإعادة، وتوزع الشغل بين المعالجة الفورية والدفعات — عشان يصير Claude مكوّن موثوق داخل أنظمة الإنتاج. How to write precise prompts with explicit criteria, guarantee schema-compliant output, build validation and retry loops, and split work between real-time and batch — so Claude becomes a dependable component inside production systems.

ملخص الدومينDomain summary

هذا الدومين يقيس شي واحد جوهري: هل تقدر تحوّل Claude من "مساعد يتكلم زين" إلى مكوّن هندسي متوقع السلوك داخل خط إنتاج؟ الأسئلة تدور حول خمس مهارات: كتابة معايير مراجعة صريحة بدل التعليمات الغامضة (لأن "كن متحفظاً" ما تحسّن الدقة)، استخدام أمثلة few-shot للحالات الغامضة، فرض مخرجات منظمة عبر tool_use مع JSON schemas، بناء حلقات تحقق وإعادة بتغذية راجعة عن الأخطاء، واختيار Message Batches API للشغل غير العاجل ومعماريات المراجعة متعددة المرور للجودة.

العقلية اللي يكافئها الاختبار: تعامل مع النموذج كمكوّن له عقد واضح — عرّف المدخلات والمخرجات (معايير وسكيما)، صمّم للفشل (حقول nullable، تحقق، إعادة بمعلومات محددة)، احترم الاقتصاديات (دفعات بنص السعر للشغل الليلي)، ولا تخلي المولّد يحكم على شغله بنفسه. كل خيار "اطلب من النموذج يكون أدق" أو "جرّب مرة ثانية بدون تغيير" هو غالباً الجواب الخطأ.

This domain measures one core thing: can you turn Claude from "an assistant that talks well" into an engineering component with predictable behavior inside a production pipeline? Questions revolve around five skills: writing explicit review criteria instead of vague instructions (because "be conservative" does not improve precision), using few-shot examples for ambiguous cases, enforcing structured output via tool_use with JSON schemas, building validation-and-retry loops with error feedback, and choosing the Message Batches API for latency-tolerant work plus multi-pass review architectures for quality.

The mindset it rewards: treat the model as a component with a clear contract — define inputs and outputs (criteria and schemas), design for failure (nullable fields, validation, retries with specific errors), respect the economics (half-price batches for overnight work), and never let the generator grade its own work. Any option shaped like "ask the model to be more accurate" or "just retry with no changes" is usually the wrong answer.

كيف يظهر في الاختبارHow it shows up on the exam

أسئلة هذا الدومين تجي بسيناريوهات CI واستخراج بيانات، والمشتتات لها أنماط ثابتة تقدر تتعلم ترفضها: This domain's questions arrive wrapped in CI and data-extraction scenarios, and the distractors follow fixed patterns you can learn to reject:

  • خيارات التعليمات الغامضة: "كن متحفظاً"، "بلّغ عن النتائج عالية الثقة فقط" — تخسر دائماً أمام المعايير التصنيفية الصريحة (بلّغ عن X وY، تجاهل Z). Vague-instruction options: "be conservative", "only report high-confidence findings" — these always lose to explicit categorical criteria (report X and Y, skip Z).
  • خيارات "حوّل كل شي للدفعات عشان التوفير" — أي workflow حاجب (مثل فحص قبل الدمج) لازم يبقى synchronous مهما كان التوفير مغرياً. "Switch everything to batch for the savings" options — any blocking workflow (like a pre-merge check) must stay synchronous no matter how tempting the discount.
  • خيارات "أعد المحاولة بقوة أكثر" لما تكون المعلومة أصلاً غير موجودة في المستند — الإعادة تصلح أخطاء التنسيق والهيكل، ما تخلق معلومات من العدم. "Retry harder" options when the information simply is not in the document — retries fix format and structural errors, they do not conjure missing information.
  • خيارات "نموذج أقوى / نافذة سياق أكبر" لتغطية مشكلة معمارية — تشتت الانتباه في مراجعة 14 ملف حله تقسيم المرور، مو ترقية النموذج. "Bigger model / larger context window" options papering over an architecture problem — attention dilution across a 14-file review is solved by splitting passes, not upgrading the model.
  • خيارات "خل نفس الجلسة تراجع شغلها بعناية أكبر" — النموذج يحتفظ بسياق تفكيره وقت التوليد فيدافع عن قراراته؛ الصح نسخة مستقلة بدون هذا السياق. "Have the same session review its work more carefully" options — the model keeps its generation reasoning context and defends its decisions; the right answer is an independent instance without that context.

1

مراجع الكود الآلي في CI عندكم يغرق الـ PRs بتعليقات أسلوبية أغلبها إيجابيات كاذبة، والمطورون بدأوا يتجاهلون كل تعليقاته حتى الصحيحة عن الثغرات. وش أفضل تصرف فوري؟

Your CI code reviewer floods PRs with style comments that are mostly false positives, and developers have started ignoring all of its comments — including accurate security findings. What is the best immediate action?

صحيح. الفئة عالية الإيجابيات الكاذبة تقوّض الثقة حتى بالفئات الدقيقة. التعطيل المؤقت يوقف النزيف، وتحسين المعايير يرجّع الفئة لما تصير موثوقة. "كن متحفظاً" تعليمات غامضة ما ترفع الدقة، وترقية النموذج ما تعالج غياب المعايير. Correct. A high false-positive category undermines trust even in the accurate categories. Temporarily disabling stops the bleeding while you refine the criteria, then re-enable once reliable. "Be conservative" is vague and does not improve precision, and a model upgrade does not fix missing criteria.
الصحيح B: عطّل الفئة عالية الإيجابيات الكاذبة مؤقتاً وحسّن معاييرها. التعليمات الغامضة مثل "كن متحفظاً" ما تحسّن الدقة، وترقية النموذج أو إلزام المطورين بالرد يعالجون العرض مو السبب. The answer is B: temporarily disable the high false-positive category and refine its criteria. Vague instructions like "be conservative" do not improve precision, and upgrading the model or forcing developer responses treats the symptom, not the cause.
2

كتبت تعليمات تفصيلية دقيقة لمراجع الكود عن التنسيق المطلوب (الموقع، المشكلة، الشدة، الإصلاح المقترح)، لكن المخرجات ما زالت غير متسقة: أحياناً ينسى الشدة وأحياناً يغيّر الترتيب. وش الحل الأكثر فعالية؟

You wrote detailed, precise instructions for your code reviewer about the required format (location, issue, severity, suggested fix), but output is still inconsistent: sometimes severity is missing, sometimes the order changes. What is the most effective fix?

صحيح. لما التعليمات التفصيلية وحدها تنتج مخرجات غير متسقة، الأمثلة الموجهة هي الأداة الأكثر فعالية: النموذج يقلّد التنسيق اللي شافه أفضل بكثير من وصف التنسيق. المزيد من الشرح يزيد الضجيج، وtemperature ما يعالج فهم التنسيق. Correct. When detailed instructions alone produce inconsistent output, few-shot examples are the most effective tool: the model imitates a format it has seen far better than a described one. More prose adds noise, and temperature does not fix format understanding.
الصحيح C: أمثلة few-shot تعرض التنسيق الكامل. الدليل الرسمي يعتبرها الأسلوب الأكثر فعالية لمخرجات متسقة لما تفشل التعليمات التفصيلية — النموذج يقلّد ما يشاهده. توسيع الشرح أو تصفير temperature أو تقسيم الاستدعاءات كلها لا تعالج المشكلة. The answer is C: few-shot examples showing the full format. The guide calls them the most effective technique for consistent output when detailed instructions fail — the model imitates what it sees. Longer prose, zero temperature, or per-field calls do not address the problem.
3

نظام استخراج يستقبل مستندات متنوعة (فواتير، عقود، إيصالات) وعندك أداة استخراج لكل نوع. تحتاج ضمان 100% أن كل استدعاء يرجع مخرجات منظمة عبر أداة، مع ترك حرية اختيار الأداة المناسبة للنموذج. وش الإعداد الصحيح؟

An extraction system receives mixed documents (invoices, contracts, receipts) and you have one extraction tool per type. You need a 100% guarantee that every call returns structured output through a tool, while letting the model pick the right tool. What is the correct setting?

صحيح. "any" يضمن استدعاء أداة (مخرجات منظمة مضمونة) مع حرية اختيار الأداة — مثالي لما يكون نوع المستند غير معروف. "auto" يسمح برد نصي بدون أداة، والأداة المفروضة تحشر العقود في سكيما الفواتير. Correct. "any" guarantees a tool call (structured output guaranteed) while leaving tool selection free — ideal when the document type is unknown. "auto" allows a plain-text reply with no tool, and a forced tool would squeeze contracts into the invoice schema.
الصحيح B: "any" = لازم أداة لكن باختياره. "auto" ما يضمن (ممكن يرد نص حر)، وفرض أداة واحدة خطأ لأن نوع المستند متغير، وطلب JSON في البرومبت يرجع أخطاء syntax اللي جاء tool_use أصلاً ليمنعها. The answer is B: "any" = must call a tool, its choice. "auto" gives no guarantee (a free-text reply is allowed), forcing one tool is wrong because document types vary, and prompt-requested JSON brings back the syntax errors tool use exists to eliminate.
4

فريقك انتقل من "اطلب JSON في البرومبت" إلى tool_use بسكيما صارمة، وزميل يقترح إلغاء طبقة التحقق البرمجية لأن "السكيما تضمن كل شي". وش تقول له؟

Your team moved from "ask for JSON in the prompt" to tool_use with a strict schema, and a teammate proposes removing the programmatic validation layer because "the schema guarantees everything". What do you tell him?

صحيح. tool_use يضمن بنية صالحة ملتزمة بالسكيما (لا أخطاء syntax)، لكنه لا يمنع الأخطاء الدلالية: مجاميع غلط، قيم بمواضع خاطئة. التحقق البرمجي (مثل مقارنة مجموع البنود بالإجمالي) يبقى ضرورياً — وهو أساس حلقة الإعادة في 4.4. Correct. tool_use guarantees valid, schema-compliant structure (no syntax errors), but it cannot prevent semantic errors: wrong sums, values in the wrong fields. Programmatic validation (like comparing the line-item sum to the total) remains essential — it is the foundation of the 4.4 retry loop.
الصحيح B. القاعدة الذهبية: tool_use يلغي أخطاء الـ syntax ولا يلغي الأخطاء الدلالية. فحص قابلية التحليل فقط (D) بلا فائدة لأن tool_use يضمنها أصلاً — التحقق المطلوب هو الدلالي: المجاميع، تطابق الحقول، التعارضات. The answer is B. The golden rule: tool_use eliminates syntax errors, not semantic ones. Parse-only validation (D) is useless since tool_use already guarantees parseability — the validation you need is semantic: sums, field placement, conflicts.
5

نظام استخراج فواتير يفشل التحقق دائماً على حقل po_number لمجموعة موردين معينة. بعد الفحص اتضح أن رقم أمر الشراء عند هؤلاء الموردين موجود فقط في نظام مشتريات خارجي، مو في ملف الفاتورة نفسه. النظام حالياً يعيد المحاولة 3 مرات مع رسائل الخطأ. وش التقييم الصحيح؟

An invoice extraction system keeps failing validation on the po_number field for a certain group of vendors. Investigation shows those vendors' PO numbers exist only in an external procurement system, not in the invoice file itself. The system currently retries 3 times with error messages. What is the correct assessment?

صحيح. الإعادة تصلح أخطاء التنسيق والهيكل، لكنها عاجزة لما تكون المعلومة غير موجودة أصلاً في المستند. الإبقاء على required مع الإلحاح يدفع النموذج للتلفيق — والحقل nullable + إثراء من المصدر الصحيح هو التصميم السليم. Correct. Retries fix format and structural errors, but they are powerless when the information simply is not in the document. Keeping the field required while pushing harder drives the model to fabricate — nullable plus enrichment from the right source is the sound design.
الصحيح C. القاعدة: الإعادة تنفع لأخطاء التنسيق والهيكل، ولا تنفع إطلاقاً لما تكون المعلومة موجودة فقط في مستند خارجي غير مقدَّم. المزيد من المحاولات أو الأمثلة أو الإلحاح كلها تدور بنفس الحلقة الفارغة — أو أسوأ، تدفع للتلفيق. The answer is C. The rule: retries help with format and structural errors, and never help when the information exists only in an external document that was not provided. More retries, examples, or pressure just spin the same empty loop — or worse, push toward fabrication.
6

عندكم ثلاثة أحمال عمل على Claude: (1) فحص أمني حاجب يمنع الدمج قبل اكتماله، (2) توليد اختبارات ليلي تُراجع نتائجه الصباح، (3) تدقيق أسبوعي للديون التقنية. المدير يبغى أقصى توفير عبر Message Batches API. وش التوزيع الصحيح؟

You run three Claude workloads: (1) a blocking security check that gates merges, (2) nightly test generation reviewed the next morning, (3) a weekly technical-debt audit. Your manager wants maximum savings via the Message Batches API. What is the correct split?

صحيح. القاعدة: الدفعات (توفير 50%، نافذة حتى 24 ساعة، بدون SLA مضمون) للشغل المتسامح مع التأخير وغير الحاجب؛ وأي workflow يوقف المطورين لازم يبقى synchronous. "غالباً أسرع" مو ضمان، والربط مو مشكلة لوجود custom_id. Correct. The rule: batch (50% savings, up to 24-hour window, no guaranteed SLA) for latency-tolerant, non-blocking work; any workflow that blocks developers stays synchronous. "Usually faster" is not a guarantee, and correlation is a non-issue thanks to custom_id.
الصحيح B. الفحص الحاجب لا يتحمل نافذة 24 ساعة بدون SLA؛ والشغل الليلي والأسبوعي مثالي للدفعات بنص التكلفة. خيار "الترتيب العشوائي" مغالطة لأن custom_id يربط كل طلب بنتيجته، وخيار الـ fallback تعقيد بلا داعي. The answer is B. A blocking check cannot tolerate a 24-hour window with no SLA; the nightly and weekly jobs are ideal batch candidates at half cost. The "unordered results" option is a misconception because custom_id correlates every request with its result, and the fallback option is needless complexity.
7

وكيل يولّد كود ثم تطلب منه في نفس الجلسة "راجع كودك بدقة وصحح أي أخطاء". يرجع لك: "الكود سليم" — مع أن فيه ثغرة واضحة. وش التفسير والحل؟

An agent generates code, then in the same session you ask it to "carefully review your code and fix any bugs". It replies "the code is correct" — despite an obvious flaw. What is the explanation and the fix?

صحيح. هذي حدود المراجعة الذاتية: نفس الجلسة تحمل سياق التوليد وتبريراته، فتقل احتمالية تشكيكها بقراراتها. النسخة المستقلة (بدون سياق سابق) أفعل من تعليمات المراجعة الذاتية ومن extended thinking في كشف المشاكل الدقيقة. Correct. This is the self-review limitation: the same session carries its generation context and its justifications, making it less likely to question its own decisions. An independent instance (no prior context) beats self-review instructions and extended thinking at catching subtle issues.
الصحيح C. المشكلة معمارية مو صياغية: سياق التوليد يجعل النموذج يدافع عن شغله. لا الصياغة الأشد ولا extended thinking يكسران هذا الانحياز — النسخة المستقلة النظيفة هي الحل المعتمد في الدليل. The answer is C. The problem is architectural, not phrasing: generation context makes the model defend its work. Neither stronger wording nor extended thinking breaks that bias — a clean independent instance is the guide's answer.
