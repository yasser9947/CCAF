4.1

معايير صريحة بدل التعليمات الغامضة Explicit criteria over vague instructions

ليش هالموضوع مهم؟ لأن مراجعاً آلياً بمعايير غامضة يغرق فريقك بإيجابيات كاذبة — وأول ما يفقد المطورون الثقة فيه، يتجاهلون حتى تنبيهاته الصحيحة. Why this matters: an automated reviewer with vague criteria floods your team with false positives — and once developers stop trusting it, they ignore even its accurate alerts.

وش بتتعلمWhat you'll learn

  • ليش المعيار الصريح ("بلّغ فقط عندما يناقض التعليق سلوك الكود الفعلي") يتفوق على التعليمات الغامضة ("تأكد أن التعليقات دقيقة")Why an explicit criterion ("flag comments only when claimed behavior contradicts actual code behavior") beats a vague instruction ("check that comments are accurate")
  • ليش "كن متحفظاً" و"بلّغ عن النتائج عالية الثقة فقط" يفشلان في رفع الدقة مقارنة بالمعايير التصنيفية المحددةWhy "be conservative" and "only report high-confidence findings" fail to improve precision compared to specific categorical criteria
  • أثر الإيجابيات الكاذبة على الثقة: فئة واحدة عالية الأخطاء تقوّض الثقة حتى بالفئات الدقيقةThe impact of false positives on trust: one noisy category undermines confidence even in the accurate categories
  • كتابة معايير مراجعة تحدد وش تبلّغ عنه (bugs، security) ووش تتجاهله (الأسلوب البسيط، الأنماط المحلية) بدل الفلترة بالثقةWriting review criteria that define what to report (bugs, security) versus skip (minor style, local patterns) instead of confidence-based filtering
  • التعطيل المؤقت للفئات عالية الإيجابيات الكاذبة لاستعادة ثقة المطورين أثناء تحسين برومبتاتهاTemporarily disabling high false-positive categories to restore developer trust while you improve their prompts
  • تعريف معايير شدة صريحة بأمثلة كود ملموسة لكل مستوى لتحقيق تصنيف متسقDefining explicit severity criteria with concrete code examples per level to achieve consistent classification

1 ليش التعليمات الغامضة تفشلWhy vague instructions fail

لما تكتب لمراجع الكود "تأكد أن التعليقات دقيقة"، أنت ما عطيته معياراً — عطيته هدفاً مفتوح التفسير. النموذج بيفسّر "دقيقة" بأوسع معنى: بيعلّق على تعليق ناقص التفاصيل، وتعليق قديم الصياغة، وتعليق ما يعجبه أسلوبه. النتيجة سيل من الملاحظات أغلبها ما يهم أحداً.

المعيار الصريح يقلب المعادلة: "flag a comment only when its claimed behavior contradicts the actual code behavior". هنا حددت شرط التبليغ بدقة قابلة للفحص: في تناقض بين كلام التعليق وسلوك الكود؟ بلّغ. ما في؟ اسكت. أي شخص ثالث يقدر يطبق نفس المعيار ويوصل لنفس النتيجة — وهذا تعريف المعيار الجيد.

ونفس المنطق ينسحب على تعليمات "الضبط النفسي" مثل "be conservative" أو "only report high-confidence findings": هذي ما تحسّن الدقة، لأنها ما تعرّف وش يعني "متحفظ" ولا وش يعتبر "ثقة عالية". النموذج يظل يقرر بمزاجه، بس صار الآن متردداً بشكل عشوائي — ممكن يسكت عن ثغرة حقيقية ويبلّغ عن تفضيل أسلوبي. البديل الصحيح دائماً: معايير تصنيفية تسمّي الفئات المطلوب التبليغ عنها والفئات المطلوب تجاهلها.

When you tell a code reviewer "check that comments are accurate", you have not given it a criterion — you have given it an open-ended goal. The model interprets "accurate" as broadly as possible: it comments on a comment that lacks detail, one with dated phrasing, one whose style it dislikes. The result is a flood of remarks that matter to nobody.

An explicit criterion flips the equation: "flag a comment only when its claimed behavior contradicts the actual code behavior". You have defined the reporting condition with checkable precision: is there a contradiction between what the comment claims and what the code does? Report. No contradiction? Stay silent. Any third party could apply the same criterion and reach the same verdict — which is the definition of a good criterion.

The same logic applies to "mood adjustment" instructions like "be conservative" or "only report high-confidence findings": they do not improve precision, because they never define what "conservative" means or what counts as "high confidence". The model still decides by feel, only now it hesitates randomly — it may stay silent on a real vulnerability and still report a style preference. The correct alternative is always categorical criteria that name the categories to report and the categories to skip.

VAGUE INSTRUCTION

"Check that comments are accurate.
Be conservative. Only report
high-confidence findings."

"accurate" undefined -> widest interpretation
"conservative" = random hesitation
"confidence" never defined
output: noise + missed real bugs
EXPLICIT CRITERION

"Flag a comment ONLY when its
claimed behavior contradicts
the actual code behavior."

testable condition: contradiction or not
a third party reaches the same verdict
defines when to STAY SILENT
output: fewer, real findings

مقارنة: تعليمات غامضة تنتج ضجيجاً، ومعيار صريح ينتج نتائج قليلة وحقيقية Comparison: vague instructions produce noise, an explicit criterion produces few, real findings

برومبت مراجعة بمعايير report/skip تصنيفية: A review prompt with categorical report/skip criteria: 

# Code review criteria

## REPORT only these categories
1. Bugs — the code's actual behavior contradicts its documented/claimed behavior
   (wrong operators, inverted conditions, off-by-one, unhandled edge cases that
   break the stated contract)
2. Security — SQL injection, secrets committed in code, missing auth checks,
   unsafe deserialization

## SKIP — never report
- Minor style: naming, formatting, import order (the linter owns these)
- Local patterns: idioms already used consistently in this file/codebase
- Subjective preferences: "I would write this differently"

Do NOT filter by confidence. If a finding matches a REPORT category, report it;
if it does not, skip it.

مفهوم أساسيKey concept

الدقة (precision) تتحسن لما تعرّف وش يُبلَّغ عنه ووش يُتجاهل كفئات، مو لما تطلب من النموذج "يتحفظ". المعيار الصريح يحدد شرطاً قابلاً للفحص؛ التعليمة الغامضة تفوّض القرار لمزاج النموذج.
Precision improves when you define what to report and what to skip as categories, not when you ask the model to "be careful". An explicit criterion sets a checkable condition; a vague instruction delegates the decision to the model's mood.

لمحة سريعةQuick insight

اختبار سريع لأي معيار: هل يقدر مهندس آخر يطبقه على نفس الكود ويوصل لنفس الحكم؟ إذا لا، فهو تعليمة غامضة مو معيار.
Quick test for any criterion: could another engineer apply it to the same code and reach the same verdict? If not, it is a vague instruction, not a criterion.

2 الإيجابيات الكاذبة تدمر الثقةFalse positives destroy trust

في مراجعة الكود الآلية، الإيجابية الكاذبة (false positive) أغلى بكثير مما تتصور. كل تعليق خاطئ يستهلك وقت مطور يقرأه ويتحقق منه ويرفضه — والأخطر: الثقة تنهار على مستوى الأداة كلها، مو على مستوى الفئة الخاطئة فقط. إذا كانت فئة الأسلوب ترمي 20 تعليقاً خاطئاً يومياً، المطور ما بيفرز "هذا تعليق أسلوبي أتجاهله وهذا أمني أقرأه" — بيسوي mute للمراجع كله، وبتضيع معه تنبيهات الثغرات الصحيحة.

عشان كذا الدليل الرسمي يعتمد تكتيكاً عملياً: عطّل الفئة عالية الإيجابيات الكاذبة مؤقتاً. توقيف فئة الأسلوب المزعجة يرجّع الثقة فوراً للفئات الدقيقة (bugs وsecurity)، وأنت في الخلفية تحسّن معايير الفئة المعطلة وترجعها لما تثبت دقتها على عينة اختبار. هذا مو استسلام — هذا إدارة ثقة.

In automated code review, a false positive costs far more than you would think. Every wrong comment burns developer time to read, verify, and dismiss — and worse: trust collapses at the level of the whole tool, not just the noisy category. If the style category throws 20 wrong comments a day, developers will not triage "this style comment I ignore, this security one I read" — they mute the entire reviewer, and the accurate vulnerability alerts drown with it.

That is why the official guide endorses a practical tactic: temporarily disable the high false-positive category. Switching off the noisy style category immediately restores trust in the accurate categories (bugs, security), while you refine the disabled category's criteria in the background and re-enable it once it proves precise on a test sample. That is not surrender — that is trust management.

دوامة الثقة: فئة واحدة مزعجة تسحب الأداة كلها للقاع — وكسرها يبدأ بتعطيل مؤقت The trust spiral: one noisy category drags the whole tool down — breaking it starts with a temporary disable

تنبيهWarning

لا تحاول "موازنة" فئة مزعجة بإضافة "كن أكثر تحفظاً في تعليقات الأسلوب" — رجعت للتعليمات الغامضة. الخياران الصحيحان: معايير تصنيفية أدق، أو تعطيل مؤقت للفئة كلها.
Do not try to "balance" a noisy category by adding "be more conservative about style comments" — that is the vague instruction again. The two correct moves: sharper categorical criteria, or a temporary disable of the whole category.

نصيحةTip

تتبّع نسبة الرفض (dismissal rate) لكل فئة على حدة. فئة يرفض المطورون أكثر من نصف نتائجها = مرشحة فورية للتعطيل المؤقت وإعادة صياغة معاييرها — وستشوف في 4.4 كيف حقل detected_pattern يخلي هذا التحليل منهجياً.
Track the dismissal rate per category separately. A category whose findings developers dismiss more than half the time is an immediate candidate for a temporary disable and criteria rewrite — and in 4.4 you will see how a detected_pattern field makes that analysis systematic.

3 معايير الشدة بأمثلة كود لكل مستوىSeverity criteria with code examples per level

حتى لو حددت الفئات بدقة، يبقى سؤال ثاني: وش شدة كل نتيجة؟ إذا كتبت بس "صنّف الشدة critical/high/medium"، بترجع لك تصنيفات متذبذبة — نفس المشكلة تطلع مرة high ومرة medium حسب مزاج الاستدعاء. الحل اللي يعتمده الدليل: عرّف كل مستوى شدة بمثال كود ملموس. المثال يرسّخ المعنى أكثر من أي وصف نصي، لأن النموذج يقيس الحالة الجديدة على الحالة المرجعية اللي شافها.

لاحظ أن هذا امتداد طبيعي لفكرة الموضوع كله: المعيار الصريح للفئة يجاوب "هل أبلّغ؟"، ومعيار الشدة بالأمثلة يجاوب "بأي مستوى؟". الاثنان مع بعض ينتجان مخرجات متسقة تقدر تبني عليها أتمتة (مثلاً: block على critical، تعليق فقط على medium).

Even with precise categories, a second question remains: how severe is each finding? If you just write "classify severity as critical/high/medium", you get wobbly classifications — the same issue comes back high on one call and medium on the next. The guide's solution: define each severity level with a concrete code example. An example anchors meaning better than any prose description, because the model measures new cases against the reference case it has seen.

Notice this is a natural extension of the whole topic: the explicit category criterion answers "do I report?", and example-anchored severity criteria answer "at what level?". Together they produce consistent output you can build automation on (for example: block on critical, comment-only on medium).

SEVERITY LADDER — each level anchored by a concrete code example

CRITICAL
security vulnerability / data loss
anchor: f-string SQL query with user input
HIGH
logic bug producing wrong results
anchor: inverted boundary check on discounts
MEDIUM
error-handling gap, crash on bad input
anchor: json.loads with no try/except
SKIP
style, naming, local idioms
not reported at any severity — the linter's job

سلّم الشدة: كل مستوى مثبّت بمثال كود مرجعي — وفئة SKIP خارج السلم بالكامل The severity ladder: each level anchored by a reference code example — and SKIP sits outside the ladder entirely

مقطع من برومبت المراجعة: معايير شدة بمثال لكل مستوى: Review-prompt excerpt: severity criteria with an example per level: 

## Severity criteria — classify ONLY using these anchors

### CRITICAL: exploitable security flaw or data loss
    query = f"SELECT * FROM users WHERE id = {user_id}"
    # SQL injection: user input interpolated into SQL

### HIGH: logic bug that silently produces wrong results
    if discount > 100:        # BUG: should be >= 100
        reject_order()        # a 100% discount slips through

### MEDIUM: missing error handling that can crash the job
    data = json.loads(response.text)
    # no try/except: one malformed response kills the whole run

### Rules
- Match the NEW finding to the closest anchor above.
- If it matches no anchor and no REPORT category -> do not report it.
- Never invent intermediate severities.

فخ الاختبارExam trap

أي خيار يحسّن الدقة عبر "كن متحفظاً" أو "بلّغ عن الثقة العالية فقط" أو "خفف حساسية المراجع" هو مشتت — يبدو معقولاً لأنه "يقلل الضجيج"، لكنه لا يعرّف شيئاً. الجواب الصحيح دائماً يسمّي فئات: بلّغ عن كذا، تجاهل كذا، وبأمثلة لكل مستوى شدة. وإذا كانت فئة تحترق بالإيجابيات الكاذبة، الجواب الصحيح غالباً تعطيلها مؤقتاً — مو معايرة مزاجية.
Any option that improves precision via "be conservative", "only report high confidence", or "make the reviewer less sensitive" is a distractor — it sounds reasonable because it "reduces noise", but it defines nothing. The correct answer always names categories: report these, skip those, with examples per severity level. And when a category is burning trust with false positives, the right answer is usually a temporary disable — not mood calibration.

مثال من الحياة: أمن المطارReal-life example: airport security

تخيّل مشرف أمن مطار يقول لموظفيه: "كونوا حذرين وأوقفوا أي شنطة مشبوهة". كل موظف بيفسر "مشبوهة" بمزاجه — واحد يوقف كل شنطة كبيرة، وواحد يفتش العطور. الطوابير تطول، والمسافرون يتذمرون، والموظفون أنفسهم يتعبون من الإنذارات الكاذبة لدرجة أنهم يبدأون يمررون الشنط بدون تدقيق — وهنا تعدي الشنطة الخطرة فعلاً.

المطارات الحقيقية تشتغل بالعكس: قائمة ممنوعات صريحة (سوائل فوق 100 مل، أدوات حادة، بطاريات ليثيوم فوق سعة محددة) مع صور مرجعية لكل صنف. الموظف ما يجتهد — يطابق. وإذا جهاز فحص معيّن صار يطلق إنذارات كاذبة كثيرة، يوقفونه عن الخدمة مؤقتاً ويعايرونه بدل ما يخلونه يدمر ثقة الموظفين بالإنذارات. هذا بالضبط: معايير تصنيفية + أمثلة مرجعية + تعطيل مؤقت للمصدر المزعج.

Imagine an airport security supervisor telling staff: "be careful and stop any suspicious bag". Every officer interprets "suspicious" by feel — one stops every large suitcase, another searches perfume bottles. Queues grow, travelers grumble, and the officers themselves get so worn down by false alarms that they start waving bags through unchecked — and that is when the genuinely dangerous bag slips past.

Real airports work the opposite way: an explicit prohibited-items list (liquids over 100 ml, sharp objects, lithium batteries above a set capacity) with reference photos for each item. Officers do not improvise — they match. And when one scanner starts throwing too many false alarms, it is pulled from service and recalibrated rather than being allowed to erode staff trust in alarms. That is exactly this topic: categorical criteria + reference examples + temporarily disabling the noisy source.

في الاختبارOn the exam

هذا الموضوع يجي غالباً داخل سيناريو S5 (Claude Code في CI): مراجع آلي يرمي إيجابيات كاذبة والمطورون بدأوا يتجاهلونه. يسألونك: وش تعدّل في البرومبت؟

  • استبعد فوراً: "أضف تعليمات كن متحفظاً / عالي الثقة فقط" — تعليمات غامضة لا تعرّف شيئاً.
  • استبعد: "رقِّ النموذج" أو "خل المطورين يردون على كل تعليق" — يعالجان العرض لا السبب.
  • اختر: معايير تصنيفية report/skip، أمثلة كود لكل مستوى شدة، وتعطيل مؤقت للفئة الغارقة بالإيجابيات الكاذبة.

This topic usually arrives inside scenario S5 (Claude Code for CI): an automated reviewer throwing false positives while developers start ignoring it. The question: what do you change in the prompt?

  • Eliminate immediately: "add be-conservative / high-confidence-only instructions" — vague words that define nothing.
  • Eliminate: "upgrade the model" or "make developers respond to every comment" — symptom treatments, not causes.
  • Pick: categorical report/skip criteria, code examples per severity level, and a temporary disable of the category drowning in false positives.

خلاصةTakeaway

  • المعيار الصريح = شرط تبليغ قابل للفحص ("بلّغ فقط عند تناقض الزعم مع السلوك الفعلي")، مو هدف عام ("تأكد من الدقة").An explicit criterion = a checkable reporting condition ("flag only when claim contradicts actual behavior"), not a general goal ("check accuracy").
  • "كن متحفظاً" و"عالي الثقة فقط" لا يحسّنان الدقة — المعايير التصنيفية (بلّغ عن bugs/security، تجاهل الأسلوب والأنماط المحلية) هي اللي تحسّنها."Be conservative" and "high-confidence only" do not improve precision — categorical criteria (report bugs/security, skip style and local patterns) do.
  • الإيجابيات الكاذبة تدمر الثقة بالأداة كلها — فئة مزعجة واحدة تُسكِت حتى التنبيهات الصحيحة.False positives destroy trust in the whole tool — one noisy category silences even the accurate alerts.
  • التعطيل المؤقت للفئة عالية الإيجابيات الكاذبة تكتيك مشروع: يستعيد الثقة الآن، وترجع الفئة بعد تحسين معاييرها.Temporarily disabling a high false-positive category is a legitimate tactic: it restores trust now, and the category returns once its criteria improve.
  • اتساق الشدة يجي من أمثلة كود ملموسة لكل مستوى (CRITICAL/HIGH/MEDIUM) — المثال مرساة أقوى من أي وصف.Severity consistency comes from concrete code examples per level (CRITICAL/HIGH/MEDIUM) — an example anchors better than any description.
