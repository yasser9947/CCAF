استراتيجيات المعالجة بالدفعات Efficient batch processing strategies

ليش هالموضوع مهم؟ لأن نص السعر إغراء كبير — والمهندس المعماري الحقيقي يعرف بالضبط أي الأحمال تتحمل نافذة 24 ساعة بدون SLA، وأيها يحرم عليها الانتظار. Why this matters: half price is a big temptation — the real architect knows exactly which workloads tolerate a 24-hour window with no SLA, and which must never wait.

1 اقتصاديات Batches API وقيودهBatches API economics & constraints

احفظ أرقام Message Batches API الثلاثة كأنها رقم جوالك: توفير 50% من التكلفة، نافذة معالجة تصل إلى 24 ساعة، وبدون SLA مضمون للكمون. الصفقة واضحة: تتنازل عن السرعة المضمونة مقابل نص السعر. أغلب الدفعات تخلص أسرع بكثير من 24 ساعة — لكن "غالباً أسرع" ليست ضمانة، وهنا يصطاد الاختبار من يبني workflow حاجباً على أمنية.

وفيه قيد تقني يغيب عن البال: الدفعة لا تدعم multi-turn tool calling داخل الطلب الواحد — ما تقدر تنفذ أداة في منتصف الطلب وترجع نتيجتها ليكمل النموذج. يعني وكيل يستكشف ويجرب وينادي أدوات بالتناوب مو مرشحاً للدفعات؛ أما استخراج بأداة واحدة مفروضة (استدعاء tool_use واحد يمثل المخرج، بدون تنفيذ فعلي) فيشتغل تماماً. وكل طلب في الدفعة يحمل custom_id من عندك — هو الخيط اللي يربط كل نتيجة بطلبها، لأن النتائج قد ترجع بأي ترتيب.

Memorize the Message Batches API's three numbers like your phone number: 50% cost savings, a processing window of up to 24 hours, and no guaranteed latency SLA. The deal is plain: you trade guaranteed speed for half price. Most batches finish far sooner than 24 hours — but "usually faster" is not a guarantee, and that is where the exam catches anyone building a blocking workflow on a wish.

One technical constraint is easy to forget: a batch does not support multi-turn tool calling within a single request — you cannot execute a tool mid-request and return its result for the model to continue. So an agent that explores, iterates, and alternates tool calls is not a batch candidate; a forced single-tool extraction (one tool_use call that IS the output, nothing actually executed) works perfectly. And every request in the batch carries your custom_id — the thread tying each result back to its request, since results may return in any order.

القرار كله في سؤال واحد: في أحد ينتظر النتيجة الآن؟ نعم = synchronous، لا = دفعات بنص السعر The whole decision in one question: is anyone waiting on the result right now? Yes = synchronous, no = batch at half price

إرسال دفعة استخراج ليلية — كل طلب بـ custom_id خاص: Submitting a nightly extraction batch — each request with its own custom_id: 

from anthropic import Anthropic

client = Anthropic()

batch = client.messages.batches.create(
    requests=[
        {
            "custom_id": f"invoice-{doc.id}",     # your correlation key
            "params": {
                "model": "claude-sonnet-4-5",
                "max_tokens": 2048,
                "tools": [record_invoice_tool],
                "tool_choice": {"type": "tool", "name": "record_invoice"},
                "messages": [{"role": "user",
                              "content": f"Extract the invoice data:\n\n{doc.text}"}],
            },
        }
        for doc in tonight_documents          # thousands of docs, one batch
    ]
)
print(batch.id, batch.processing_status)      # poll until "ended"

مفهوم أساسيKey concept

الاختيار بين synchronous والدفعات قرار كمون مو قرار تكلفة: حدد أولاً من ينتظر النتيجة، وبعدها التوفير يجي لوحده. من يبدأ من التوفير ينتهي بمطورين محبوسين على دفعة معلقة.
Choosing between synchronous and batch is a latency decision, not a cost decision: first determine who waits on the result, and the savings follow. Whoever starts from the savings ends with developers stuck behind a pending batch.

تنبيهWarning

لا ترسل مهام وكيلة (استكشاف + أدوات بالتناوب) للدفعات — قيد "لا multi-turn tool calling" يكسرها. الدفعات لطلبات مكتملة المدخلات: استخراج، تصنيف، تلخيص، توليد اختبارات لكود مرفق.
Do not send agentic tasks (exploration + alternating tool calls) to batches — the "no multi-turn tool calling" constraint breaks them. Batches are for input-complete requests: extraction, classification, summarization, test generation for attached code.

2 أي الأحمال تناسب الدفعاتWhich workloads fit batch

القاعدة من الدليل حرفياً: الدفعات مناسبة للأحمال غير الحاجبة والمتسامحة مع الكمون — تقارير الديون التقنية الليلية، التدقيقات الأسبوعية، توليد الاختبارات الليلي — وغير مناسبة إطلاقاً للتدفقات الحاجبة مثل فحوص ما قبل الدمج اللي يقف عندها المطور منتظراً. السؤال الحاسم مو "كم نوفر؟" بل "من يجلس ينتظر؟". مطور محبوس ساعة على فحص أغلى بكثير من أي توفير API.

The guide's rule verbatim: batch fits non-blocking, latency-tolerant workloads — nightly technical-debt reports, weekly audits, nightly test generation — and is flat-out inappropriate for blocking flows like pre-merge checks where a developer stands waiting. The deciding question is not "how much do we save?" but "who sits waiting?". A developer stuck an hour behind a check costs far more than any API discount.

لمحة سريعةQuick insight

اختصار للاختبار: الكلمات "overnight/nightly/weekly" = دفعات. الكلمات "blocking/pre-merge/gate/ينتظر" = synchronous. نادراً ما يحتاج السؤال أكثر من هذي الخريطة.
Exam shortcut: the words "overnight/nightly/weekly" = batch. The words "blocking/pre-merge/gate/waiting" = synchronous. Questions rarely need more than this mapping.

فخ الاختبارExam trap

من سؤال رسمي في الدليل: المشتتات الثلاثة الكلاسيكية هي (1) "حوّل الكل للدفعات مع polling — غالباً تخلص بسرعة": الاعتماد على "غالباً" في تدفق حاجب خطأ؛ (2) "أبقِ الكل synchronous لأن ترتيب نتائج الدفعات مشكلة": خرافة — custom_id يحلها؛ (3) "دفعات مع timeout يرجع للـ synchronous": تعقيد بلا داعي والحل الأبسط هو مطابقة كل API لحالته.
From an official guide question: the three classic distractors are (1) "move everything to batch with polling — it usually finishes fast": relying on "usually" for a blocking flow is wrong; (2) "keep everything synchronous because batch result ordering is a problem": a myth — custom_id solves it; (3) "batch with a timeout fallback to synchronous": needless complexity when the simple fix is matching each API to its use case.

3 حساب التكرار ومعالجة الفشلSubmission-frequency math & failure handling

افرض أنك وعدت عملاءك بمعالجة كل مستند خلال 30 ساعة من وصوله (SLA)، والدفعة قد تأخذ حتى 24 ساعة. كم مرة ترسل دفعة؟ الحساب: أسوأ حالة لمستند = زمن انتظاره قبل دخول دفعة + زمن معالجة الدفعة. لو أرسلت كل 4 ساعات، أسوأ مستند (وصل لحظة انطلاق الدفعة السابقة) ينتظر 4 ساعات ثم يعالَج بحد أقصى 24: المجموع 28 ساعة ≤ 30 — مع هامش ساعتين لاسترجاع النتائج ومعالجتها. الإرسال كل 6 ساعات يعطيك 30 ساعة بالضبط: تحقيق نظري للـ SLA بهامش صفر — أي تأخير ثانية يكسره، ولذلك نوافذ الـ 4 ساعات هي الجواب الهندسي.

وعند اكتمال الدفعة بيطلع فيها فاشلون — مستند تجاوز حد السياق، طلب رفضته الفلاتر. القاعدة: أعد إرسال الفاشل فقط، معرّفاً بـ custom_id، مع التعديل المناسب لسبب فشله (مستند طويل؟ قسّمه chunks). إعادة الدفعة كاملة تدفع ثمن الناجحين مرتين. وقبل هذا كله، قاعدة الذهب للأحجام الكبيرة: جرّب البرومبت على عينة صغيرة أولاً — اكتشاف عيب في البرومبت بعد معالجة 100 ألف مستند يعني إعادة مكلفة كان يمنعها اختبار على 200 مستند.

Suppose you promised customers every document is processed within 30 hours of arrival (the SLA), and a batch may take up to 24 hours. How often do you submit? The math: a document's worst case = its wait before entering a batch + the batch's processing time. Submitting every 4 hours, the unluckiest document (arriving just after the previous batch left) waits 4 hours then processes in at most 24: total 28 hours, at or under 30 — with a two-hour margin for retrieving and handling results. Submitting every 6 hours yields exactly 30: a zero-margin theoretical fit that one second of delay breaks — which is why 4-hour windows are the engineering answer.

When the batch ends, some requests will have failed — a document exceeded the context limit, a request was filtered. The rule: resubmit only the failures, identified by custom_id, with modifications fitting the failure cause (long document? chunk it). Resubmitting the whole batch pays for the successes twice. And before any of this, the golden rule for large volumes: refine the prompt on a small sample first — discovering a prompt flaw after processing 100,000 documents means a costly resubmission that a 200-document trial would have prevented.

BATCH LIFECYCLE — SUBMIT, POLL, RESUBMIT ONLY FAILURES

دورة الدفعة: تجميع بمعرفات، إرسال كل 4 ساعات، polling، ثم إعادة إرسال الفاشل فقط بعد تعديله The batch cycle: collect with IDs, submit every 4 hours, poll, then resubmit only the modified failures

قراءة النتائج بـ custom_id وإعادة إرسال الفاشل فقط: Reading results by custom_id and resubmitting only the failures: 

failed = []

for result in client.messages.batches.results(batch.id):
    if result.result.type == "succeeded":
        save_extraction(result.custom_id, result.result.message)
    else:                                   # errored / expired / canceled
        failed.append(result.custom_id)

# resubmit ONLY the failures — with a fix matching the failure cause
retry_requests = []
for cid in failed:
    doc = docs_by_custom_id[cid]
    for i, chunk in enumerate(chunk_document(doc)):   # e.g. exceeded context
        retry_requests.append({
            "custom_id": f"{cid}-part{i}",
            "params": build_extraction_params(chunk),
        })

retry_batch = client.messages.batches.create(requests=retry_requests)

نصيحةTip

قبل دفعة الـ 100 ألف مستند: شغّل البرومبت synchronous على عينة 100-200 مستند ممثلة للتنوع، صحح العيوب، وبعدها أطلق الدفعة الكبيرة. تكلفة العينة فتات مقابل إعادة معالجة جماعية — وهذا "رفع نسبة نجاح المرور الأول" اللي ينص عليه الدليل.
Before the 100k-document batch: run the prompt synchronously on a 100-200 document sample representing the variety, fix the flaws, then launch the big batch. The sample's cost is crumbs next to a mass reprocessing — this is the guide's "maximize first-pass success rates".

مثال من الحياة: المغسلةReal-life example: the dry cleaner

مغسلة ملابس تقدم خدمتين: استعجال — تجلس تنتظر وثوبك يطلع خلال ساعة بالسعر الكامل (synchronous)، وعادي — تسلّمهم الثياب وترجع "بكرة أو بعده" بنص السعر (الدفعات: نافذة طويلة بدون موعد مضمون). لو عندك مناسبة الليلة، الغبي فقط يختار العادي عشان التوفير — والذكي ما يدفع الاستعجال لثياب الدوام اللي يحتاجها الأسبوع الجاي.

وعند التسليم يعلقون على كل قطعة رقم بطاقة (custom_id) — عشان لما تستلم 20 قطعة، تعرف أن هذا ثوبك أنت مو ثوب غيرك، مهما اختلف ترتيب الخروج. طلعت قطعتان ببقع ما راحت؟ ترجّع القطعتين فقط بأرقام بطاقتيهما مع ملاحظة "بقعة زيت — تحتاج معالجة خاصة" (إعادة الفاشل فقط مع التعديل المناسب) — ما أحد يعيد غسل السلة كلها. وفندق بيوقع عقداً مع المغسلة بشرط "كل قطعة ترجع خلال 30 ساعة"؟ بيرسل شحنة كل 4 ساعات، لأن قطعة وصلت بعد الشحنة مباشرة بتنتظر 4 ثم تُعالج بحد أقصى 24 — يعني 28 ساعة وداخل الوعد.

A dry cleaner offers two services: express — you sit and wait, your thobe is ready within the hour at full price (synchronous), and regular — drop the clothes off and come back "tomorrow or the day after" at half price (batch: a long window with no promised time). If you have an event tonight, only a fool picks regular for the savings — and only a spendthrift pays express rates for next week's work clothes.

At drop-off they pin a ticket number on every piece (custom_id) — so when you collect 20 items, you know this thobe is yours regardless of the order they come out. Two pieces come back still stained? You return those two only, by their ticket numbers, with a note "oil stain — needs special treatment" (resubmit only failures, with the fitting modification) — nobody rewashes the whole basket. And a hotel signing a "every item back within 30 hours" contract with the cleaner? It sends a van every 4 hours, because an item arriving right after a van waits 4, then takes at most 24 — 28 hours, inside the promise.

في الاختبارOn the exam

سؤال رسمي كامل في الدليل مبني على هذا الموضوع (فحص حاجب + تقرير ليلي). خلاصة التعامل:

  • صنّف كل حمل: حاجب = synchronous، ليلي/أسبوعي = دفعات. الجواب الصحيح يقسم، ما يعمم.
  • أسئلة الحساب: أقصى انتظار قبل الدفعة + 24 ساعة معالجة لازم يبقى تحت الـ SLA بهامش — نوافذ 4 ساعات لسلا الـ 30 ساعة.
  • فشل جزئي؟ الجواب يذكر custom_id + إعادة الفاشل فقط + تعديل يناسب السبب (تقسيم الطويل).
  • استبعد: "الدفعات غالباً سريعة" لتدفق حاجب، "الترتيب العشوائي مشكلة"، وfallback timeout الهجين.

A full official guide question is built on this topic (blocking check + overnight report). The playbook:

  • Classify each workload: blocking = synchronous, nightly/weekly = batch. The correct answer splits; it never generalizes.
  • Math questions: max pre-batch wait + 24h processing must stay under the SLA with margin — 4-hour windows for a 30-hour SLA.
  • Partial failure? The right answer mentions custom_id + resubmitting only failures + a cause-fitting modification (chunk the long ones).
  • Eliminate: "batches are usually fast" for a blocking flow, "random ordering is a problem", and the hybrid timeout-fallback.

صحيح. تجريب البرومبت على عينة قبل الحجم الكامل يرفع نجاح المرور الأول ويجنّبك إعادة معالجة 200 ألف عقد بسبب عيب كان سيظهر في أول 200. الحمل متسامح مع الكمون فالدفعات صح، وsynchronous يضاعف التكلفة بلا مبرر، وتقسيم الدفعات لا يعالج مشكلة البرومبت غير المجرَّب. Correct. Refining the prompt on a sample before full volume maximizes first-pass success and spares you reprocessing 200k contracts over a flaw the first 200 would have exposed. The workload is latency-tolerant so batch is right, synchronous doubles cost for nothing, and splitting batches does not fix an untested prompt.
الصحيح B: عينة أولاً ثم الحجم الكامل بالدفعات — "prompt refinement on a sample set" من الدليل لرفع نجاح المرور الأول وتقليل تكاليف الإعادة. الإرسال الأعمى يخاطر بإعادة كاملة، وsynchronous هدر، والتقسيم لا يحل شيئاً هنا. The answer is B: sample first, then the full volume via batch — the guide's "prompt refinement on a sample set" to maximize first-pass success and cut resubmission costs. Blind submission risks a full redo, synchronous is waste, and splitting solves nothing here.

خلاصةTakeaway

  • الأرقام الثلاثة: توفير 50%، نافذة حتى 24 ساعة، بدون SLA مضمون — و"غالباً أسرع" ليست ضمانة.The three numbers: 50% savings, up to a 24-hour window, no guaranteed SLA — and "usually faster" is not a guarantee.
  • حاجب (pre-merge) = synchronous دائماً؛ ليلي/أسبوعي غير حاجب = دفعات دائماً — القرار قرار كمون لا تكلفة.Blocking (pre-merge) = always synchronous; non-blocking nightly/weekly = always batch — it is a latency decision, not a cost one.
  • لا multi-turn tool calling داخل طلب الدفعة — المهام الوكيلة التفاعلية خارج نطاقها.No multi-turn tool calling inside a batch request — interactive agentic tasks are out of scope.
  • حساب الـ SLA: أقصى انتظار + 24 ≤ الوعد بهامش — نوافذ 4 ساعات تضمن SLA الثلاثين ساعة (28 ساعة أسوأ حالة).SLA math: max wait + 24 must sit under the promise with margin — 4-hour windows secure the 30-hour SLA (28-hour worst case).
  • فشل جزئي: أعد الفاشل فقط بـ custom_id مع تعديل يناسب السبب — وجرّب البرومبت على عينة قبل أي حجم كبير.Partial failure: resubmit only the failures by custom_id with a cause-fitting modification — and refine the prompt on a sample before any large volume.
