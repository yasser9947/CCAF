4.6

معماريات المراجعة متعددة النسخ والمرور Multi-instance & multi-pass review architectures

ليش هالموضوع مهم؟ لأن أخطر مراجع للكود هو اللي كتبه: سياق التوليد يدافع عن قراراته — والجودة الحقيقية تجي من نسخة مستقلة ومرور مقسّم بذكاء. Why this matters: the most dangerous reviewer of code is its author — generation context defends its own decisions, and real quality comes from an independent instance and intelligently split passes.

وش بتتعلمWhat you'll learn

  • حدود المراجعة الذاتية: النموذج يحتفظ بسياق تفكيره من التوليد فتقل احتمالية تشكيكه بقراراته في نفس الجلسةSelf-review limitations: the model retains its generation reasoning context, making it less likely to question its own decisions in the same session

  • المراجعة متعددة المرور: تقسيم المراجعات الكبيرة إلى مرور محلي لكل ملف + مرور تكاملي لتدفق البيانات بين الملفات، لتفادي تشتت الانتباه والنتائج المتناقضةMulti-pass review: splitting large reviews into per-file local passes + a cross-file integration pass for data flow, avoiding attention dilution and contradictory findings

1 ليش المراجعة الذاتية قاصرةWhy self-review falls short

تطلب من وكيل ولّد كوداً: "الحين راجع كودك بعناية واكتشف الأخطاء". يبدو منطقياً — لكنه ضعيف بنيوياً. السبب مو كسل النموذج، بل سياق التوليد نفسه: في نفس الجلسة، النموذج ما زال يحمل سلسلة التفكير اللي أوصلته لكل قرار — "اخترت هذا الشرط لأن..." — فلما يراجع، يقرأ الكود عبر عدسة تبريراته. القرار الغلط يجي ومعه مبرره جاهزاً، فيبدو صحيحاً. النتيجة: "الكود سليم" فوق ثغرة واضحة.

البديل المعتمد في الدليل: نسخة مراجعة مستقلة — استدعاء جديد (أو جلسة جديدة) يستلم الكود ومعايير المراجعة فقط، بدون أي سياق من التوليد. هذي النسخة ما عندها التزام نفسي تجاه القرارات، فتقرأ الكود كما هو مكتوب، لا كما قُصد — وتكتشف المشاكل الدقيقة اللي عمي عنها المولّد. والدليل صريح في التراتبية: النسخة المستقلة أفعل من تعليمات المراجعة الذاتية ومن extended thinking — التفكير الأطول داخل نفس السياق المنحاز يعمّق التبرير، ما يكسره.

You ask an agent that just generated code: "now review your code carefully and find the bugs". Sounds reasonable — but it is structurally weak. The cause is not model laziness; it is generation context itself: in the same session, the model still carries the chain of reasoning behind every decision — "I chose this condition because..." — so when it reviews, it reads the code through the lens of its own justifications. A wrong decision arrives with its excuse pre-attached, so it looks right. The result: "the code is correct" sitting on top of an obvious flaw.

The guide's endorsed alternative: an independent review instance — a fresh call (or session) receiving only the code and the review criteria, with zero generation context. That instance has no psychological commitment to the decisions, so it reads the code as written, not as intended — and catches the subtle issues the generator was blind to. The guide is explicit about the ranking: the independent instance beats self-review instructions and extended thinking — longer thinking inside the same biased context deepens the justification; it does not break it.

SELF-REVIEW vs INDEPENDENT REVIEW

SAME SESSION (SELF-REVIEW)
context window contains:
- the generated code
- the REASONING that produced it
- every decision's justification
reads code through its own excuses
unlikely to question its decisions
extended thinking deepens the bias
FRESH INSTANCE (INDEPENDENT)
context window contains:
- the code (as text)
- the review criteria
- NOTHING else
reads what the code DOES, not what was meant
no commitment to prior decisions
catches the subtle issues

الفرق كله في محتوى نافذة السياق: المراجع الذاتي يحمل تبريراته، والمستقل يحمل الكود والمعايير فقط The whole difference is context-window content: the self-reviewer carries its justifications, the independent one carries only code and criteria

نسخة مراجعة مستقلة: استدعاء نظيف يستلم الكود والمعايير فقط: An independent review instance: a clean call receiving only code and criteria: 

# Instance A generated the code (its session holds all the reasoning).
generated_diff = generator_session.result_diff

# Instance B reviews with a FRESH call: no generation context crosses over.
review = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=4096,
    system=REVIEW_CRITERIA,        # explicit report/skip criteria (see 4.1)
    messages=[{
        "role": "user",
        "content": f"Review this diff against the criteria:\n\n{generated_diff}",
    }],
)
# Instance B never saw WHY the code was written this way —
# so it evaluates what the code actually does.

مفهوم أساسيKey concept

الاستقلالية هنا خاصية معمارية مو تعليمة: تتحقق بفصل نوافذ السياق (استدعاء/جلسة جديدة)، لا بكتابة "راجع بموضوعية" داخل نفس الجلسة الملوثة بسياق التوليد.
Independence here is an architectural property, not an instruction: it is achieved by separating context windows (a fresh call/session), not by writing "review objectively" inside the same session contaminated with generation context.

2 المراجعة متعددة المرور للتغييرات الكبيرةMulti-pass review for large changes

مشكلة ثانية مختلفة تظهر مع الحجم: PR يعدّل 14 ملفاً، ومراجعة "مرور واحد" على كل الملفات معاً تطلع بنتائج مختلة — تعليقات عميقة على أول ملفين وسطحية على الباقي، أخطاء واضحة تنفلت، وأسوأ شي: نتائج متناقضة — نفس النمط يُرفض في ملف ويُمرَّر في ملف ثاني بنفس الـ PR. هذا تشتت الانتباه (attention dilution): جودة الانتباه تتوزع وتضعف مع كثرة المحتوى المتزامن، ونافذة سياق أكبر ما تحل المشكلة — تكديس أكثر لنفس الانتباه المشتت.

علاج الدليل: قسّم المراجعة لمرورين متخصصين. المرور الأول محلي لكل ملف: كل ملف يُراجع وحده باهتمام كامل للمشاكل المحلية (منطق، معالجة أخطاء، أمان الملف نفسه) — عمق متسق لكل ملف بلا استثناء. المرور الثاني تكاملي عبر الملفات: يركز حصرياً على تدفق البيانات بين الملفات، توافق الواجهات، والعقود بين الوحدات. كل مرور له تركيز واحد واضح، فتختفي التناقضات ويثبت العمق.

A second, different problem appears with scale: a PR touches 14 files, and a single-pass review over all of them produces lopsided results — deep comments on the first two files and shallow ones on the rest, obvious bugs slipping through, and worst of all: contradictory findings — the same pattern flagged in one file and approved in another within the same PR. This is attention dilution: attention quality spreads thin across too much simultaneous content, and a larger context window does not fix it — it just piles more onto the same diluted attention.

The guide's remedy: split the review into two specialized passes. Pass one is per-file local: each file reviewed alone with full attention on local issues (logic, error handling, file-level security) — consistent depth for every file, no exceptions. Pass two is cross-file integration: focused exclusively on data flow between files, interface compatibility, and inter-module contracts. Each pass has one clear focus, so contradictions vanish and depth holds steady.

MULTI-PASS REVIEW PIPELINE (14-FILE PR)

single pass over 14 files -> attention dilution: uneven depth, missed bugs, contradictory findings

PASS 1 — PER-FILE LOCAL ANALYSIS

file01.py file02.py file03.py ... x14, one focused call each

full attention per file -> consistent depth, local issues (logic, error handling)

PASS 2 — CROSS-FILE INTEGRATION

data flow across files - interface compatibility - contracts between modules
one pass, one focus: how the pieces fit together

merged findings: consistent depth + integration issues caught, no contradictions

خط المراجعة: مرور محلي مركّز لكل ملف، ثم مرور تكاملي واحد لتدفق البيانات — كل مرور بتركيز واحد The review pipeline: a focused local pass per file, then one integration pass for data flow — each pass with a single focus

لمحة سريعةQuick insight

سعة السياق غير جودة الانتباه. نافذة أكبر تستوعب الملفات الـ 14 كلها — لكنها لا ترفع جودة الانتباه الموزع عليها. الحل تقسيم الشغل، مو توسيع الوعاء.
Context capacity is not attention quality. A bigger window can hold all 14 files — but it does not raise the quality of the attention spread across them. The fix is splitting the work, not widening the container.

فخ الاختبارExam trap

من سؤال رسمي (مراجعة 14 ملفاً غير متسقة): المشتتات هي (1) "ألزم المطورين بتقسيم الـ PRs" — يرمي العبء عليهم بدون تحسين النظام؛ (2) "نموذج أعلى بنافذة سياق أكبر" — سوء فهم لأن سعة السياق لا تعالج جودة الانتباه؛ (3) "ثلاث مراجعات كاملة وخذ ما يتفق عليه اثنان" — التصويت يكبت الأخطاء الحقيقية اللي تنكشف بشكل متقطع. الصحيح دائماً: مرور لكل ملف + مرور تكاملي منفصل.
From an official question (the inconsistent 14-file review): the distractors are (1) "make developers split their PRs" — shifts the burden without improving the system; (2) "a higher-tier model with a larger context window" — a misunderstanding, capacity does not fix attention quality; (3) "three full-review runs, keep findings two agree on" — consensus voting suppresses real bugs that surface intermittently. The correct answer is always: per-file passes + a separate integration pass.

3 التصريح بالثقة لتوجيه المراجعةConfidence self-reporting for routing

الأداة الثالثة في معمارية المراجعة: مرور تحقق يصرّح فيه النموذج بدرجة ثقته مع كل نتيجة كحقل بيانات مهيكل. الفكرة مو فلترة النتائج — الفكرة توجيهها (routing) توجيهاً معايراً: النتيجة عالية الثقة (0.9) تنشر تلقائياً كتعليق على الـ PR، والمتوسطة (0.6) تروح لطابور فرز بشري، والمنخفضة (0.3) تُسجَّل للتحليل بدون إزعاج أحد. كل نتيجة تاخذ المسار المناسب لموثوقيتها — ومع الوقت تقارن الثقة المصرّحة بقرارات المطورين فتعاير النظام.

وهنا لازم توقف عند تمييز يحبه الاختبار، لأنه يبدو تناقضاً مع 4.1 وهو ليس كذلك: في 4.1 قلنا "بلّغ عن النتائج عالية الثقة فقط" تعليمة فلترة غامضة فاشلة — تطلب من النموذج يقمع نتائج داخلياً بمعيار غير معرّف، فلا تتحسن الدقة. هنا العكس تماماً: النموذج يبلّغ عن كل شي حسب معاييره التصنيفية، والثقة تطلع كحقل بيانات صريح، والتوجيه قرار برمجي خارجي بعتبات تضبطها أنت وتعايرها بالبيانات. الفرق: قمع داخلي غامض مقابل توجيه خارجي معاير.

The third tool in the review architecture: a verification pass where the model self-reports confidence alongside each finding as a structured data field. The idea is not filtering findings — it is calibrated routing: a high-confidence finding (0.9) auto-posts as a PR comment, a medium one (0.6) goes to a human triage queue, a low one (0.3) is logged for analysis without bothering anyone. Every finding takes the path its reliability deserves — and over time you compare self-reported confidence against developer verdicts to calibrate the system.

Pause here for a distinction the exam loves, because it looks like a contradiction with 4.1 and is not: in 4.1, "only report high-confidence findings" was a failed vague filtering instruction — asking the model to internally suppress findings by an undefined bar, improving nothing. Here it is the exact opposite: the model reports everything per its categorical criteria, confidence emerges as an explicit data field, and routing is an external programmatic decision with thresholds you set and calibrate with data. The difference: vague internal suppression versus calibrated external routing.

CONFIDENCE-BASED ROUTING — REPORT ALL, ROUTE BY DATA

verification pass emits EVERY finding
+ "confidence": 0.0 - 1.0 (a structured field)

التوجيه بالثقة: النموذج يبلّغ عن الكل والعتبات في كودك أنت — نشر تلقائي أو فرز بشري أو تسجيل فقط Confidence routing: the model reports everything and the thresholds live in your code — auto-post, human triage, or log only

نتيجة تحقق بحقل الثقة + منطق التوجيه الخارجي: A verification finding with the confidence field + the external routing logic: 

finding = {
    "location": "billing/rates.py:88",
    "issue": "currency conversion applied twice on refunds",
    "severity": "high",
    "detected_pattern": "double conversion in refund path",
    "confidence": 0.55,          # self-reported, structured — not a filter
}

# routing happens OUTSIDE the model, with calibratable thresholds
def route(finding: dict) -> None:
    c = finding["confidence"]
    if c >= 0.8:
        post_pr_comment(finding)          # trusted enough to publish
    elif c >= 0.5:
        send_to_triage_queue(finding)     # a human decides
    else:
        log_for_calibration(finding)      # data, not noise

نصيحةTip

عاير العتبات بالبيانات: قارن دورياً ثقة النتائج بمصيرها عند المطورين (قُبلت/رُفضت). إذا كانت نتائج الـ 0.9 تُرفض كثيراً فالثقة المصرّحة متضخمة — عدّل العتبات أو حسّن برومبت التحقق.
Calibrate thresholds with data: periodically compare finding confidence against developer verdicts (accepted/dismissed). If 0.9 findings get dismissed often, self-reported confidence is inflated — adjust thresholds or improve the verification prompt.

تنبيهWarning

لا تخلط بين الآليتين في الاختبار: "أضف للبرومبت: بلّغ عن الثقة العالية فقط" = فخ 4.1 (فلترة غامضة). "أضف حقل confidence لكل نتيجة ووجّهها برمجياً" = مهارة 4.6 المشروعة. الصياغة الأولى قمع، والثانية بيانات.
Do not mix the two mechanisms on the exam: "add to the prompt: only report high confidence" = the 4.1 trap (vague filtering). "Add a confidence field to each finding and route programmatically" = the legitimate 4.6 skill. The first phrasing is suppression; the second is data.

مثال من الحياة: المؤلف ودار النشرReal-life example: the author and the publishing house

اسأل أي مؤلف: راجع مخطوطتك بنفسك عشرين مرة، وبتظل الأخطاء تعبر. مو لأنه مهمل — لأنه يقرأ ما قصد كتابته، لا ما كُتب فعلاً. عينه تكمّل الناقص وتصحح الخطأ تلقائياً لأن القصة كلها حية في ذهنه (سياق التوليد). عشان كذا دور النشر ما تعتمد أبداً على مراجعة المؤلف لنفسه، وتسلّم المخطوطة لمحرر مستقل ما شارك في الكتابة — يقرأ النص كما هو على الورق، فيصطاد ما عمي عنه صاحبه.

والدار المحترفة تقسم المراجعة مرورين: تدقيق فصل بفصل (لغة، صياغة، سلاسة — المرور المحلي لكل ملف) ثم مرور استمرارية على الكتاب كاملاً: هل عمر البطلة في الفصل 12 يطابق الفصل 3؟ هل الخط الزمني متسق؟ (المرور التكاملي عبر الملفات). ومع كل ملاحظة، المحرر يكتب هامشاً بدرجة يقينه: "خطأ قاطع — يُصحح فوراً" أو "أظنها سهواً — تُعرض على المؤلف" — فتتوزع الملاحظات بين تصحيح مباشر وقائمة نقاش: هذا توجيه الثقة بعينه.

Ask any author: proofread your own manuscript twenty times, and errors still slip through. Not carelessness — the author reads what they meant to write, not what is actually written. The eye auto-completes and auto-corrects because the whole story lives in their head (generation context). That is why publishing houses never rely on author self-review and hand the manuscript to an independent editor who took no part in the writing — reading the text as it sits on the page, catching what its owner is blind to.

A professional house also splits the review into two passes: chapter-by-chapter copyediting (language, phrasing, flow — the per-file local pass) and then a continuity pass across the whole book: does the heroine's age in chapter 12 match chapter 3? Is the timeline consistent? (the cross-file integration pass). And with each note, the editor writes a margin mark of certainty: "definite error — fix immediately" or "probably an oversight — raise with the author" — notes split between direct fixes and a discussion list: confidence routing in the flesh.

في الاختبارOn the exam

سؤالان رسميان يدوران في هذا الفلك (المولّد يمدح شغله، ومراجعة الـ 14 ملفاً). القواعد:

  • مولّد يراجع نفسه ويقول "كل شي تمام"؟ الجواب: نسخة مستقلة بدون سياق التوليد — مو صياغة أقوى ولا extended thinking.
  • مراجعة كبيرة غير متسقة/متناقضة؟ الجواب: مرور لكل ملف + مرور تكاملي منفصل — مو نموذج أكبر ولا تصويت ثلاثي ولا ترحيل العبء للمطورين.
  • توجيه النتائج حسب موثوقيتها؟ الجواب: حقل confidence مهيكل + عتبات توجيه خارجية.
  • استبعد أي خيار يحل مشكلة معمارية (انحياز السياق، تشتت الانتباه) بتعليمات أشد أو موارد أكبر.

Two official questions orbit this topic (the self-praising generator, and the 14-file review). The rules:

  • A generator reviewing itself and saying "all good"? Answer: an independent instance without generation context — not stronger wording, not extended thinking.
  • A large review that is inconsistent/contradictory? Answer: per-file passes + a separate integration pass — not a bigger model, not triple-run voting, not offloading onto developers.
  • Routing findings by reliability? Answer: a structured confidence field + external routing thresholds.
  • Eliminate any option solving an architectural problem (context bias, attention dilution) with sterner instructions or bigger resources.

A bigger window does not raise attention quality, voting suppresses intermittently-caught bugs, and mandating smaller PRs offloads the burden without improving anything.
الصحيح C: مرور محلي لكل ملف + مرور تكاملي منفصل — جواب السؤال الرسمي المطابق في الدليل. سعة السياق لا تعالج جودة الانتباه، والتصويت الثلاثي يقمع أخطاء حقيقية، وترحيل العبء للمطورين ليس تحسيناً للنظام. The answer is C: per-file local passes + a separate integration pass — the matching official question's answer in the guide. Context capacity does not fix attention quality, triple voting suppresses real bugs, and offloading to developers is not a system improvement.
3

تبغى النتائج عالية الموثوقية تُنشر تلقائياً على الـ PR، والمشكوك فيها تمر على إنسان أولاً. وش التصميم الصحيح؟

You want high-reliability findings auto-posted to the PR, and doubtful ones to pass through a human first. What is the right design?

صحيح. الثقة كحقل بيانات + توجيه خارجي بعتبات قابلة للمعايرة = مهارة 4.6. الخيار A هو فخ الفلترة الغامضة من 4.1، وC يدفن المطورين بالضجيج، وD يضاعف التكلفة ثلاثاً ويكبت النتائج الصحيحة غير المجمع عليها. Correct. Confidence as a data field + external routing with calibratable thresholds = the 4.6 skill. Option A is the 4.1 vague-filtering trap, C buries developers in noise, and D triples cost while suppressing correct non-unanimous findings.
الصحيح B: التصريح بالثقة كحقل مهيكل مع توجيه برمجي معاير — هذا "calibrated review routing" من الدليل. التعليمة الغامضة قمع داخلي (فخ 4.1)، والنشر الشامل والإجماع الثلاثي كلاهما تطرف بلا معايرة. The answer is B: self-reported confidence as a structured field with calibrated programmatic routing — the guide's "calibrated review routing". The vague instruction is internal suppression (the 4.1 trap), and blanket posting or triple unanimity are both uncalibrated extremes.

خلاصةTakeaway

  • المراجعة الذاتية قاصرة بنيوياً: سياق التوليد يدفع النموذج لتبرير قراراته بدل التشكيك فيها.Self-review is structurally limited: generation context pushes the model to justify its decisions rather than question them.
  • النسخة المستقلة (كود + معايير فقط، بدون سياق سابق) تكشف المشاكل الدقيقة أكثر من تعليمات المراجعة الذاتية ومن extended thinking.An independent instance (code + criteria only, no prior context) catches subtle issues better than self-review instructions and extended thinking.
  • المراجعات الكبيرة: مرور محلي لكل ملف + مرور تكاملي منفصل — يعالج تشتت الانتباه والنتائج المتناقضة؛ النافذة الأكبر لا تعالجها.Large reviews: per-file local passes + a separate integration pass — fixing attention dilution and contradictory findings; a bigger window does not.
  • التصريح بالثقة كحقل مهيكل + عتبات توجيه خارجية = routing معاير: نشر تلقائي، فرز بشري، أو تسجيل.Self-reported confidence as a structured field + external thresholds = calibrated routing: auto-post, human triage, or log.
  • فرّق دائماً: "بلّغ عن الثقة العالية فقط" في البرومبت = فخ 4.1؛ حقل confidence للتوجيه البرمجي = مهارة 4.6.Always distinguish: "only report high confidence" in the prompt = the 4.1 trap; a confidence field for programmatic routing = the 4.6 skill.
