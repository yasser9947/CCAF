4.4

حلقات التحقق والإعادة والتغذية الراجعة Validation, retry & feedback loops

ليش هالموضوع مهم؟ لأن السكيما ضمنت الشكل فقط — جودة الاستخراج الحقيقية تجي من حلقة: تحقق دلالي، إعادة بأخطاء محددة، ومعرفة دقيقة بمتى الإعادة عبث. Why this matters: the schema only guaranteed shape — real extraction quality comes from a loop: semantic validation, retries with specific errors, and knowing exactly when retrying is futile.

  • بناء طلب المتابعة الصحيح: المستند الأصلي + الاستخراج الفاشل + أخطاء التحقق المحددةBuilding the correct follow-up request: the original document + the failed extraction + the specific validation errors
  • حدود الإعادة: تنجح مع أخطاء التنسيق والهيكل، وتفشل حتماً لما تكون المعلومة غائبة عن المستند (موجودة فقط في مصدر خارجي)The limits of retry: it succeeds on format and structural errors, and inevitably fails when the information is absent from the document (existing only in an external source)

1 حلقة التحقق والإعادةThe validation-retry loop

وصلتك بيانات ملتزمة بالسكيما من 4.3 — الآن يبدأ التحقق الدلالي: هل مجموع البنود يساوي الإجمالي؟ هل التاريخ منطقي؟ هل القيم في حقولها الصحيحة؟ لما يفشل التحقق، أسوأ رد فعل هو إعادة الطلب كما هو ("جرّب مرة ثانية") — النموذج ما يدري وش غلط، فيكرر نفس الخطأ غالباً. النمط الصحيح من الدليل: retry-with-error-feedback.

طلب الإعادة الفعال يحمل ثلاثة مكونات، الثلاثة كلها: المستند الأصلي (عشان يرجع للمصدر لا لذاكرته)، والاستخراج الفاشل (عشان يعرف وش أنتج)، وأخطاء التحقق المحددة نصاً: "مجموع البنود 4,700 لكن stated_total = 5,200" — مو "فيه خطأ، صححه". الخطأ المحدد يوجه انتباه النموذج للحقل المكسور بالضبط، فيصحح جراحياً بدل ما يعيد توليد كل شي ويكسر حاجة ثانية.

Schema-compliant data arrived from 4.3 — now semantic validation begins: do the line items sum to the total? Is the date plausible? Are values in their right fields? When validation fails, the worst reaction is resending the request unchanged ("try again") — the model has no idea what was wrong, so it usually repeats the same mistake. The guide's pattern: retry-with-error-feedback.

An effective retry request carries three components, all three: the original document (so it returns to the source, not its memory), the failed extraction (so it knows what it produced), and the specific validation errors, spelled out: "line items sum to 4,700 but stated_total = 5,200" — not "there is an error, fix it". The specific error points the model's attention at exactly the broken field, so it corrects surgically instead of regenerating everything and breaking something else.

الحلقة: استخراج ثم تحقق دلالي؛ عند الفشل إعادة بالمكونات الثلاثة، وعند نفاد المحاولات تحويل لمراجعة بشرية The loop: extract, then semantically validate; on failure retry with all three components, on exhausted attempts route to human review

حلقة تحقق وإعادة بنكهة Pydantic — الأخطاء المحددة ترجع للنموذج: A Pydantic-flavored validation-retry loop — specific errors go back to the model: 

from pydantic import BaseModel, ValidationError, model_validator

class Invoice(BaseModel):
    invoice_number: str
    line_items: list[LineItem]
    stated_total: float            # what the document SAYS
    calculated_total: float        # what the items actually SUM to
    conflict_detected: bool        # true when the source contradicts itself

    @model_validator(mode="after")
    def totals_must_reconcile(self):
        calc = round(sum(i.amount for i in self.line_items), 2)
        if abs(calc - self.stated_total) > 0.01 and not self.conflict_detected:
            raise ValueError(
                f"line items sum to {calc} but stated_total is "
                f"{self.stated_total}; if the document itself is inconsistent, "
                f"set conflict_detected=true instead of inventing numbers"
            )
        return self

def extract_with_retry(document: str, max_retries: int = 2) -> Invoice:
    error_feedback = None
    for attempt in range(max_retries + 1):
        raw = call_extraction_tool(document, error_feedback)   # tool_use, forced
        try:
            return Invoice.model_validate(raw)
        except ValidationError as e:
            error_feedback = build_retry_prompt(document, raw, str(e))
    route_to_human_review(document, raw, error_feedback)       # loop exhausted

بناء طلب الإعادة بمكوناته الثلاثة: Building the retry request with its three components: 

def build_retry_prompt(document: str, failed: dict, errors: str) -> str:
    return f"""Your previous extraction failed validation.

<document>
{document}
</document>

<failed_extraction>
{json.dumps(failed, indent=2)}
</failed_extraction>

<validation_errors>
{errors}
</validation_errors>

Re-read the document, correct ONLY the fields named in the validation
errors, and call record_invoice again. If the document itself contains
contradictory values, set conflict_detected=true — do not force numbers
to reconcile."""

مفهوم أساسيKey concept

قيمة الإعادة كلها في تحديد الخطأ: "المجموع 4,700 والمصرح 5,200" يصلح؛ "فيه خطأ" يدوّخ. الإعادة الموجهة بأخطاء دقيقة تحوّل النموذج من مخمّن إلى مصحح.
All of retry's value lives in error specificity: "sum is 4,700, stated 5,200" fixes; "something is wrong" flails. Retries guided by precise errors turn the model from a guesser into a corrector.

2 حدود الإعادة: متى تصير عبثاًThe limits of retry: when it becomes futile

قبل ما تعيد، اسأل السؤال الفاصل: هل المعلومة موجودة أصلاً في المستند المقدَّم؟ الإعادة تشتغل مع أخطاء التنسيق والهيكل: تاريخ بصيغة خاطئة، قيمة بحقل غلط، مجموع محسوب خطأ — كلها حالات "المعلومة موجودة والاستخراج تعثر"، فتوجيه الانتباه يصلحها. لكن إذا كان رقم أمر الشراء ما ذُكر في الفاتورة أساساً — موجود فقط في نظام خارجي ما مررته — فكل محاولة إضافية حرق توكنز: ما تقدر تستخرج شيئاً غير موجود. علامة هذي الحالة في الإنتاج: نفس الحقل يفشل بنفس الطريقة عبر كل المحاولات، أو يتقلب بين null وقيم ملفقة مختلفة.

التصرف الهندسي الصحيح مع المعلومة الغائبة: حقل nullable (من 4.3)، إثراء لاحق من المصدر الصحيح، أو تحويل للمراجعة البشرية — وأبداً ليس "محاولات أكثر بإصرار أعلى".

Before retrying, ask the deciding question: does the information exist in the provided document at all? Retry works on format and structural errors: a date in the wrong format, a value in the wrong field, a miscomputed total — all cases of "the information is there and extraction stumbled", where directed attention fixes it. But if the PO number was never mentioned in the invoice — it lives only in an external system you did not pass — every extra attempt burns tokens: you cannot extract what is not there. The production signature of this case: the same field failing the same way across all attempts, or oscillating between null and assorted fabricated values.

The sound engineering response to absent information: a nullable field (from 4.3), later enrichment from the right source, or routing to human review — and never "more attempts with more insistence".

سؤال واحد يحسم: المعلومة موجودة والاستخراج تعثر؟ أعد بتغذية راجعة. غائبة؟ الإعادة حرق مال One question decides: information present but extraction stumbled? Retry with feedback. Absent? Retrying burns money

لمحة سريعةQuick insight

الإعادة تصلح أخطاء الإخراج، لا نقص المدخلات. إذا كان الحل الحقيقي "أعطه المستند الثاني"، فلا صيغة برومبت ولا عدد محاولات بيعوّض عنه.
Retry fixes output errors, not missing input. If the real fix is "hand it the other document", no prompt wording and no retry count will substitute for it.

فخ الاختبارExam trap

لما يذكر السؤال أن المعلومة "موجودة في نظام/مستند خارجي لم يُقدَّم"، كل خيارات "زد المحاولات"، "قوِّ صياغة البرومبت"، "اجعل الحقل إلزامياً ليجتهد النموذج" مشتتات — بعضها يفاقم المشكلة بدفع النموذج للتلفيق. الجواب الصحيح يعالج المدخلات: nullable، إثراء من المصدر، أو مسار بشري.
When the question states the information "exists in an external system/document that was not provided", every "increase retries", "strengthen the prompt wording", "make the field required so the model tries harder" option is a distractor — some actively worsen things by pushing fabrication. The correct answer fixes the input side: nullable, source enrichment, or a human path.

3 حقول التغذية الراجعة والتصحيح الذاتيFeedback-loop & self-correction fields

الحلقة تصير أذكى لما تصمم حقولاً في السكيما نفسها تخدم التحسين المستمر. أولها detected_pattern في نتائج المراجعة: كل نتيجة تسجل أي بناء برمجي أطلقها ("f-string SQL query"، "bare except"، "mutable default arg"). لما يرفض المطورون نتائج معينة، تجمّع الرفض حسب النمط فتشوف بالأرقام: "نمط X مرفوض بنسبة 80% = مصدر إيجابيات كاذبة" — فتعدّل معاييره أو تعطله (ربطاً بـ 4.1) بتحليل منهجي بدل الانطباعات.

وثانيها ثنائي التصحيح الذاتي للاستخراج: بدل استخراج الإجمالي مرة واحدة، اطلب حقلين — stated_total (المكتوب في المستند نصاً) وcalculated_total (مجموع البنود اللي يحسبه النموذج). تطابقا؟ ثقة أعلى. اختلفا؟ عندك إشارة تعارض قابلة للفحص الآلي. وثالثها conflict_detected: قيمة boolean يرفعها النموذج لما يتناقض المصدر نفسه (جدول يقول 5,200 وفقرة تقول 5,400). بدون هذا الحقل، النموذج المحاصر بالتحقق قد "يوفّق" الأرقام بنفسه ويخفي التعارض — ومع الحقل، التعارض يطفو كبيانات صريحة تقرر أنت كيف تعالجها.

The loop gets smarter when you design fields inside the schema itself that serve continuous improvement. First, detected_pattern on review findings: each finding records which code construct triggered it ("f-string SQL query", "bare except", "mutable default arg"). When developers dismiss findings, you aggregate dismissals by pattern and see it in numbers: "pattern X dismissed 80% of the time = a false-positive source" — so you refine or disable its criteria (tying back to 4.1) through systematic analysis instead of impressions.

Second, the self-correction pair for extraction: rather than extracting the total once, request two fields — stated_total (what the document literally says) and calculated_total (the line-item sum the model computes). They match? Higher confidence. They differ? You have a machine-checkable discrepancy signal. Third, conflict_detected: a boolean the model raises when the source contradicts itself (a table says 5,200, a paragraph says 5,400). Without this field, a validation-cornered model may quietly "reconcile" the numbers and bury the conflict — with it, the conflict surfaces as explicit data you decide how to handle.

THREE FIELDS THAT MAKE THE LOOP SMARTER

detected_pattern

which construct triggered the finding -> aggregate dismissals -> find FP sources

stated_total vs calculated_total

document's claim vs computed sum -> mismatch = checkable discrepancy flag

conflict_detected

source contradicts ITSELF -> surface it as data, never silently reconcile

design the schema to CARRY quality signals — the loop then improves itself with data

ثلاثة حقول تحمل إشارات الجودة داخل المخرجات نفسها: نمط الاكتشاف، وثنائي الإجمالي، وراية التعارض Three fields carrying quality signals inside the output itself: the detection pattern, the totals pair, and the conflict flag

نتيجة مراجعة مهيكلة بحقل detected_pattern + استخراج بثنائي الإجمالي وراية التعارض: A structured review finding with detected_pattern + an extraction with the totals pair and conflict flag:

  "invoice_number": "INV-2026-0341",
  "line_items": [

نصيحةTip

اربط الحلقات ببعض: تقرير أسبوعي يجمّع الرفض حسب detected_pattern، والأنماط الأعلى رفضاً تدخل قائمة التحسين — أمثلة few-shot جديدة (4.2) أو تعديل معايير (4.1). كذا تتحول الإيجابيات الكاذبة من إزعاج إلى وقود تحسين.
Chain the loops together: a weekly report aggregating dismissals by detected_pattern, with the most-dismissed patterns entering the improvement queue — new few-shot examples (4.2) or criteria changes (4.1). False positives turn from noise into improvement fuel.

تنبيهWarning

تحقق صارم بدون مخرج conflict_detected يدفع النموذج "لتجميل" البيانات المتعارضة حتى تعبر الفحص — فتخسر أهم إشارة جودة في النظام. لازم يكون للتعارض طريق شرعي للظهور.
Strict validation with no conflict_detected exit pushes the model to "beautify" contradictory data until it passes the checks — losing the most important quality signal in the system. Conflict must have a legitimate way to surface.

مثال من الحياة: المعلم والقلم الأحمرReal-life example: the teacher's red pen

معلم رياضيات استلم واجباً فيه أخطاء. المعلم الضعيف يرجّع الورقة مكتوب عليها "أعد الحل" — الطالب بيعيد نفس الأخطاء لأنه ما يدري وينها. المعلم الشاطر يرجّع الورقة ومعها ثلاثة أشياء: الأسئلة الأصلية (المستند)، وحل الطالب كما هو (الاستخراج الفاشل)، وملاحظات حمراء محددة عند كل خطأ: "هنا جمعت بدل ما تضرب — راجع السطر الثالث" (أخطاء التحقق المحددة). الطالب يصحح المواضع المحددة بالضبط — هذا retry-with-error-feedback حرفياً.

لكن لو كان السؤال يعتمد على جدول لوغاريتمات ما وُزّع على الطلاب أصلاً، فلا إعادة ولا عشر إعادات بتنفع — المعلومة مو عند الطالب (حدود الإعادة). والمعلم الخبير يمسك دفتراً يسجل فيه نوع كل خطأ متكرر عبر الفصل — "قسمة الكسور: 12 طالباً غلطوا فيها" — فيعيد شرح الدرس المحدد بدل ما يعيد المنهج كله: هذا بالضبط دور detected_pattern.

A math teacher receives homework with mistakes. The weak teacher hands it back stamped "redo" — the student repeats the same mistakes, having no idea where they are. The good teacher returns it with three things: the original questions (the document), the student's work as-is (the failed extraction), and specific red notes at each error: "you added instead of multiplying here — recheck line three" (the specific validation errors). The student corrects exactly the marked spots — that is retry-with-error-feedback, literally.

But if the problem depends on a logarithm table that was never handed out, no retry — not even ten — will help: the student does not have the information (the limits of retry). And the veteran teacher keeps a notebook logging each recurring error type across the class — "fraction division: 12 students got it wrong" — then re-teaches that specific lesson instead of the whole syllabus: exactly the role of detected_pattern.

في الاختبارOn the exam

أسئلة هذا الموضوع (سيناريو S6 غالباً) تختبر ثلاث تمييزات:

  • إعادة صحيحة = المستند + الاستخراج الفاشل + الأخطاء المحددة. أي خيار "أعد الطلب فقط" أو "بدون تحديد الأخطاء" ناقص.
  • ميّز الفشل القابل للإصلاح (تنسيق/هيكل — أعد) من غير القابل (معلومة غائبة/بمستند خارجي — لا تعد؛ صحح المدخلات).
  • لكشف التعارضات: استخرج calculated_total مع stated_total وأضف conflict_detected — مو "خل النموذج يتأكد من الجمع" كتعليمة إنشائية.
  • استبعد: رفع عدد المحاولات كحل جذري، الإعادة بدون تغذية راجعة، وتجاهل تتبع أنماط الرفض.

Questions here (usually scenario S6) test three distinctions:

  • A correct retry = document + failed extraction + specific errors. Any "just resend" or "without naming the errors" option is incomplete.
  • Separate fixable failures (format/structure — retry) from unfixable ones (absent/external information — do not retry; fix the inputs).
  • For discrepancy detection: extract calculated_total alongside stated_total and add conflict_detected — not a prose "make sure the sums are right" instruction.
  • Eliminate: raising the retry count as a root fix, feedback-free retries, and ignoring dismissal-pattern tracking.

صحيح. detected_pattern يحوّل كل رفض إلى نقطة بيانات مصنفة — فتشوف بالأرقام أي الأنماط مصدر الإيجابيات الكاذبة وتعالجها بمعايير أدق أو تعطيل مؤقت. الاستبيانات انطباعية، والسقف العددي يخفي مشاكل حقيقية، والشرح الأطول يزيد الضجيج. Correct. detected_pattern turns every dismissal into a labeled data point — you see numerically which patterns source the false positives and fix them with sharper criteria or a temporary disable. Surveys are impressionistic, caps hide real issues, and longer explanations add noise.
الصحيح B: حقل detected_pattern + تجميع الرفض حسب النمط — تصميم حلقة التغذية الراجعة كما في الدليل. يعطيك تحليلاً منهجياً بالبيانات بدل الانطباعات والحلول الشكلية. The answer is B: a detected_pattern field + aggregating dismissals by pattern — the guide's feedback-loop design. It gives systematic, data-driven analysis instead of impressions and cosmetic fixes.

خلاصةTakeaway

  • الإعادة الفعالة = المستند الأصلي + الاستخراج الفاشل + أخطاء التحقق المحددة نصاً — التحديد هو اللي يصحح.An effective retry = original document + failed extraction + the specific validation errors spelled out — specificity is what corrects.
  • الإعادة تصلح أخطاء التنسيق والهيكل، وتعجز حتماً عن المعلومة الغائبة عن المستند — عالج المدخلات: nullable، إثراء، أو مسار بشري.Retry fixes format and structural errors, and is inevitably powerless against information absent from the document — fix the inputs: nullable, enrichment, or a human path.
  • التحقق الدلالي (المجاميع، مواضع الحقول) مسؤوليتك البرمجية — السكيما ألغت الـ syntax فقط.Semantic validation (sums, field placement) is your programmatic responsibility — the schema only killed syntax.
  • detected_pattern يحوّل رفض المطورين لبيانات تحليل منهجي لأنماط الإيجابيات الكاذبة.detected_pattern turns developer dismissals into systematic analysis data for false-positive patterns.
  • صمّم للتصحيح الذاتي: calculated_total بجانب stated_total يكشف الفروقات، وconflict_detected يمنع "تجميل" التعارض في المصدر.Design for self-correction: calculated_total beside stated_total exposes discrepancies, and conflict_detected stops source contradictions from being "beautified" away.
