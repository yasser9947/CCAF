1.6

استراتيجيات تفكيك المهام المعقّدة Task decomposition strategies for complex workflows

نفس المهمة الكبيرة: تفكيك صحيح = نتائج متّسقة وعميقة؛ تفكيك خاطئ = انتباه مشتّت وأحكام متناقضة. هنا تتعلم متى تسلسل ومتى تتكيّف. Same big task: the right decomposition yields consistent depth; the wrong one yields diluted attention and contradictory verdicts. Here you learn when to chain and when to adapt.

وش بتتعلم What you'll learn

  • تفرّق بين الأنبوب الثابت المتسلسل (prompt chaining) والتفكيك الديناميكي التكيّفي المبني على المكتشفات الوسيطة.
  • تختار النمط المناسب: chaining للمراجعات المتوقّعة متعددة الجوانب، والديناميكي للاستقصاء المفتوح.
  • تقسّم المراجعات الكبيرة: مرور محلي لكل ملف + مرور تكامل منفصل عابر للملفات — لتفادي تمييع الانتباه.
  • تشخّص أعراض تمييع الانتباه (عمق متفاوت، أخطاء منفلتة، أحكام متناقضة) وتعالجها بتقسيم المرورات.
  • تفكّك مهمة مفتوحة مثل «أضف اختبارات شاملة لكود قديم»: خريطة البنية ← مناطق عالية الأثر ← خطة أولويات تتكيّف مع التبعيات المكتشفة.
  • Distinguish fixed sequential pipelines (prompt chaining) from dynamic adaptive decomposition built on intermediate findings.
  • Select the right pattern: chaining for predictable multi-aspect reviews, dynamic for open-ended investigation.
  • Split large reviews: a per-file local pass plus a separate cross-file integration pass — to avoid attention dilution.
  • Diagnose attention dilution symptoms (uneven depth, escaped bugs, contradictory verdicts) and cure them by splitting passes.
  • Decompose an open-ended task like "add comprehensive tests to a legacy codebase": map the structure, identify high-impact areas, build a prioritized plan that adapts as dependencies surface.

01 النمطان: سلسلة ثابتة أم خطة تتكيّف؟ The two patterns: fixed chain or adaptive plan?

عندك استراتيجيتان لتفكيك أي مهمة معقّدة. الأولى: prompt chaining — أنبوب ثابت من خطوات محددة مسبقًا تتنفّذ بالترتيب، ومخرج كل خطوة يدخل في اللي بعدها. تختارها لما تكون المهمة متوقّعة البنية: تعرف مسبقًا وش الجوانب اللي تحتاج فحصًا، وما يتغيّر هذا حسب النتائج.

الثانية: التفكيك الديناميكي التكيّفي — خطة أولية تتولّد، وكل خطوة تولّد مهامّ فرعية جديدة بناءً على ما اكتُشف. تختارها للمهام الاستقصائية المفتوحة حيث لا تعرف وش بتلقى قبل ما تبدأ. قاعدة الاختيار بسطر: هل تقدر تكتب كل الخطوات قبل البدء وتظل صحيحة؟ نعم ← chaining. لا ← ديناميكي.

You have two strategies for decomposing any complex task. First: prompt chaining — a fixed pipeline of pre-defined steps executed in order, each step's output feeding the next. Choose it when the task's structure is predictable: you know upfront which aspects need examination, and that doesn't change with the results.

Second: dynamic adaptive decomposition — an initial plan is generated, and each step spawns new subtasks based on what was discovered. Choose it for open-ended investigative work where you can't know what you'll find before starting. The selection rule in one line: can you write every step before starting and have them stay correct? Yes — chaining. No — dynamic.

PROMPT CHAINING — fixed
step 1: analyze file A
step 2: analyze file B
step 3: integration pass
plan fully known upfront -- never changes
DYNAMIC — adaptive
map structure
discover: hidden dependency!

اليسار: خطوات معروفة سلفًا تنفَّذ بالترتيب. اليمين: كل اكتشاف يعيد تشكيل الخطة. One side: steps known upfront, executed in order. The other: every discovery reshapes the plan.

Key concept: the selection criterion is predictability, not size. Reviewing 50 files is huge but predictable — chaining. Adding tests to one obscure legacy module is small but unknown — dynamic.

02 مراجعة الكود الكبيرة: مرور لكل ملف + مرور تكامل Large code reviews: per-file passes plus an integration pass

المثال الكلاسيكي للـ chaining هو مراجعة PR يعدّل 14 ملفًا. لو حشرت الملفات كلها في مرور واحد، ظهرت أعراض تمييع الانتباه (attention dilution) الثلاثة: ملاحظات عميقة لبعض الملفات وسطحية لغيرها، أخطاء واضحة تنفلت، وأحكام متناقضة — نفس النمط يُرفض في ملف ويُقبل في آخر داخل نفس المراجعة.

العلاج المنصوص: قسّم المراجعة إلى مرورات مركّزة — (1) مرور محلي لكل ملف على حدة يصطاد مشاكل الملف الداخلية (أخطاء منطقية، معالجة استثناءات)، ثم (2) مرور تكامل منفصل يفحص القضايا العابرة للملفات فقط: تدفّق البيانات بين الوحدات، تطابق العقود (contracts)، والمنطق المكرر. كل مرور ياخذ انتباهًا كاملًا لنطاق ضيّق — فيثبت العمق وتختفي التناقضات. نفس المبدأ يرجع في الدومين 4 باسم multi-pass review.

The classic chaining example is reviewing a PR touching 14 files. Cram them all into a single pass and the three symptoms of attention dilution appear: deep feedback on some files but superficial notes on others, obvious bugs slipping through, and contradictory verdicts — the same pattern flagged in one file and approved in another within the same review.

The prescribed cure: split the review into focused passes — (1) a local pass per file catching file-internal issues (logic bugs, error handling), then (2) a separate integration pass examining only cross-file concerns: data flow between modules, contract mismatches, duplicated logic. Each pass gives full attention to a narrow scope — depth becomes consistent and the contradictions vanish. The same principle returns in Domain 4 as multi-pass review.

PR: 14 changed files
file 1
local pass
file 2
local pass
...
file 14
local pass
each pass: full attention on ONE file (bugs, error handling)
separate INTEGRATION pass: cross-file data flow, contracts, duplication
consistent findings -- no contradictions, no missed bugs

مرورات محلية مركّزة ثم مرور تكامل واحد — بدل مرور واحد مشتّت على 14 ملفًا. Focused local passes then one integration pass — instead of a single diluted pass over 14 files.

نصيحة: احفظ التشخيص من أعراضه: «عمق متفاوت + تناقضات على نفس النمط» = تمييع انتباه، والعلاج تقسيم المرورات — مو موديل أضخم ولا نافذة سياق أكبر. النافذة الأكبر تستوعب الملفات؛ ما تصلح جودة الانتباه عليها.
Tip: memorize the diagnosis by its symptoms: "uneven depth + contradictions on the same pattern" = attention dilution, and the cure is splitting the passes — not a bigger model or a larger context window. A larger window fits the files; it doesn't fix the quality of attention over them.

03 المهام المفتوحة: خريطة ← أثر عالٍ ← خطة تتكيّف Open-ended tasks: map, high-impact, adaptive plan

خذ المهمة النموذجية: «أضف اختبارات شاملة لقاعدة كود قديمة». كتابة خطة كاملة مسبقًا هنا مستحيلة أصلًا — ما تعرف البنية ولا التبعيات ولا المفاجآت المدفونة. التفكيك الديناميكي الصحيح ثلاث مراحل: (1) خرّط البنية: وش الوحدات، كيف تترابط، وين نقاط الدخول؛ (2) حدّد المناطق عالية الأثر: الوحدات الحرجة كثيرة الاستخدام قليلة التغطية — الاختبار فيها يشتري أعلى قيمة؛ (3) ابنِ خطة مرتّبة بالأولوية تتكيّف: كل ما اكتشفت تبعية جديدة أثناء الشغل، تتحدّث الخطة — مهام تُضاف، وأولويات تتقدم أو تتأخر.

Take the canonical task: "add comprehensive tests to a legacy codebase." Writing a full plan upfront here is impossible by definition — you don't know the structure, the dependencies, or the buried surprises. Correct dynamic decomposition runs in three stages: (1) map the structure: what the modules are, how they interconnect, where the entry points sit; (2) identify high-impact areas: critical, heavily-used, under-covered modules — testing there buys the most value; (3) build a prioritized plan that adapts: every dependency discovered mid-work updates the plan — tasks get added, priorities move up or down.

النمطان جنبًا إلى جنب: chaining ثابت مقابل تفكيك تكيّفي Both patterns side by side: fixed chaining vs adaptive decomposition 
# Pattern 1 -- PROMPT CHAINING (fixed sequence, predictable reviews)
# Per-file local passes avoid attention dilution across 14 files...
local_findings = {}
for path in changed_files:
    local_findings[path] = review_agent(
        f"Review ONLY {path} for local issues (bugs, error handling):\n{read(path)}"
    )

# ...then ONE separate integration pass for cross-file concerns.
integration_findings = review_agent(
    "Given these per-file findings, analyze CROSS-FILE issues only "
    "(data flow, contract mismatches, duplicated logic):\n"
    + render(local_findings)
)

# Pattern 2 -- DYNAMIC ADAPTIVE DECOMPOSITION (open-ended work)
# "Add comprehensive tests to a legacy codebase"
plan = agent("Map the repository structure and rank modules by impact and risk.")
while plan.has_pending_tasks():
    task   = plan.next_highest_priority()
    result = agent(f"Write tests for: {task.module} (context: {task.context})")
    plan.adapt(result.discovered_dependencies)   # subtasks emerge from findings
لمحة سريعة: لاحظ أن النمطين يتعاونان: داخل الخطة التكيّفية، كل مهمة فرعية («اختبر الوحدة X») ممكن تنفَّذ بسلسلة ثابتة صغيرة. الاختيار يتم لكل مستوى من المهمة، مو مرة واحدة للنظام كله.
Quick insight: the two patterns compose: inside an adaptive plan, each subtask ("test module X") may itself run as a small fixed chain. The choice is made per level of the task, not once for the whole system.

فخ الاختبارExam trap

  • «انتقل لموديل أعلى بنافذة سياق أكبر» لمراجعة متفاوتة الجودة — النافذة الأكبر لا تعالج جودة الانتباه؛ فخ متكرر في أسئلة المراجعات."Switch to a higher-tier model with a larger context window" for an inconsistent review — a bigger window doesn't fix attention quality; a recurring trap in review questions.
  • «شغّل 3 مراجعات مستقلة واعتمد ما يتكرر في اثنتين» — تصويت الإجماع يكتم الأخطاء الحقيقية التي تُكتشف أحيانًا فقط."Run 3 independent reviews and keep findings appearing in at least 2" — consensus voting suppresses real bugs that are only caught intermittently.
  • «ألزم المطوّرين بتقسيم الـ PRs الكبيرة» — ينقل العبء للبشر بدل إصلاح النظام."Require developers to split large PRs" — shifts the burden onto humans instead of fixing the system.
  • كتابة خطة تفصيلية كاملة مسبقًا لمهمة استقصائية مفتوحة — عكس التفكيك التكيّفي الذي يطلبه الدليل.Writing a complete detailed plan upfront for an open-ended investigation — the opposite of the adaptive decomposition the guide calls for.

مثال من الحياة: ورشة السيارات Real-life example: the auto repair shop

الورشة الجيدة تعرف الفرق بين نوعين من الشغل. الفحص الدوري هو الـ prompt chaining: قائمة ثابتة معروفة — زيت، فرامل، إطارات، بطارية — بنفس الترتيب لكل سيارة، لأن الجوانب المطلوب فحصها معروفة مسبقًا ولا تتغيّر. ولاحظ أن الفنّي المحترف ما يفحص السيارة «كلها مرة وحدة» — يفحص كل نظام على حدة بتركيز كامل، ثم يختم بنظرة تكامل: هل اهتزاز المقود مرتبط بوضع الإطارات؟ هذا بالضبط «مرور لكل ملف + مرور تكامل».

أما «فيه صوت غريب يطلع أحيانًا» فهذا تفكيك ديناميكي: مستحيل يكتب الفنّي خطة الفحص كاملة قبل ما يبدأ. يفحص الأحزمة — سليمة، لكن يلاحظ بقعة زيت؛ يتتبعها للجوان — فيكتشف تآكلًا في عازل قريب... كل اكتشاف يولّد خطوة الفحص التالية. ولو أصرّ على قائمة مكتوبة سلفًا، بيفحص عشرين بندًا ما لها علاقة ويفوّت العطل الحقيقي. الورشة الشاطرة تعرف: الصيانة الدورية تمشي على checklist، والأعطال الغامضة تمشي على التتبّع التكيّفي.

A good repair shop knows the difference between two kinds of work. The periodic service is prompt chaining: a fixed, known checklist — oil, brakes, tires, battery — in the same order for every car, because the aspects to inspect are known upfront and never change. Notice too that a professional mechanic never inspects the car "all at once" — he checks each system separately with full focus, then finishes with an integration look: is the steering vibration related to the tire condition? That is exactly "per-file pass + integration pass."

But "there's a strange noise that comes and goes" — that's dynamic decomposition: the mechanic cannot possibly write the full diagnostic plan before starting. He checks the belts — fine, but spots an oil stain; traces it to a gasket — and discovers worn insulation nearby... each discovery generates the next inspection step. Had he insisted on a pre-written list, he'd check twenty irrelevant items and miss the real fault. The smart shop knows: routine service runs on a checklist; mystery faults run on adaptive tracing.

في الاختبارOn the exam

أسئلة 1.6 نوعان: «مراجعة متعددة الملفات طلعت نتائجها متناقضة وسطحية — كيف تعيد الهيكلة؟» و«مهمة مفتوحة — أي استراتيجية تفكيك؟».

  • أعراض التفاوت والتناقض في مراجعة كبيرة ← الجواب دائمًا: مرورات لكل ملف + مرور تكامل منفصل.
  • مهمة تحتوي «قديم / غير موثّق / استكشاف» ← الجواب: خريطة ← مناطق عالية الأثر ← خطة أولويات تتكيّف.
  • المشتّتات الأربعة الجاهزة: موديل أكبر، تصويت إجماع بين مراجعات، تحميل المطوّرين تقسيم الـ PRs، وخطة كاملة مسبقة لمهمة مجهولة.

Task 1.6 questions come in two shapes: "a multi-file review produced contradictory, shallow findings — how do you restructure?" and "an open-ended task — which decomposition strategy?"

  • Uneven-depth and contradiction symptoms in a big review — the answer is always: per-file passes + a separate integration pass.
  • A task featuring "legacy / undocumented / exploration" — the answer: map, high-impact areas, an adaptive prioritized plan.
  • The four stock distractors: a bigger model, consensus voting across reviews, making developers split PRs, and a complete upfront plan for an unknown task.

بدأت مهمة «إضافة اختبارات لنظام قديم» بالتفكيك الديناميكي. وش أول خطوة صحيحة؟ You're starting "add tests to a legacy system" with dynamic decomposition. What is the correct first step?

صحيح. الترتيب المنصوص: خريطة البنية ← مناطق عالية الأثر ← خطة أولويات تتكيّف كلما ظهرت تبعيات. تفهم قبل ما تكتب، وتستثمر جهد الاختبار حيث القيمة الأعلى. Correct. The prescribed order: map the structure, find high-impact areas, then a prioritized plan that adapts as dependencies emerge. Understand before writing, and invest testing effort where it buys the most.
خطأ. الصحيح: الخريطة أولًا ثم الأثر ثم الخطة التكيّفية. الترتيب الأبجدي تفكيك أعمى، وكتابة كل شيء دفعة واحدة تتجاهل الأولويات والتبعيات، ونسبة التغطية الصارمة هدف شكلي يسبق الفهم. Not quite. The correct start: map, then impact, then the adaptive plan. Alphabetical order is blind decomposition, writing everything at once ignores priorities and dependencies, and a rigid coverage target is a vanity goal set before understanding.

خلاصةTakeaway

  • مهمة متوقّعة متعددة الجوانب ← prompt chaining؛ استقصاء مفتوح ← تفكيك ديناميكي.
  • المعيار قابلية التنبؤ، مو الحجم: تقدر تكتب الخطوات مسبقًا وتظل صحيحة؟ سلسلة. لا؟ تكيّف.
  • مراجعة كبيرة: مرور محلي لكل ملف + مرور تكامل منفصل — يمنع تمييع الانتباه.
  • «عمق متفاوت + أحكام متناقضة» = تمييع انتباه؛ العلاج تقسيم المرورات لا موديل أكبر.
  • مهمة مفتوحة: خريطة ← مناطق عالية الأثر ← خطة أولويات تتكيّف مع التبعيات المكتشفة.
  • Predictable multi-aspect work — prompt chaining; open-ended investigation — dynamic decomposition.
  • The criterion is predictability, not size: can the steps be written upfront and stay correct? Chain. No? Adapt.
  • Large reviews: a local pass per file + a separate integration pass — prevents attention dilution.
  • "Uneven depth + contradictory verdicts" = attention dilution; the cure is splitting passes, not a bigger model.
  • Open-ended tasks: map, high-impact areas, a prioritized plan adapting to discovered dependencies.
