1.7

إدارة حالة الجلسة: الاستئناف والتفريع Managing session state: resumption & forking

شغلك مع الوكيل ما ينتهي بإغلاق الطرفية. استئناف، تفريع، أو بداية جديدة بملخّص — قرار له قواعد واضحة، والاختبار يقيسها كلها. Your work with the agent doesn't end when the terminal closes. Resume, fork, or start fresh with a summary — a decision with clear rules, and the exam measures all of them.

وش بتتعلم What you'll learn

  • تستأنف محادثة سابقة محددة بالاسم عبر --resume <session-name> لمواصلة جلسات استقصاء ممتدة.
  • تنشئ فروعًا مستقلة من أساس تحليلي مشترك بـ fork_session لمقارنة نهجين متباعدين.
  • تخبر الجلسة المستأنفة بالملفات المتغيّرة تحديدًا لإعادة تحليل مستهدفة بدل استكشاف كامل.
  • تعرف متى تكون الجلسة الجديدة بملخّص منظّم أوثق من الاستئناف بنتائج أدوات بائتة.
  • تحسم قرار «استأنف / افرع / ابدأ من جديد» حسب صلاحية السياق السابق.
  • Resume a specific named prior conversation with --resume <session-name> to continue extended investigation sessions.
  • Create independent branches from a shared analysis baseline with fork_session to compare divergent approaches.
  • Inform a resumed session exactly which files changed for targeted re-analysis instead of full re-exploration.
  • Know when a fresh session with a structured summary is more reliable than resuming with stale tool results.
  • Settle the resume / fork / start-fresh decision by how valid the prior context still is.

01 الاستئناف بالاسم: جلسة استقصاء تمتد أيامًا Named resumption: an investigation spanning days

الجلسات أعمارها أطول من نافذة الطرفية. --resume <session-name> يرجّعك لمحادثة سابقة محددة بالاسم بكامل سياقها: كل تحليل تراكم، كل ملف قُرئ، كل استنتاج توصّل له الوكيل — كأنك ما سكّرت أبدًا. هذا مثالي لجلسات الاستقصاء المسمّاة الممتدة عبر أيام عمل: تسمّي الجلسة auth-audit يوم الأحد، وترجع لها الاثنين والثلاثاء بنفس الاسم.

لكن انتبه للنقطة اللي يحبها الاختبار: لو رجعت للجلسة بعد ما تعدّلت ملفات سبق تحليلها، الوكيل ما يدري عن التعديل — بيجاوب من ذاكرة تحليل قديم. الواجب عليك: أخبره بالتغييرات تحديدًا («ملف token.py تحوّل لـ async — أعد تحليله هو ومستدعيه فقط») ليقوم بإعادة تحليل مستهدفة للمتأثر بدل إعادة استكشاف كاملة تحرق الوقت والتوكنز.

Sessions outlive the terminal window. --resume <session-name> returns you to a specific prior conversation by name with its full context: every accumulated analysis, every file read, every conclusion the agent reached — as if you never closed it. That is ideal for named investigation sessions spanning workdays: name the session auth-audit on Sunday and return to it Monday and Tuesday by the same name.

But mind the point the exam loves: if you resume after previously analyzed files were modified, the agent doesn't know about the edits — it will answer from a memory of stale analysis. Your job: tell it exactly what changed ("token.py was refactored to async — re-analyze only it and its callers") so it performs a targeted re-analysis of what's affected instead of a full re-exploration that burns time and tokens.

DAY 1
claude  (session: auth-audit)
deep analysis: auth flow, token handling, 3 findings
DAY 2
claude --resume auth-audit
full context restored -- continues where it left off
DAY 3
claude --resume auth-audit  +  "token.py changed"
code changed since day 2 -- inform the agent: targeted re-analysis of token.py + callers only

جلسة مسمّاة تمتد ثلاثة أيام: استئناف كامل السياق، ومع تغيّر الكود تُخبر الوكيل بالتغيير لإعادة تحليل مستهدفة. A named session spanning three days: full-context resumption, and when code changes you inform the agent for targeted re-analysis.

الاستئناف والتفريع والبداية الجديدة من الطرفية Resuming, forking, and starting fresh from the CLI 
# Continue a specific named investigation session where it left off
claude --resume auth-audit

# Resuming AFTER code changed? Inform the agent precisely what changed,
# so it re-analyzes only the affected files instead of re-exploring everything.
claude --resume auth-audit -p "Since our last session, src/auth/token.py was \
refactored to async. Re-analyze only that file and its callers."

# Fork twice from the SAME baseline to compare divergent approaches in parallel
claude --resume auth-audit --fork-session -p "Approach A: design the test suite around pytest fixtures"
claude --resume auth-audit --fork-session -p "Approach B: design the test suite around factory-based mocks"

# Stale tool results? Do NOT resume -- start FRESH with a structured summary:
claude -p "Context summary: repo uses JWT auth (src/auth/), 3 known bugs listed \
in notes.md, coverage is 41%. Task: propose a prioritized test plan."
لمحة سريعة: «إعادة تحليل مستهدفة» تعني تحديد الملف ومستدعيه — مو «راجع المشروع» العامة ولا الصمت الكامل. الدقة في وصف التغيير هي اللي توفّر إعادة الاستكشاف.
Quick insight: "targeted re-analysis" means naming the file and its callers — not a vague "review the project" and not total silence. Precision in describing the change is what saves you the full re-exploration.

02 fork_session: فرعان مستقلان من أساس واحد fork_session: two independent branches from one baseline

أحيانًا ما تحتاج «تكمل» الجلسة — تحتاج تتفرّع منها. fork_session ينشئ جلسة جديدة مستقلة تبدأ من نقطة الأساس المستأنفة، ويترك الأصل كما هو. الاستخدام النموذجي: بعد جلسة حلّلت قاعدة الكود بعمق، تبي تقارن نهجين متباعدين — استراتيجيتي اختبار (fixtures مقابل factory mocks) أو نهجي إعادة هيكلة. تفرع مرتين من نفس الأساس: كل فرع يستكشف نهجه بحرية كاملة، بلا تلوّث متبادل، والأساس المشترك حُلّل مرة واحدة فقط.

قارن بالبديلين الخاسرين: تجربة النهجين بالتتابع في جلسة واحدة — النهج الأول يبقى في السياق ويلوّن حكم الوكيل على الثاني (والوكيل ما «ينسى» عند الطلب)؛ أو جلستان جديدتان من الصفر — تدفع كلفة تحليل قاعدة الكود مرتين كاملتين بلا أي مقابل.

Sometimes you don't need to "continue" a session — you need to branch from it. fork_session creates a new independent session starting from the resumed baseline, leaving the original untouched. The canonical use: after a session that deeply analyzed your codebase, you want to compare two divergent approaches — two testing strategies (fixtures vs factory mocks) or two refactoring paths. Fork twice from the same baseline: each branch explores its approach with full freedom, no cross-contamination, and the shared baseline was analyzed exactly once.

Compare the two losing alternatives: trying both approaches sequentially in one session — the first approach stays in context and colors the agent's judgment of the second (and the agent doesn't "forget" on request); or two brand-new sessions from scratch — paying the full codebase-analysis cost twice for nothing.

session: auth-audit
shared analysis baseline (analyzed ONCE)
fork_session x2
fork A: pytest fixtures strategy
independent context -- explores freely
fork B: factory mocks strategy
independent context -- explores freely
neither branch pollutes the other -- original session stays untouched

شجرة التفريع: أساس يُحلَّل مرة واحدة، وفرعان معزولان يستكشف كل منهما نهجًا — والأصل يبقى سليمًا. The fork tree: one baseline analyzed once, two isolated branches each exploring an approach — and the original stays intact.

نفس المفهوم داخل الـ Agent SDK The same concept inside the Agent SDK 
from claude_agent_sdk import query, ClaudeAgentOptions

# resume alone -> CONTINUE the same session (its history keeps growing)
options = ClaudeAgentOptions(resume="auth-audit")

# resume + fork_session -> BRANCH: a new independent session that starts
# from the resumed baseline, leaving the original untouched
branch_a = ClaudeAgentOptions(resume="auth-audit", fork_session=True)
branch_b = ClaudeAgentOptions(resume="auth-audit", fork_session=True)
# branch_a and branch_b now diverge freely -- neither sees the other.

03 القرار: استأنف، افرع، أم ابدأ من جديد؟ The decision: resume, fork, or start fresh?

يبقى السؤال الأهم: متى يكون الاستئناف نفسه فكرة سيئة؟ الجواب: لما تكون نتائج الأدوات القديمة بائتة (stale) على نطاق واسع — الكود تغيّر كثيرًا منذ التحليل. الجلسة المستأنفة تحمل النتائج القديمة كأنها حقائق حاضرة، والوكيل بيبني استنتاجات جديدة فوق واقع ما عاد موجودًا. الدليل صريح هنا: البدء بجلسة جديدة مع ملخّص منظّم — بالحقائق اللي ما زالت صحيحة فقط — أوثق من الاستئناف بنتائج بائتة.

القرار الكامل بأربع حالات: سياق سابق معظمه صالح ← استأنف. ملفات محددة تغيّرت ← استأنف + أخبره بالتغييرات. مقارنة نهجين من أساس مشترك ← افرع. نتائج بائتة على نطاق واسع ← جلسة جديدة + ملخّص منظّم.

The biggest question remains: when is resuming itself a bad idea? Answer: when the old tool results are broadly stale — the code has moved substantially since the analysis. A resumed session carries the old results as if they were present-day facts, and the agent will stack new conclusions on top of a reality that no longer exists. The guide is explicit here: starting a new session with a structured summary — containing only the facts that still hold — is more reliable than resuming with stale results.

The full decision in four cases: prior context mostly valid — resume. Specific files changed — resume + state the changes. Comparing approaches from a shared baseline — fork. Broadly stale results — fresh session + structured summary.

مفهوم أساسي: السؤال الحاسم قبل أي استئناف: «هل نتائج الأدوات المخزّنة في الجلسة ما زالت تطابق الواقع؟» نعم ← استأنف (أو افرع). لا ← جلسة جديدة بملخّص الحقائق الصالحة. عمر الجلسة نفسه مو المعيار — صلاحية محتواها هي المعيار.
Key concept: the decisive question before any resume: "do the tool results stored in the session still match reality?" Yes — resume (or fork). No — a fresh session with a summary of the still-valid facts. The session's age is not the criterion — the validity of its contents is.
تنبيه: «الاستئناف دائمًا أوفر» فكرة مغرية وخاطئة. لو الكود تغيّر كثيرًا، وفّرت دقائق الإعداد وخسرت موثوقية كل استنتاج لاحق — الوكيل يحاكم واقعًا انتهى.
Warning: "resuming is always cheaper" is tempting and wrong. If the code has moved a lot, you saved setup minutes and forfeited the reliability of every subsequent conclusion — the agent is reasoning about a reality that's gone.

فخ الاختبارExam trap

  • تجربة نهجين بالتتابع في نفس الجلسة — الأول يلوّث سياق الثاني؛ الصح fork_session.Trying two approaches sequentially in the same session — the first contaminates the second; the right tool is fork_session.
  • جلستان جديدتان تعيدان التحليل كاملًا من الصفر لمقارنة نهجين — تدفع كلفة التحليل مرتين بلا داعٍ.Two brand-new sessions redoing the full analysis to compare approaches — paying the analysis cost twice for nothing.
  • استئناف جلسة بعد تعديل ملفات بدون إخبار الوكيل — بيجاوب من ذاكرة تحليل قديم.Resuming after file edits without informing the agent — it will answer from a memory of stale analysis.
  • استئناف جلسة نتائجها بائتة على نطاق واسع «للاستفادة من السياق» — الدليل صريح: الجلسة الجديدة بملخّص منظّم أوثق.Resuming a broadly-stale session "to leverage the context" — the guide is explicit: a fresh session with a structured summary is more reliable.

مثال من الحياة: ملف المريض عند الطبيب Real-life example: the patient file at the doctor's

علاقتك بطبيبك هي إدارة جلسات بامتياز. المراجعة عند نفس الطبيب هي --resume: ملفك عنده كامل — التاريخ، التحاليل، الملاحظات — فيكمل من حيث وقف بدل ما يبدأ من الصفر. ولما تدخل عليه تقول: «من آخر زيارة سويت عملية بسيطة وغيّرت الدواء الفلاني» — هذا بالضبط إخبار الجلسة المستأنفة بالتغييرات: معلومة دقيقة تخلّيه يعيد تقييم الجزء المتأثر فقط، بدل إعادة الفحص الشامل.

وتبي رأيين علاجيين مختلفين لنفس الحالة؟ ما تعيد التحاليل مرتين — تنسخ الملف وترسله لاستشاريين، كل واحد يبني خطته باستقلال من نفس الأساس: هذا fork_session. أما لو رجعت بعد عشر سنين وصحتك تغيّرت جذريًا، الطبيب الحكيم ما يبني قرارات اليوم على تحاليل 2016 البائتة — يطلب فحوصات جديدة مع خطاب ملخّص بالثوابت المهمة (الحساسيات، العمليات السابقة): جلسة جديدة بملخّص منظّم، لأن القرارات على بيانات ميتة أخطر من كلفة الفحص الجديد.

Your relationship with your doctor is session management par excellence. Following up with the same doctor is --resume: your file is complete on their desk — history, labs, notes — so they continue where they left off instead of starting over. And when you walk in saying, "since my last visit I had a minor surgery and switched that medication" — that is exactly informing the resumed session about changes: precise information that lets them re-evaluate only the affected part rather than repeating the full workup.

Want two different treatment opinions on the same case? You don't redo the labs twice — you copy the file to two consultants, each building their plan independently from the same baseline: that is fork_session. But if you return after ten years with your health fundamentally changed, a wise doctor won't base today's decisions on stale 2016 labs — they order fresh tests plus a summary letter of the durable constants (allergies, past surgeries): a fresh session with a structured summary, because decisions on dead data cost more than the new workup.

في الاختبارOn the exam

أسئلة 1.7 كلها سيناريوهات قرار: يوصفون لك وضع جلسة (تحليل قديم، كود تغيّر، رغبة بمقارنة نهجين) ويطلبون التصرف الأمثل.

  • «مقارنة نهجين من تحليل مشترك» ← fork_session مرتين. «مواصلة استقصاء مسمّى» ← --resume. «كل شيء تغيّر» ← جلسة جديدة بملخّص.
  • لما يذكر السؤال «ملفات معيّنة تعدّلت»، الإجابة الصحيحة تتضمّن إخبار الوكيل بالتغيير تحديدًا لإعادة تحليل مستهدفة.
  • استبعد: التجربة المتتابعة في جلسة واحدة (تلوّث)، الجلستين الجديدتين لمقارنة (كلفة مزدوجة)، والاستئناف الأعمى بنتائج بائتة (استنتاجات عن واقع منتهٍ).

Task 1.7 questions are all decision scenarios: they describe a session situation (old analysis, changed code, a wish to compare approaches) and ask for the optimal move.

  • "Compare two approaches from shared analysis" — fork_session twice. "Continue a named investigation" — --resume. "Everything changed" — a fresh session with a summary.
  • When the stem mentions "specific files were modified," the right answer includes telling the agent exactly what changed for targeted re-analysis.
  • Eliminate: sequential trials in one session (contamination), two fresh sessions for a comparison (double cost), and blind resumption over stale results (conclusions about a dead reality).

رجعت لجلسة auth-audit بعد يومين، وفي أثنائهما أعيدت هيكلة token.py فقط. وش التصرف الصحيح؟ You return to the auth-audit session after two days, during which only token.py was refactored. What is the correct move?

صحيح. تغيير محدود = استئناف + إخبار دقيق بالتغيير لإعادة تحليل مستهدفة. تستفيد من التحليل المتراكم وتصحّح الجزء البائت فقط. Correct. A contained change = resume + precise notification for targeted re-analysis. You keep the accumulated analysis and refresh only the stale part.
خطأ. الصحيح: استئناف + إخبار بالتغيير تحديدًا. الصمت يترك الوكيل يجاوب من تحليل قديم، والجلسة الجديدة الكاملة إهدار لتحليل ما زال معظمه صالحًا، والـ fork لمقارنة نهجين مو لتحديث ملف. Not quite. The correct move: resume + state the specific change. Silence leaves the agent answering from stale analysis, a full new session wastes mostly-valid work, and forking is for comparing approaches, not refreshing a file.

جلسة تحليل عمرها ثلاثة أشهر، وتغيّر منذها معظم الكود المُحلَّل: هجرة إطار عمل، حذف وحدات، وإعادة تسمية واسعة. تحتاج تكمل الشغل على نفس الموضوع. وش الأوثق؟ An analysis session is three months old, and most of the analyzed code has since changed: a framework migration, deleted modules, sweeping renames. You need to continue work on the same topic. What is most reliable?

صحيح. نتائج بائتة على نطاق واسع = البداية الجديدة بملخّص منظّم أوثق من الاستئناف — نصّ الدليل حرفيًا. الملخّص يحمل الثوابت الصالحة فقط، والوكيل يستكشف الواقع الحالي. Correct. Broadly stale results = starting fresh with a structured summary is more reliable than resuming — the guide verbatim. The summary carries only the still-valid constants, and the agent explores current reality.
خطأ. الصحيح: جلسة جديدة + ملخّص منظّم. الاستئناف (والـ fork فرع منه) يورّث نتائج أدوات عن كود ما عاد موجودًا، و«تجاهل القديم» تعليمة احتمالية على سياق ملوّث أصلًا. Not quite. The correct call: fresh session + structured summary. Resuming (and forking, which inherits from it) carries tool results about code that no longer exists, and "ignore the outdated parts" is a probabilistic instruction over already-contaminated context.
3

وش الذي يميّز fork_session عن --resume العادي؟ What distinguishes fork_session from a plain --resume?

صحيح. resume = مواصلة نفس الجلسة؛ fork = فرع مستقل يبدأ من الأساس ويترك الأصل سليمًا — ولهذا يصلح لمقارنة نهجين متوازيين من تحليل واحد. Correct. Resume = continuing the same session; fork = an independent branch starting from the baseline, leaving the original untouched — which is why it suits comparing parallel approaches from one analysis.
خطأ. الصحيح: fork = جلسة مستقلة جديدة من الأساس المستأنَف، وresume = مواصلة نفس الجلسة. الـ fork ليس فارغًا (يحمل الأساس) وليس للقراءة فقط، والآليتان مختلفتان جوهريًا. Not quite. The correct answer: fork = a new independent session from the resumed baseline; resume = continuing the same session. A fork is neither empty (it carries the baseline) nor read-only, and the two mechanisms are fundamentally different.

خلاصةTakeaway

  • --resume <session-name> يستأنف محادثة مسمّاة محددة بكامل سياقها.
  • fork_session = فروع مستقلة من أساس مشترك لمقارنة نهجين — الأساس يُحلَّل مرة واحدة.
  • رجعت بعد تعديل ملفات؟ أخبر الوكيل بالتغيير تحديدًا لإعادة تحليل مستهدفة.
  • نتائج بائتة على نطاق واسع؟ جلسة جديدة + ملخّص منظّم أوثق من الاستئناف.
  • المعيار صلاحية المحتوى لا عمر الجلسة: هل نتائج الأدوات ما زالت تطابق الواقع؟
  • --resume <session-name> continues a specific named conversation with full context.
  • fork_session = independent branches from a shared baseline to compare approaches — the baseline analyzed once.
  • Back after file edits? Tell the agent exactly what changed for targeted re-analysis.
  • Broadly stale results? A fresh session + structured summary beats resuming.
  • The criterion is content validity, not session age: do the tool results still match reality?
