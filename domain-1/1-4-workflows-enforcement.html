سير العمل متعدد الخطوات: الفرض والتسليم Multi-step workflows: enforcement & handoff

لما تكون الغلطة بفلوس أو هوية عميل، «البرومبت قال له» ما هي حجة. هنا تتعلم متى تفرض الترتيب بالكود، وكيف تسلّم الحالة للبشر تسليمًا محترمًا. When the mistake costs money or a customer's identity, "the prompt told it to" is no defense. Here you learn when to enforce ordering in code, and how to hand a case to humans properly.

وش بتتعلم What you'll learn

  • تفرّق بين الفرض البرمجي (hooks وبوابات مسبقة) والتوجيه بالبرومبت لترتيب خطوات سير العمل.
  • تعرف أن تعليمات البرومبت وحدها لها نسبة فشل غير صفرية حين يكون الامتثال الحتمي مطلوبًا (مثل التحقق من الهوية قبل العمليات المالية).
  • تبني بوابة مسبقة تحجب process_refund حتى يُرجع get_customer هوية عميل متحقَّقة.
  • تفكّك الطلب متعدد الهموم لعناصر منفصلة، تحقّق فيها بالتوازي بسياق مشترك، ثم توحّد الحل.
  • تجهّز ملخّص تسليم منظّمًا للتصعيد أثناء العملية: هوية العميل، السبب الجذري، المبلغ، والإجراء الموصى به.
  • Distinguish programmatic enforcement (hooks and prerequisite gates) from prompt-based guidance for workflow ordering.
  • Know that prompt instructions alone carry a non-zero failure rate when deterministic compliance is required (e.g. identity verification before financial operations).
  • Build a prerequisite gate that blocks process_refund until get_customer returns a verified customer ID.
  • Decompose multi-concern requests into distinct items, investigate each in parallel with shared context, then synthesize a unified resolution.
  • Compile a structured handoff summary for mid-process escalation: customer ID, root cause, amount, and recommended action.

01 فرض برمجي أم توجيه بالبرومبت؟ Programmatic enforcement or prompt guidance?

الفكرة المحورية في هذا الموضوع كله: تعليمة البرومبت — مهما كانت واضحة ومكرّرة — هي «رجاء» موجّه للموديل، والموديل كيان احتمالي. يعني حتى لو التزم 99% من المرات، تظل هناك نسبة فشل غير صفرية. في نبرة الرد أو أسلوب الشرح، الـ 1% ما تضرّ. لكن في التحقق من هوية العميل قبل عملية مالية؟ الـ 1% تعني استردادات لحسابات خاطئة ومشكلة امتثال حقيقية.

القاعدة اللي يبنى عليها نصف هذا الدومين: إذا كان الامتثال الحتمي مطلوبًا، انقل القاعدة من البرومبت إلى الكود — بوابة مسبقة (prerequisite gate) أو hook. البرومبت يبقى للتوجيه السلوكي اللي يُحتمل فيه الخطأ النادر. الاختبار يعيد صياغة هذي الفكرة بعشر طرق، وكل مرة الجواب نفسه.

The pivotal idea behind this whole topic: a prompt instruction — however clear and however often repeated — is a "please" addressed to the model, and the model is a probabilistic system. Even at 99% compliance, there remains a non-zero failure rate. For tone of voice or explanation style, that 1% is harmless. For verifying a customer's identity before a financial operation? That 1% means refunds to the wrong accounts and a genuine compliance problem.

The rule half this domain is built on: when deterministic compliance is required, move the rule from the prompt into code — a prerequisite gate or a hook. Prompts remain for behavioral guidance where a rare miss is tolerable. The exam rephrases this idea ten different ways, and the answer is the same every time.

Key concept: if the question involves money or identity, and the options pit "improve the prompt" against "enforce it with a gate/hook" — programmatic enforcement is always the answer. The prompt is probabilistic; the gate is deterministic.

02 البوابة المسبقة: احجب الأداة حتى يكتمل شرطها The prerequisite gate: block the tool until its precondition holds

الحالة النموذجية من سيناريو 1: بيانات الإنتاج تكشف أن الوكيل أحيانًا يتخطّى get_customer ويستدعي lookup_order بالاسم المنطوق فقط — والنتيجة حسابات مُشخّصة غلط واستردادات خاطئة. الحل المعماري: بوابة مسبقة في الكود تحجب النداءات اللاحقة (lookup_order وprocess_refund) إلى أن يكون get_customer قد أرجع فعلًا معرّف عميل متحقَّقًا منه.

لاحظ أن البوابة تفحص حالة فعلية («هل رجعت هوية متحقَّقة؟») مو نية الموديل. الموديل ممكن «يعتقد» أنه تحقق؛ البوابة لا تهتم بالاعتقاد — تفتح فقط عند تحقق الشرط في البيانات. وهذا الفرق بينها وبين أي تحسين برومبتي.

The canonical case from Scenario 1: production data shows the agent sometimes skips get_customer and calls lookup_order using only the customer's stated name — yielding misidentified accounts and incorrect refunds. The architectural fix: a prerequisite gate in code that blocks the downstream calls (lookup_order and process_refund) until get_customer has actually returned a verified customer ID.

Note that the gate checks actual state ("did a verified ID come back?"), not the model's intent. The model may "believe" it verified; the gate doesn't care about beliefs — it opens only when the condition holds in the data. That is the difference between it and any prompt improvement.

بوابة في الكود: أدوات الطلبات والاسترداد لا تنفتح إلا بعد هوية متحقَّقة — بغضّ النظر عن «قناعة» الموديل. A gate in code: order and refund tools open only after a verified identity — regardless of the model's "confidence."

بوابة مسبقة: امنع الاسترداد قبل التحقق من الهوية A prerequisite gate: block refunds until identity is verified 
# Deterministic gate: identity MUST be verified before any order/refund tool runs.
GATED_TOOLS = {"lookup_order", "process_refund"}
verified_customer_id = None

def before_tool(name, args):
    """Runs before every tool call (enforced in code, not by a prompt)."""
    if name in GATED_TOOLS and verified_customer_id is None:
        # Do NOT let the model proceed on a stated name alone.
        raise PrerequisiteError(
            "get_customer must return a verified customer_id before this tool."
        )

def after_tool(name, result):
    """Record the verified identity so the gate opens exactly when satisfied."""
    global verified_customer_id
    if name == "get_customer" and result.get("verified") is True:
        verified_customer_id = result["customer_id"]
لمحة سريعة: البوابة تعالج مشكلة ترتيب («تحقق قبل ما تسترد»)، بينما مصنّف التوجيه يعالج مشكلة توفّر («أي أدوات تُعرض لهذا الطلب»). سؤال الدليل الرسمي الأول يميّز بينهما بالضبط — لا تخلطهما.
Quick insight: a gate solves an ordering problem ("verify before refunding"), while a routing classifier solves an availability problem ("which tools are exposed for this request"). The guide's first official sample question hinges on exactly that distinction — don't conflate them.

03 الطلبات متعددة الهموم: فكّك، حقّق بالتوازي، وحّد Multi-concern requests: decompose, investigate in parallel, unify

رسالة عميل واقعية نادرًا ما تحمل همًّا واحدًا: «طلبي وصل ناقص، وانخصم مني مرتين، وأبغى أغيّر عنوان التوصيل الجاي». التعامل معها كسؤال واحد يعني إجابة تلمّ أطرافها وتفوّت التفاصيل. النمط الصحيح ثلاث خطوات: (1) فكّك الرسالة إلى عناصر منفصلة (نقص بالشحنة / خصم مكرر / تحديث عنوان)؛ (2) حقّق في كل عنصر بالتوازي مستفيدًا من سياق مشترك — هوية العميل المتحقَّقة وسجل الطلب يُجلبان مرة واحدة ويخدمان التحقيقات الثلاثة؛ (3) وحّد الحل في رد واحد متماسك يعالج كل همّ بنتيجته.

A real customer message rarely carries one concern: "my order arrived incomplete, I was charged twice, and I want to change my next delivery address." Treating it as a single question produces an answer that skims all three and nails none. The correct pattern has three steps: (1) decompose the message into distinct items (short shipment / duplicate charge / address update); (2) investigate each in parallel over shared context — the verified identity and order record are fetched once and serve all three investigations; (3) synthesize a unified resolution: one coherent reply addressing every concern with its outcome.

تفكيك ← تحقيق متوازٍ بسياق مشترك ← توحيد: كل همّ يُعالج، والعميل يستلم ردًا واحدًا متكاملًا. Decompose, investigate in parallel over shared context, unify: every concern handled, one complete reply.

04 التسليم المنظّم: صعّد بملف، لا بلغز Structured handoff: escalate with a file, not a riddle

أحيانًا يجب التصعيد في منتصف العملية — استثناء سياسة، حد صلاحيات، أو طلب صريح من العميل. المشكلة: الموظف البشري المستلم لا يملك وصولًا لنص المحادثة. لو صعّدت بـ «عميل غاضب يحتاج مساعدة»، أجبرت الموظف يبدأ من الصفر ويعيد على العميل نفس الأسئلة — أسوأ تجربة ممكنة.

بروتوكول التسليم المنظّم يرسل ملفًا مكتملًا: هوية العميل (متحقَّقة)، تحليل السبب الجذري (وش صار فعلًا)، تفاصيل مالية (مبلغ الاسترداد المطلوب)، والإجراء الموصى به (وش يحتاج قرار بشري بالضبط وليش). الموظف يفتح الملف ويقرّر خلال ثوانٍ — والعميل ما يعيد قصته.

Sometimes you must escalate mid-process — a policy exception, an authority limit, or an explicit customer request. The problem: the receiving human agent has no access to the conversation transcript. Escalate with "angry customer needs help" and you force the human to start over and re-ask the customer everything — the worst possible experience.

A structured handoff protocol ships a complete file: the customer ID (verified), a root cause analysis (what actually happened), financial details (the refund amount at stake), and the recommended action (exactly what needs a human decision and why). The human opens the file and decides in seconds — and the customer never repeats their story.

ملخّص تسليم منظّم عند التصعيد لموظف بشري A structured handoff summary for human escalation 
{
  "escalation_reason": "policy_gap: competitor price match not covered by policy",
  "customer_id": "CUS-84213",
  "identity_verified": true,
  "root_cause": "Customer wants a price match vs a competitor; policy only covers own-site drops within 14 days.",
  "concerns": [
    { "order_id": "ORD-55190", "issue": "price_match_request", "amount_requested": 42.00 },
    { "order_id": "ORD-55190", "issue": "late_delivery_credit", "amount_requested": 10.00 }
  ],
  "refund_amount_at_stake": 52.00,
  "recommended_action": "Human decides on a one-time goodwill credit; no policy precedent exists.",
  "summary_for_human": "Verified customer, 1 order, 2 concerns; agent lacks authority on the price match."
}
تنبيه: صمّم الملخّص على افتراض أن قارئه ما شاف أي شيء من المحادثة. أي معلومة «بديهية عندك» وغير مكتوبة في الملخّص = معلومة ضائعة عند الموظف.
Warning: design the summary assuming its reader saw none of the conversation. Any fact that is "obvious to you" but unwritten in the summary is a fact the human never receives.

فخ الاختبارExam trap

  • «12% من الحالات يتخطّى الوكيل get_customer» ← الجواب بوابة برمجية؛ «شدّد البرومبت» و«أضف few-shot» و«مصنّف توجيه» ثلاثتها مشتّتات (الأولان احتماليان، والثالث يحل مشكلة توفّر لا ترتيب)."In 12% of cases the agent skips get_customer" — the answer is a programmatic gate; "strengthen the prompt," "add few-shot," and "a routing classifier" are all distractors (the first two are probabilistic; the third solves availability, not ordering).
  • التصعيد بجملة عامة أو برسالة «راجع المحادثة» — الموظف لا يرى المحادثة أصلًا؛ الصحيح ملخّص منظّم بالحقول الأربعة.Escalating with a vague line or "see the conversation" — the human can't see the conversation at all; correct is a structured summary with the four fields.
  • معالجة رسالة متعددة الهموم همًّا تلو الآخر بردود منفصلة، أو تجاهل بعض الهموم — الصحيح: تفكيك، تحقيق متوازٍ بسياق مشترك، رد موحّد.Handling a multi-concern message one concern at a time with separate replies, or dropping concerns — correct: decompose, parallel investigation over shared context, one unified reply.

مثال من الحياة: بوابة صعود الطائرة Real-life example: the airport boarding gate

في المطار نوعان من «القواعد». اللوحة المكتوب عليها «جهّزوا جوازاتكم وبطاقات الصعود» — هذا البرومبت: توجيه مفيد، وأغلب الناس يلتزمون به، لكن دائمًا فيه واحد واصل البوابة وجوازه في قاع الشنطة. أما بوابة الصعود نفسها فما تفتح إلا بمسح بطاقة صالحة — هذي البوابة المسبقة: ما تهتم كم أنت متأكد أنك «على هذي الرحلة»، ولا تقبل الرجاء ولا الاستعجال. الشرط يتحقق في النظام، أو ما تعدّي. صفر استثناءات، صفر ركاب على الرحلة الغلط.

ولما تنكشف مشكلة في جوازك، موظف البوابة ما يقول لك «روح لمكتب الجوازات واشرح لهم من الأول» — يطبع قسيمة تحويل منظّمة: اسمك، رقم رحلتك، المشكلة بالضبط، والإجراء المطلوب. موظف المكتب — اللي ما حضر شيئًا مما جرى عند البوابة — يفتح القسيمة ويعرف كل شيء خلال ثوانٍ. هذا هو ملخّص التسليم المنظّم: المستلم يقرّر بسرعة لأن الملف كامل، مو لأنه سمع القصة.

An airport runs on two kinds of "rules." The sign reading "have your passports and boarding passes ready" — that's the prompt: useful guidance, and most people comply, but there's always someone at the gate with their passport at the bottom of a bag. The boarding gate itself, though, opens only on a valid scan — that's the prerequisite gate: it doesn't care how certain you are that you're "on this flight," and accepts neither pleading nor urgency. The condition verifies in the system, or you don't pass. Zero exceptions, zero passengers on the wrong plane.

And when a problem surfaces with your passport, the gate agent doesn't say "go to the immigration desk and explain from the top" — they print a structured transfer slip: your name, flight number, the exact problem, and the required action. The desk officer — who witnessed nothing at the gate — opens the slip and knows everything in seconds. That is the structured handoff summary: the receiver decides fast because the file is complete, not because they heard the story.

في الاختبارOn the exam

أسئلة 1.4 تعطيك نسبة فشل من الإنتاج («في X% من الحالات يتخطّى الوكيل خطوة إلزامية») أو موقف تصعيد، وتطلب الحل الأضمن.

  • كلمات مثل «إلزامي»، «دائمًا»، «لا يفشل أبدًا»، «عواقب مالية» = المطلوب فرض برمجي (بوابة/hook)، واستبعد كل الخيارات البرومبتية فورًا.
  • سؤال التصعيد الصحيح جوابه يذكر الحقول: هوية متحقَّقة، سبب جذري، مبلغ، إجراء موصى به — لأن المستلم بلا وصول للمحادثة.
  • انتبه لمشتّت «مصنّف التوجيه»: يبدو تقنيًا مقنعًا لكنه يحل مشكلة توفّر الأدوات، والسؤال غالبًا عن ترتيب الخطوات.

Task 1.4 questions hand you a production failure rate ("in X% of cases the agent skips a mandatory step") or an escalation situation, and ask for the most reliable fix.

  • Words like "mandatory," "always," "never fails," "financial consequences" = programmatic enforcement (gate/hook) is required; eliminate every prompt-side option on sight.
  • The right escalation answer names the fields: verified ID, root cause, amount, recommended action — because the receiver has no transcript access.
  • Watch the "routing classifier" distractor: it sounds technically convincing but solves tool availability, while the question is usually about step ordering.

خلاصةTakeaway

  • برومبت = احتمالي بنسبة فشل غير صفرية؛ بوابة/hook = حتمي 100%. القواعد الملزمة للكود.
  • احجب process_refund (وlookup_order) حتى يرجع get_customer هوية متحقَّقة.
  • البوابة تحل «الترتيب»، والمصنّف يحل «التوفّر» — لا تخلط بينهما.
  • الطلب متعدد الهموم: فكّك ← حقّق بالتوازي بسياق مشترك ← وحّد الرد.
  • التصعيد = ملخّص منظّم (هوية، سبب جذري، مبلغ، توصية) — المستلم لا يرى المحادثة.
  • Prompt = probabilistic with a non-zero failure rate; gate/hook = 100% deterministic. Binding rules go in code.
  • Block process_refund (and lookup_order) until get_customer returns a verified ID.
  • Gates solve ordering; classifiers solve availability — never conflate the two.
  • Multi-concern requests: decompose, investigate in parallel over shared context, unify the reply.
  • Escalation = a structured summary (ID, root cause, amount, recommendation) — the receiver can't see the transcript.
