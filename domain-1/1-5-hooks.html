خطافات الـ Agent SDK: الاعتراض والتوحيد Agent SDK hooks: interception & normalization

الـ hooks هي «قوانين الفيزياء» في نظامك الوكيل: تتنفّذ في كل مرة، ولا تعتمد على انتباه الموديل. بها توحّد البيانات الداخلة وتحظر الأفعال الخارجة المخالفة. Hooks are your agent system's "laws of physics": they fire every single time, independent of the model's attention. With them you normalize incoming data and block outgoing violations.

وش بتتعلم What you'll learn

  • تشرح نمط PostToolUse: اعتراض نتيجة الأداة وتحويلها قبل أن يعالجها الموديل.
  • تشرح نمط اعتراض النداءات الصادرة: فحص نداء الأداة قبل تنفيذه لفرض قواعد الامتثال.
  • توحّد صيغًا غير متجانسة من أدوات MCP مختلفة (Unix timestamps، ISO 8601، رموز حالة رقمية) بهوك PostToolUse.
  • تحظر الأفعال المخالفة للسياسة (استرداد فوق 500$) وتوجّه الوكيل لمسار بديل (تصعيد بشري).
  • تختار الـ hooks على الفرض البرومبتي متى ما تطلّبت قاعدة العمل امتثالًا مضمونًا.
  • Explain the PostToolUse pattern: intercepting a tool's result and transforming it before the model processes it.
  • Explain outgoing-call interception: inspecting a tool call before it executes to enforce compliance rules.
  • Normalize heterogeneous formats from different MCP tools (Unix timestamps, ISO 8601, numeric status codes) with a PostToolUse hook.
  • Block policy-violating actions (refunds over $500) and redirect the agent to an alternative workflow (human escalation).
  • Choose hooks over prompt-based enforcement whenever a business rule requires guaranteed compliance.

01 وش هي الـ hooks؟ نقاط اعتراض في دورة الحياة What are hooks? Interception points in the lifecycle

الـ hook هو دالة تكتبها أنت ويشغّلها الـ SDK تلقائيًا عند نقطة محددة من دورة حياة الوكيل. الاختبار يركّز على نمطين مرتبطين باتجاهين متعاكسين: اعتراض النداء الصادر (نمط PreToolUse) — يفحص نداء الأداة قبل تنفيذه ويقدر يسمح أو يرفض؛ واعتراض النتيجة الداخلة (PostToolUse) — يستلم نتيجة الأداة بعد التنفيذ وقبل أن تصل للموديل ويقدر يحوّلها.

الفرق الجوهري عن أي تعليمة برومبت: الـ hook كود يتنفّذ في كل مرة بلا استثناء. الموديل ما يقدر «ينسى» تشغيله ولا «يجتهد» بتجاوزه — لأنه أصلًا خارج إرادة الموديل. لذلك يوصف الـ hook بأنه ضمانة حتمية، بينما تعليمة البرومبت امتثال احتمالي.

A hook is a function you write that the SDK runs automatically at a defined point in the agent's lifecycle. The exam focuses on two patterns tied to opposite directions: outgoing-call interception (the PreToolUse pattern) — inspecting a tool call before it executes, able to allow or deny; and incoming-result interception (PostToolUse) — receiving the tool's result after execution but before it reaches the model, able to transform it.

The essential difference from any prompt instruction: a hook is code that runs every time without exception. The model cannot "forget" to trigger it or "reason" its way around it — it sits outside the model's will entirely. That is why a hook is described as a deterministic guarantee while a prompt instruction is probabilistic compliance.

model emits tool call
PreToolUse gate
allow / deny
tool executes
PostToolUse
normalize result
model processes result
deny path: call blocked + reason returned to model -> alternative workflow (escalate_to_human)

خط الأنابيب: بوابة قبل التنفيذ تفرض السياسة، ومحوّل بعد التنفيذ يوحّد النتيجة — والموديل لا يرى إلا الشكل النظيف. The pipeline: a pre-execution gate enforces policy, a post-execution transformer normalizes the result — the model only ever sees the clean shape.

مفهوم أساسي: احفظ اتجاه كل نمط: PostToolUse يشكّل البيانات الداخلة للموديل (توحيد/تنظيف النتائج)، واعتراض النداءات يحكم الأفعال الخارجة منه (حظر/تحويل). أسئلة كثيرة تُحسم بمجرد تحديد الاتجاه المطلوب.
Key concept: memorize each pattern's direction: PostToolUse shapes data flowing in to the model (normalizing/cleaning results), while call interception governs actions flowing out of it (blocking/redirecting). Many questions are settled just by identifying which direction is needed.

02 PostToolUse: توحيد البيانات غير المتجانسة PostToolUse: normalizing heterogeneous data

الحالة النموذجية من سيناريو 1: وكيل الدعم يستخدم ثلاث أدوات MCP من أنظمة خلفية مختلفة — وحدة ترجع التواريخ Unix timestamps (أرقام مثل 1789034400)، وثانية ISO 8601، وثالثة ترجع الحالات كرموز رقمية (status: 2 بدل «موقوف»). لو تركت الموديل «ينتبه للصيَغ» بنفسه، سيقرؤها صح غالبًا... ويغلط أحيانًا — وأحيانًا في خدمة عملاء تعني معلومات شحن خاطئة لعميل حقيقي.

الإصلاح المعماري: هوك PostToolUse يعترض كل نتيجة أداة ويحوّل الصيَغ الثلاث إلى شكل قياسي واحد قبل أن تدخل سياق الموديل. النتيجة: الموديل ما يشوف الفوضى أصلًا، فلا توجد فرصة ليخطئ قراءتها — انعدام فرصة الخطأ أقوى من أي «انتباه» له.

The canonical case from Scenario 1: the support agent uses three MCP tools from different backends — one returns dates as Unix timestamps (numbers like 1789034400), another as ISO 8601, and a third returns statuses as numeric codes (status: 2 instead of "suspended"). Leave the model to "watch out for formats" on its own and it will read them right most of the time... and wrong occasionally — and in customer support, occasionally means wrong shipping information to a real customer.

The architectural fix: a PostToolUse hook intercepts every tool result and converts all three formats into one canonical shape before it enters the model's context. The model never sees the mess at all, so there is no opportunity to misread it — eliminating the opportunity beats any amount of "attention."

هوك PostToolUse يوحّد الصيَغ قبل وصولها للموديل A PostToolUse hook normalizing formats before they reach the model 
from datetime import datetime, timezone
from claude_agent_sdk import query, ClaudeAgentOptions, HookMatcher

STATUS_LABELS = {0: "inactive", 1: "active", 2: "suspended"}

async def normalize_tool_data(input_data, tool_use_id, context):
    """PostToolUse: runs AFTER the tool executes, BEFORE the model processes it."""
    raw = input_data["tool_response"]
    normalized = dict(raw)

    # Unix timestamp (1789034400) -> ISO 8601
    if isinstance(raw.get("created_at"), (int, float)):
        normalized["created_at"] = datetime.fromtimestamp(
            raw["created_at"], tz=timezone.utc).isoformat()

    # Numeric status code (2) -> semantic label ("suspended")
    if isinstance(raw.get("status"), int):
        normalized["status"] = STATUS_LABELS.get(raw["status"], "unknown")

    # Hand the model ONE canonical shape, whatever the backend returned
    return {
        "hookSpecificOutput": {
            "hookEventName": "PostToolUse",
            "additionalContext": f"Normalized tool data: {normalized}",
        }
    }

options = ClaudeAgentOptions(
    hooks={
        # No matcher -> applies to every tool result from every MCP server
        "PostToolUse": [HookMatcher(hooks=[normalize_tool_data])],
    },
)
لمحة سريعة: «أضف أداة convert_date يستدعيها الموديل عند الحاجة» تبدو حلًا — لكنها ترجع الاعتماد على أن الموديل يتذكّر استدعاءها كل مرة. رجعت للاحتمالية من الباب الخلفي. التوحيد في hook يشيل القرار من يد الموديل نهائيًا.
Quick insight: "add a convert_date tool the model can call when needed" sounds like a fix — but it re-introduces reliance on the model remembering to call it every time. Probability sneaks back in through the side door. Normalizing in a hook removes the decision from the model's hands entirely.

03 اعتراض النداءات: احظر ووجّه لمسار بديل Call interception: block and redirect

الحالة الثانية: قاعدة عمل تقول «أي استرداد فوق 500$ يتطلّب موافقة بشرية». الحل الحتمي: hook يعترض نداء process_refund قبل تنفيذه، يفحص المبلغ، وإذا تجاوز الحد يرفض النداء ويرجّع للموديل سببَ الرفض مع التوجيه للمسار البديل: escalate_to_human. الموديل يستلم الرفض كنتيجة، يفهم السبب، ويكمل عبر مسار التصعيد — بملخّص التسليم المنظّم الذي تعلمناه في 1.4.

لاحظ جمال التركيبة: الحظر حتمي (ولا استرداد فوق الحد سيمرّ أبدًا)، لكن الاستجابة له تبقى ذكية — الموديل يقرأ سبب الرفض ويتصرف بناءً عليه بدل ما ينهار أو يكرر المحاولة عمياء.

The second case: a business rule says "any refund above $500 requires human approval." The deterministic solution: a hook intercepts the process_refund call before it executes, checks the amount, and above the threshold it denies the call, returning the reason to the model along with the pointer to the alternative workflow: escalate_to_human. The model receives the denial as a result, understands why, and proceeds down the escalation path — with the structured handoff summary from 1.4.

Note the elegance of the combination: the block is deterministic (no over-limit refund will ever pass), yet the response to it stays intelligent — the model reads the denial reason and acts on it rather than crashing or blindly retrying.

هوك اعتراض يحظر الاسترداد فوق 500$ ويوجّه للتصعيد An interception hook blocking refunds over $500 and redirecting to escalation 
REFUND_LIMIT = 500   # business rule: above this, a human must approve

async def enforce_refund_policy(input_data, tool_use_id, context):
    """Deterministic guardrail: fires on EVERY call -- it cannot be
    'forgotten' the way a prompt instruction can."""
    amount = input_data["tool_input"].get("amount", 0)
    if amount > REFUND_LIMIT:
        return {
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",          # block the call outright
                "permissionDecisionReason": (
                    f"Refunds over ${REFUND_LIMIT} require human approval "
                    f"(requested: ${amount}). Use escalate_to_human instead."
                ),
            }
        }
    return {}   # under the limit -> allow the call through

options = ClaudeAgentOptions(
    hooks={
        # Matcher scopes the hook to the refund tool only
        "PreToolUse": [HookMatcher(matcher="process_refund",
                                   hooks=[enforce_refund_policy])],
    },
)
# The deny reason is fed back to the model, which then follows the
# alternative workflow: calling escalate_to_human with a handoff summary.

04 Hooks أم برومبت؟ قاعدة الاختيار Hooks or prompts? The selection rule

القاعدة كما يصوغها الدليل: إذا كانت قاعدة العمل تتطلّب امتثالًا مضمونًا، اختر الـ hook. البرومبت يبقى مناسبًا للتوجيه السلوكي — النبرة، الأسلوب، التفضيلات — حيث الخطأ النادر مقبول. الفرق ليس في «القوة» بل في طبيعة الضمان: الـ hook ينفَّذ 100% من المرات لأنه كود؛ البرومبت يُتَّبع «غالبًا» لأنه إقناع.

The rule as the guide frames it: when a business rule requires guaranteed compliance, choose the hook. Prompts remain right for behavioral guidance — tone, style, preferences — where a rare miss is acceptable. The difference isn't "strength" but the nature of the guarantee: a hook fires 100% of the time because it's code; a prompt is followed "usually" because it's persuasion.

HOOK — deterministic
fires on EVERY call, no exceptions
lives in code, outside model judgment
fits: refund limits, format normalization
PROMPT — probabilistic
followed "usually" -- until it isn't
lives inside model judgment
fits: tone, style, soft preferences

قاعدة ملزمة بعواقب مالية أو قانونية؟ اللوحة الخضراء. توجيه سلوكي يحتمل الخطأ النادر؟ اللوحة الحمراء تكفي. Binding rule with financial or legal stakes? The green panel. Behavioral guidance tolerating a rare miss? The red panel suffices.

تنبيه: لا تعكس القاعدة: نقل كل شيء للـ hooks (حتى النبرة والأسلوب) يجمّد النظام ويحرمك مرونة الموديل. الـ hooks للقواعد الملزمة؛ البرومبت لكل ما عداها.
Warning: don't invert the rule either: pushing everything into hooks (even tone and style) rigidifies the system and forfeits the model's flexibility. Hooks are for binding rules; prompts for everything else.

فخ الاختبارExam trap

  • «أضف للبرومبت: لا تسترد فوق 500$» — يبدو منطقيًا لكنه احتمالي؛ للقواعد الملزمة الجواب دائمًا اعتراض برمجي."Add to the prompt: never refund above $500" — sounds reasonable but is probabilistic; for binding rules the answer is always programmatic interception.
  • «اشرح الصيَغ الثلاث في البرومبت» أو «أضف أداة تحويل يستدعيها عند الحاجة» — كلاهما يعتمد على تذكّر الموديل؛ PostToolUse يضمن التوحيد."Explain the three formats in the prompt" or "add a conversion tool it can call when needed" — both depend on the model remembering; PostToolUse guarantees the normalization.
  • «اطلب من فرق الأنظمة الخلفية توحيد صيَغهم» — حل تنظيمي بطيء خارج سيطرتك؛ الاختبار يبي الإصلاح المعماري في طبقتك أنت."Ask the backend teams to standardize their formats" — a slow organizational fix outside your control; the exam wants the architectural fix in your own layer.
  • خلط الاتجاهات: اختيار PostToolUse لحظر نداء صادر، أو اعتراض النداءات لتنظيف نتيجة داخلة.Mixing directions: picking PostToolUse to block an outgoing call, or call interception to clean an incoming result.

مثال من الحياة: لوحة الكهرباء في البيت Real-life example: the home electrical panel

لوحة الكهرباء عندك فيها الجهازان اللذان يشرحان الـ hooks بالضبط. القاطع (circuit breaker) هو هوك الاعتراض: أي حمل يتجاوز الحد المسموح، يفصل التيار فورًا وفي كل مرة — ما يسأل عن نيّتك ولا يتأثر بحماسك، والتيار الزائد ببساطة لن يمرّ. هذا بالضبط حظر الاسترداد فوق 500$: القاعدة تتنفّذ في الكود قبل وقوع الضرر، ويوجّهك القاطع للمسار البديل (فنّي الكهرباء = التصعيد البشري).

ومنظّم الجهد (voltage stabilizer) هو هوك PostToolUse: الكهرباء توصل البيت من مصادر بجهد متذبذب، لكنه يسلّم أجهزتك 220V ثابتة دائمًا — أجهزتك ما تشوف الفوضى أصلًا، فما تحتاج «تنتبه». قارن هذا بورقة ملصوقة على اللوحة: «الرجاء عدم تشغيل السخان والمكيف معًا» — هذي تعليمة البرومبت: أغلب أهل البيت يلتزمون، إلى أن ينسى أحدهم يومًا... والفرق بين الورقة والقاطع هو حرفيًا الفرق بين البرومبت والـ hook.

Your electrical panel holds the two devices that explain hooks exactly. The circuit breaker is the interception hook: any load beyond the rated limit and it cuts the current instantly, every single time — it doesn't ask about your intentions or bend to your enthusiasm; the excess current simply will not pass. That is precisely the over-$500 refund block: the rule executes in code before the damage happens, and the breaker points you to the alternative path (the electrician = human escalation).

The voltage stabilizer is the PostToolUse hook: power reaches the house from sources with fluctuating voltage, but it hands your appliances a steady 220V always — your devices never see the chaos, so they never need to "be careful." Compare that with a note taped to the panel: "please don't run the heater and AC together" — that's the prompt instruction: most of the household complies, until someone forgets one day... and the difference between the note and the breaker is literally the difference between a prompt and a hook.

في الاختبارOn the exam

أسئلة 1.5 نوعان: «بيانات غير متجانسة تسبّب أخطاء قراءة» (الجواب PostToolUse) و«قاعدة عمل ملزمة تُخالَف أحيانًا» (الجواب اعتراض النداء + توجيه بديل).

  • حدّد الاتجاه أولًا: بيانات داخلة للموديل ← PostToolUse؛ فعل خارج من الموديل ← اعتراض النداء (deny + سبب + مسار بديل).
  • عبارة «امتثال مضمون / guaranteed compliance» في السؤال = hook، مهما بدت خيارات البرومبت مصقولة.
  • المشتّتات الثلاثة الدائمة: تعليمات برومبت عن الصيَغ، أداة تحويل اختيارية، وطلب توحيد من فرق خارجية — كلها تعيد الاحتمالية أو تخرج عن سيطرتك.

Task 1.5 questions come in two kinds: "heterogeneous data causes misreads" (answer: PostToolUse) and "a binding business rule gets violated occasionally" (answer: call interception + alternative redirect).

  • Identify the direction first: data flowing into the model — PostToolUse; an action flowing out of the model — call interception (deny + reason + alternative workflow).
  • The phrase "guaranteed compliance" in the stem = hook, however polished the prompt options look.
  • The three recurring distractors: prompt instructions about formats, an optional conversion tool, and asking external teams to standardize — each re-introduces probability or leaves your control.

أي متطلب من التالي يرجّح كفّة hook على تعليمة برومبت؟ Which of the following requirements tips the scale toward a hook over a prompt instruction?

صحيح. «يُمنع منعًا باتًا» + عواقب تنظيمية = امتثال مضمون مطلوب، وهذا حصريًا اختصاص الـ hooks. البقية تفضيلات أسلوبية يكفيها البرومبت. Correct. "Strictly forbidden" + regulatory stakes = guaranteed compliance required, which is exclusively hook territory. The rest are stylistic preferences a prompt handles fine.
خطأ. الصحيح: القاعدة التنظيمية الملزمة. النبرة والافتتاحية واللغة كلها توجيه سلوكي يتحمّل الخطأ النادر — برومبت يكفيها؛ الـ hook للقواعد التي لا تقبل الفشل. Not quite. خلاصةTakeaway

  • PostToolUse = بيانات داخلة: وحّد Unix timestamps وISO 8601 والرموز الرقمية قبل الموديل.
  • اعتراض النداءات = أفعال خارجة: deny فوق الحد + سبب + مسار بديل (تصعيد بشري).
  • Hook = ضمانة حتمية 100%؛ برومبت = امتثال احتمالي. «امتثال مضمون» في السؤال = hook.
  • لا تعكسها: النبرة والأسلوب تظل للبرومبت — الـ hooks للقواعد الملزمة فقط.
  • PostToolUse = incoming data: normalize Unix timestamps, ISO 8601, and numeric codes before the model.
  • Call interception = outgoing actions: deny above the limit + reason + alternative workflow (human escalation).
  • Hook = 100% deterministic guarantee; prompt = probabilistic compliance. "Guaranteed compliance" in the stem = hook.
  • Don't invert it: tone and style stay in the prompt — hooks are for binding rules only.
