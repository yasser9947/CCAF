حلقة الوكيل للتنفيذ المستقل The agentic loop for autonomous execution

كل وكيل — من بوت الدعم إلى مساعد البرمجة — هو في جوهره هذي الحلقة. إذا فهمت متى تستمر ومتى تتوقف، فهمت نصف الـ Agent SDK. Every agent — from a support bot to a coding assistant — is at its core this loop. Understand when it continues and when it stops, and you understand half the Agent SDK.

وش بتتعلم What you'll learn

  • تشرح دورة حياة الحلقة الوكيلة: إرسال الطلب لـ Claude، فحص stop_reason، تنفيذ الأدوات المطلوبة، وإرجاع النتائج للدورة التالية.
  • تبني control flow يستمر عند "tool_use" ويتوقف عند "end_turn" — لا شيء غيرهما.
  • تضيف نتائج الأدوات (tool_result مربوطة بـ tool_use_id) لتاريخ المحادثة حتى يبني الموديل على المعلومة الجديدة.
  • تفرّق بين القرار الذي يقوده الموديل (model-driven) وشجرة القرارات المُعدّة مسبقًا.
  • تتجنّب أنماط الإيقاف الخاطئة الثلاثة: تحليل النص، سقف التكرارات كآلية أساسية، واعتبار وجود النص دليل اكتمال.
  • Explain the agentic loop lifecycle: send a request to Claude, inspect stop_reason, execute the requested tools, and return results for the next iteration.
  • Build control flow that continues on "tool_use" and terminates on "end_turn" — nothing else.
  • Append tool results (tool_result keyed by tool_use_id) to conversation history so the model can reason over the new information.
  • Distinguish model-driven decision-making from pre-configured decision trees.
  • Avoid the three termination anti-patterns: text parsing, iteration caps as the primary stop, and treating text presence as completion.

01 دورة الحياة: أربع خطوات تتكرّر The lifecycle: four repeating steps

الحلقة الوكيلة (agentic loop) هي القلب النابض لأي وكيل. دورتها بسيطة: ترسل الطلب لـ Claude، ثم تفحص stop_reason في الرد. لو كانت قيمته "tool_use" فهذا يعني أن Claude يطلب تنفيذ أداة أو أكثر: تنفّذها أنت في الكود، وترجّع النتائج، وتعيد الإرسال. ولو كانت "end_turn" فالموديل أنهى المهمة وقدّم رده النهائي — الحلقة تنكسر هنا.

لاحظ التقسيم الدقيق للأدوار: الموديل يقرّر (أي أداة، بأي مدخلات، ومتى ينتهي)، والكود ينفّذ (يشغّل الأداة ويرجّع النتيجة). أنت ما تكتب منطق «إذا سأل عن الطلب استدعِ lookup_order» — Claude نفسه يستنتج ذلك من السياق ووصف الأدوات.

The agentic loop is the beating heart of any agent. The cycle is simple: send a request to Claude, then inspect the response's stop_reason. If it is "tool_use", Claude is requesting one or more tool executions: your code runs them, returns the results, and sends again. If it is "end_turn", the model has finished the task and produced its final answer — the loop breaks here.

Note the precise division of labor: the model decides (which tool, with what inputs, and when it's done) while your code executes (runs the tool, returns the result). You never write logic like "if they ask about an order, call lookup_order" — Claude infers that from context and tool descriptions.

user request
messages.create()
check stop_reason
"tool_use"
execute requested tools
append tool_result to messages
loop: send again
"end_turn"
task complete
return final text to user
exit loop

الدورة الكاملة: طلب ← فحص stop_reason ← تنفيذ وإلحاق النتائج ← تكرار، والخروج الوحيد عند end_turn. The full cycle: request, inspect stop_reason, execute and append results, repeat — the only exit is end_turn.

حلقة وكيل تُقاد بـ stop_reason (Messages API) An agentic loop driven by stop_reason (Messages API) 
import anthropic

client = anthropic.Anthropic()
messages = [{"role": "user", "content": "Refund order #12345 for this customer"}]

while True:
    response = client.messages.create(
        model="claude-opus-4-8",
        max_tokens=1024,
        tools=TOOLS,                      # your MCP / custom tool schemas
        messages=messages,
    )

    # Control flow is driven ONLY by stop_reason -- never by parsing text.
    if response.stop_reason == "tool_use":
        # 1) Record Claude's turn (it may contain several tool_use blocks)
        messages.append({"role": "assistant", "content": response.content})

        # 2) Execute every requested tool and collect the results
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                output = run_tool(block.name, block.input)      # your dispatcher
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,                    # correlate to the call
                    "content": output,
                })

        # 3) Append results so the model can reason on the NEXT iteration
        messages.append({"role": "user", "content": tool_results})
        continue

    # stop_reason == "end_turn" -> the task is done
    break

final_text = "".join(b.text for b in response.content if b.type == "text")
print(final_text)

02 إلحاق النتائج بالسياق: وقود الدورة التالية Appending results to context: fuel for the next iteration

ليش نلحق النتائج بتاريخ المحادثة؟ لأن الموديل عديم الذاكرة بين النداءات — كل نداء API مستقل، وما «يشوف» إلا ما ترسله في messages. فإذا نفّذت lookup_order وما رجّعت النتيجة في الرسالة التالية، فكأن العملية ما صارت أبدًا من وجهة نظر Claude.

الترتيب الدقيق: (1) تلحق رد المساعد كاملًا (بما فيه كتل tool_use)، ثم (2) تلحق رسالة user تحتوي كتل tool_result، كل كتلة مربوطة بندائها عبر tool_use_id. بهذا يقدر الموديل في الدورة التالية أن يقرأ النتيجة، يربطها بالسؤال اللي طرحه، ويقرّر خطوته الجاية بناءً عليها — هذي هي «المحادثة الذاتية» اللي تجعل الوكيل وكيلًا.

Why append results to conversation history? Because the model is stateless between calls — every API call stands alone, and Claude "sees" only what you send in messages. If you execute lookup_order but don't return the result in the next message, from Claude's perspective the operation never happened.

The exact order: (1) append the assistant's full turn (including its tool_use blocks), then (2) append a user message containing tool_result blocks, each correlated to its call via tool_use_id. On the next iteration the model reads the result, ties it back to the question it asked, and decides its next move accordingly — this is the self-conversation that makes an agent an agent.

لمحة سريعة: الرد الواحد ممكن يحتوي عدة كتل tool_use دفعة واحدة — رجّع tool_result لكل واحدة منها في نفس رسالة الـ user، وإلا يفشل النداء التالي.
Quick insight: a single response can carry several tool_use blocks at once — return a tool_result for each of them in the same user message, or the next call fails.

03 من يقرّر الأداة التالية؟ الموديل، مو مخطط مسبق Who picks the next tool? The model, not a script

هنا الفرق الجوهري بين الوكيل الحقيقي وسكربت الأتمتة: في اتخاذ القرار الذي يقوده الموديل (model-driven decision-making)، Claude يقرأ السياق الحالي — طلب المستخدم، نتائج الأدوات السابقة، أوصاف الأدوات — ويستنتج بنفسه أي أداة يستدعي بعدين. أما شجرة القرارات المُعدّة مسبقًا فتفرض تسلسل أدوات ثابتًا مكتوبًا في الكود: الخطوة 1 ثم 2 ثم 3 مهما حصل.

ليش يهم؟ لأن مهام مثل المرتجعات ونزاعات الفوترة (سيناريو 1) عالية الغموض: ما تعرف مسبقًا وش بيقول العميل ولا وش بتكشف البيانات. الشجرة الثابتة تنكسر مع أول حالة غير متوقعة؛ الموديل يعيد التخطيط ويتكيّف.

Here is the essential difference between a real agent and an automation script: with model-driven decision-making, Claude reads the current context — the user's request, prior tool results, tool descriptions — and infers by itself which tool to call next. A pre-configured decision tree, by contrast, hard-codes a fixed tool sequence: step 1, then 2, then 3 no matter what.

Why does it matter? Because tasks like returns and billing disputes (Scenario 1) are high-ambiguity: you can't know upfront what the customer will say or what the data will reveal. The fixed tree breaks on the first unexpected case; the model re-plans and adapts.

مفهوم أساسي: stop_reason هو «إشارة المرور» الرسمية للحلقة. النص اللي يكتبه الموديل محتوى للمستخدم، مو إشارة تحكّم للبرنامج — وخلط الاثنين هو أصل معظم أخطاء الحلقات.
Key concept: stop_reason is the loop's official traffic light. The model's text is content for the user, not a control signal for your program — conflating the two is the root of most loop bugs.

04 شروط الإيقاف: الصح والغلط Termination: the right way and the wrong ways

دليل الاختبار يسمّي ثلاثة أنماط خاطئة بالاسم، وكلها تظهر كمشتّتات «معقولة» في الأسئلة: تحليل إشارات اللغة الطبيعية لإنهاء الحلقة (البحث عن «انتهيت» في النص)، سقف تكرارات عشوائي كآلية التوقف الأساسية، واعتبار وجود نص في الرد دليل اكتمال. الثلاثة تشترك في نفس الخطيئة: تستبدل الإشارة الرسمية باستدلال هشّ.

The exam guide names three anti-patterns explicitly, and all three appear as "reasonable-looking" distractors: parsing natural-language signals to end the loop (scanning the text for "done"), an arbitrary iteration cap as the primary stopping mechanism, and treating the presence of assistant text as a completion indicator. All three commit the same sin: replacing the official signal with brittle inference.

GOOD — signal-driven
if stop_reason == "tool_use": run + append + loop
if stop_reason == "end_turn": break
cap exists only as a SAFETY backstop
BAD — guess-driven
if "I'm done" in text: break
for i in range(5): ... # cap as PRIMARY stop
if response.has_text: assume complete

اليسار الأخضر يقود بالإشارة الرسمية؛ اليمين الأحمر يخمّن — وكل تخمين ينكسر في الإنتاج. The green panel drives on the official signal; the red panel guesses — and every guess breaks in production.

نصيحة: سقف التكرارات مو ممنوع — وجوده كصمام أمان ضد الحلقات الجامحة ممارسة سليمة. الممنوع أن يكون الآلية الأساسية للتوقف. الفرق بين «حزام أمان» و«فرامل السيارة».
Tip: an iteration cap isn't forbidden — keeping one as a safety valve against runaway loops is sound practice. What's forbidden is making it the primary stopping mechanism. It's the difference between a seatbelt and the car's brakes.

فخ الاختبارExam trap

  • «أوقف الحلقة لما يكتب الموديل عبارة إنهاء متفق عليها» — يبدو ذكيًا، لكنه تحليل لغة طبيعية: نمط خاطئ صريح."Stop the loop when the model writes an agreed completion phrase" — sounds clever, but it's natural-language parsing: an explicit anti-pattern.
  • «حدّد max_iterations كآلية التوقف الأساسية» — السقف حاجز أمان احتياطي فقط."Make max_iterations the primary stop" — a cap is only a safety backstop.
  • «إذا رجع نص في الرد فالمهمة خلصت» — النص ممكن يرافق tool_use («دقيقة أتحقق من الطلب...») فلا يدل على الاكتمال."If the response contains text, the task is done" — text can accompany tool_use ("One moment, checking the order...") so it proves nothing about completion.

مثال من الحياة: الشيف والنادل Real-life example: the chef and the waiter

تخيّل مطبخ مطعم: الشيف هو الموديل والنادل هو الكود اللي ينفّذ الحلقة. الشيف يطبخ، وكل ما احتاج شيئًا من المخزن يرفع تذكرة مكتوبة: «أبغى كيلو طماطم» — هذي بالضبط stop_reason: "tool_use". النادل ما يناقش ولا يفسّر ولا «يحس» — يقرأ التذكرة، يجيب الطلب، ويحطّه قدام الشيف مع رقم التذكرة (tool_use_id) عشان يعرف الشيف هذا رد على أي طلب. ثم يرجع الشيف يكمل بناءً على المكوّن الجديد.

ولما يعلن الشيف «الصحن جاهز، قدّموه» فهذي "end_turn" — إشارة رسمية واضحة. لاحظ وش ما يفعله النادل الشاطر: ما يسحب الصحن لمجرد أنه سمع الشيف يدندن (تحليل نص)، ولا يقرّر «خمس تذاكر تكفي، بقدّم اللي موجود» (سقف تكرارات)، ولا يعتبر أي كلام من الشيف علامة انتهاء (النص ليس دليل اكتمال). النادل يتحرّك على الإشارة الرسمية فقط — وهذا سرّ مطعم ما يطلع منه صحن ناقص.

Picture a restaurant kitchen: the chef is the model and the waiter is the code running the loop. The chef cooks, and whenever he needs something from the storeroom he raises a written ticket: "one kilo of tomatoes" — that is exactly stop_reason: "tool_use". The waiter doesn't argue, interpret, or guess — he reads the ticket, fetches the item, and places it before the chef with the ticket number attached (tool_use_id) so the chef knows which request it answers. The chef then continues, building on the new ingredient.

When the chef announces "the dish is ready, serve it," that is "end_turn" — a clear, official signal. Note what a good waiter never does: he doesn't grab the plate because he heard the chef humming (text parsing), doesn't decide "five tickets is plenty, I'll serve what's there" (iteration cap), and doesn't treat any chatter from the chef as a done signal (text is not completion). The waiter moves on the official signal only — which is why no half-finished dish ever leaves that kitchen.

في الاختبارOn the exam

أسئلة 1.1 تجيك بصيغتين: «أي تنفيذ للحلقة صحيح؟» (تختار كودًا يقوده stop_reason)، أو «الحلقة تتوقف مبكرًا/تعلق — ليش؟» (تشخّص نمط إيقاف خاطئ).

  • الإجابة الصحيحة دائمًا تذكر stop_reason صراحةً: استمرار عند "tool_use"، توقف عند "end_turn"، مع إلحاق النتائج بين الدورات.
  • استبعد فورًا: أي خيار يفحص نص الرد، أي خيار يجعل العدّاد آلية التوقف الأساسية، وأي خيار يستنتج الاكتمال من وجود نص.
  • انتبه لخيارات تنسى إلحاق tool_result للتاريخ — بدونها الموديل «ما شاف» النتيجة أصلًا.

Task 1.1 questions come in two shapes: "which loop implementation is correct?" (pick the stop_reason-driven code) or "the loop stops early / hangs — why?" (diagnose a termination anti-pattern).

  • The correct answer always names stop_reason explicitly: continue on "tool_use", stop on "end_turn", appending results between iterations.
  • Eliminate on sight: any option scanning response text, any option making a counter the primary stop, and any option inferring completion from text presence.
  • Watch for options that forget to append tool_result to history — without it, the model never "saw" the result at all.

صحيح. كل كتلة tool_use تحتاج tool_result مقابلة بمعرّفها، وتُلحق النتائج كلها كرسالة user واحدة قبل الدورة التالية. Correct. Every tool_use block needs a matching tool_result keyed by its id, all appended as one user message before the next iteration.
خطأ. الصحيح: تنفيذ كل الأدوات المطلوبة وإرجاع tool_result لكل كتلة في نفس رسالة الـ user. تجاهل أداة أو بدء محادثة جديدة يقطع سلسلة الاستدلال، والنص المرافق ليس علامة اكتمال. Not quite. The correct step: execute all requested tools and return a tool_result per block in the same user message. Skipping a tool or restarting the conversation breaks the reasoning chain, and accompanying text is not a completion signal.

وكيل دعم ينفّذ lookup_order بنجاح، لكن في الدورة التالية يتصرّف وكأنه ما شاف النتيجة أبدًا ويعيد طلب نفس الأداة. وش أرجح سبب؟ A support agent successfully executes lookup_order, but on the next iteration it acts as if it never saw the result and requests the same tool again. Most likely cause?

صحيح. الموديل عديم الذاكرة بين النداءات — لا يعرف إلا ما في messages. نتيجة ما أُلحقت = نتيجة ما صارت من وجهة نظره، فيعيد الطلب. Correct. The model is stateless between calls — it knows only what's in messages. A result never appended is a result that never happened from its perspective, so it asks again.
خطأ. الصحيح: النتيجة ما أُلحقت بالتاريخ. هذا خلل في الحلقة نفسها مو في البرومبت ولا في سرعة الأداة ولا في max_tokens — الموديل ببساطة ما استلم المعلومة. Not quite. The correct cause: the result was never appended to history. It's a loop bug — not the prompt, not tool speed, not max_tokens. The model simply never received the information.

وش الدور الصحيح لسقف التكرارات (max_iterations) في حلقة وكيل إنتاجية؟ What is the correct role of an iteration cap (max_iterations) in a production agentic loop?

صحيح. السقف حزام أمان: يمنع الكارثة لو انحرفت الحلقة، لكنه لا يقود التوقف الطبيعي — تلك مهمة stop_reason وحدها. Correct. The cap is a seatbelt: it prevents disaster if the loop goes rogue, but it never drives normal termination — that is stop_reason's job alone.
خطأ. الصحيح: صمام أمان احتياطي فقط. جعله الآلية الأساسية نمط خاطئ صريح، ومنعه كليًا مبالغة — الممنوع هو الاعتماد عليه للتوقف الطبيعي بدل stop_reason. Not quite. The correct role: a safety backstop only. Making it primary is an explicit anti-pattern, and banning it entirely is overkill — what's forbidden is relying on it for normal termination instead of stop_reason.

خلاصةTakeaway

  • الحلقة: أرسل ← افحص stop_reason ← نفّذ ← ألحق ← كرّر. الخروج الوحيد: "end_turn".
  • كل tool_use يقابلها tool_result بمعرّفها، تُلحق كرسالة user قبل الدورة التالية.
  • القرار يقوده الموديل من السياق — مو شجرة قرارات مبرمجة.
  • ممنوعات الإيقاف الثلاثة: تحليل النص، السقف كآلية أساسية، النص كدليل اكتمال.
  • The loop: send, inspect stop_reason, execute, append, repeat. The only exit: "end_turn".
  • Every tool_use gets a matching tool_result by id, appended as a user message before the next iteration.
  • Decisions are model-driven from context — not a scripted decision tree.
  • The three termination sins: text parsing, cap-as-primary, text presence as completion.
