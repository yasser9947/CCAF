استجابات الأخطاء المنظّمة لأدوات MCP Structured Error Responses for MCP Tools

ليش هالموضوع مهم؟ لأن الخطأ الجيد يقول للوكيل وش يسوي بعده — يعيد؟ يصحّح؟ يشرح؟ يصعّد؟ — بينما "فشلت العملية" يقفل كل أبواب التعافي. Why it matters: a good error tells the agent what to do next — retry? correct? explain? escalate? — while "Operation failed" slams every recovery door shut.

وش بتتعلمWhat you'll learn

  • نمط علم isError في MCP لإبلاغ الوكيل بفشل الأداة، وليش الرسائل الموحّدة العامة تمنع قرارات التعافي.The MCP isError flag pattern for signaling tool failure to the agent, and why uniform generic messages block recovery decisions.
  • تصنيف الأخطاء الأربعة: عابر (transient)، تحقّق (validation)، عمل (business)، صلاحية (permission) — وقرار الوكيل الصحيح لكل نوع.The four error categories: transient, validation, business, permission — and the correct agent action for each.
  • إرجاع بيانات وصفية منظّمة (errorCategory، isRetryable، وصف مقروء، رسالة ودّية للعميل) تمنع المحاولات المهدورة.Returning structured metadata (errorCategory, isRetryable, a human-readable description, a customer-friendly message) that prevents wasted retries.
  • التعافي المحلي داخل الوكيل الفرعي، التصعيد بنتائج جزئية وما جرت محاولته، والتفريق بين فشل الوصول والنتيجة الفارغة الصالحة.Local recovery inside the subagent, escalation with partial results and what was attempted, and distinguishing access failures from valid empty results.

1 علم isError — والمحتوى اللي يجي بعدهThe isError flag — and the content that follows it

في MCP، الأداة تبلّغ الوكيل بفشلها عبر علم isError: true في الاستجابة — هذا هو النمط الرسمي. لكن العلم لوحده مجرد جرس إنذار؛ القيمة الحقيقية في محتوى الخطأ. رسالة موحّدة عامة مثل "Operation failed" تشعل الجرس وتسكت، فيقف الوكيل حائرًا: أعيد المحاولة؟ أصحّح المدخل؟ أشرح للعميل؟ أصعّد لإنسان؟ الرسائل الموحّدة تمنع الوكيل من اتخاذ قرار التعافي المناسب — هذي عبارة الدليل حرفيًا، وهي مربط الفرس في أسئلة هذا الموضوع.

الحل: أرجِع مع كل خطأ بيانات وصفية منظّمة — errorCategory يصنّف النوع، وisRetryable يحسم قرار الإعادة، ووصف مقروء يشرح، ولو كان الخطأ مخالفة سياسة: رسالة ودّية جاهزة للعميل مع retriable: false صريحة. البيان الصريح لقابلية الإعادة يمنع محاولات مهدورة على خطأ لن يُحل بالتكرار.

In MCP, a tool signals failure to the agent via an isError: true flag on the response — that is the official pattern. But the flag alone is just an alarm bell; the real value is in the error's content. A uniform generic message like "Operation failed" rings the bell and goes silent, leaving the agent stuck: retry? correct the input? explain to the customer? escalate to a human? Uniform responses prevent the agent from making an appropriate recovery decision — that is the guide's phrasing verbatim, and it is the crux of this topic's questions.

The fix: return structured metadata with every error — errorCategory classifies the type, isRetryable settles the retry decision, a human-readable description explains, and for policy violations: a ready customer-friendly message with an explicit retriable: false. Explicitly stating retryability prevents wasted retry attempts on an error repetition will never fix.

استجابة خطأ منظّمة: عمل مقابل عابر A structured error response: business vs transient 

// process_refund rejects an amount above the $500 policy cap.
// Business rule violation -> NOT retryable, explain to the customer.
{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": {
        "errorCategory": "business",
        "isRetryable": false,
        "code": "REFUND_LIMIT_EXCEEDED",
        "description": "Refund of $780 exceeds the $500 auto-approval limit. Requires human approval.",
        "customerMessage": "I can approve refunds up to $500 automatically. For $780 I'll hand this to a specialist who can help.",
        "partialResults": null,
        "attempted": "process_refund(order=ORD-12345, amount=780.00)"
      }
    }
  ]
}

// Contrast: a transient failure the agent SHOULD retry locally.
{
  "isError": true,
  "content": [{ "type": "text", "text": {
    "errorCategory": "transient",
    "isRetryable": true,
    "description": "Billing service timed out after 5s.",
    "attempted": "get_customer(email='a@b.com')"
  }}]
}

لاحظ حقلي attempted وpartialResults — هما اللي يمكّنان المنسّق من قرار ذكي لو صُعّد الخطأ. Note the attempted and partialResults fields — they are what enable an intelligent coordinator decision if the error gets escalated.

لمحة سريعةQuick insight

isError: true ما هو انهيار — هو رسالة للنموذج يقرأها ويتصرف بناءً عليها. عشان كذا محتواها لازم يُكتب للنموذج، مو لسجلات المطوّرين.

isError: true is not a crash — it is a message the model reads and acts on. That is why its content must be written for the model, not for developer logs.

2 شجرة تصنيف الأخطاء الأربعةThe four-category error taxonomy

الدليل يميّز أربعة أنواع، ولكل نوع قرار وكيل مختلف — وهذا بالضبط ما تقيسه الأسئلة: هل تعرف تربط النوع بالقرار؟

The guide distinguishes four categories, each demanding a different agent action — and that is exactly what the questions measure: can you map the category to the action?

مفهوم أساسيKey concept

مخالفة قاعدة العمل (مثل استرجاع فوق الحد) ليست عطلًا تقنيًا — النظام اشتغل صح ورفض صح. عشان كذا ترجع retriable: false مع شرح ودّي جاهز للعميل، فيتحول الوكيل من "يعيد المحاولة بغباء" إلى "يتواصل باحتراف".

A business rule violation (like an over-limit refund) is not a technical fault — the system worked correctly and refused correctly. That is why you return retriable: false with a ready customer-friendly explanation, turning the agent from "dumbly retrying" into "communicating professionally."

3 التعافي المحلي والتصعيد الذكيLocal recovery & intelligent escalation

في الأنظمة متعددة الوكلاء، القاعدة: عالِج الأخطاء العابرة محليًا داخل الوكيل الفرعي (إعادة محاولة بـ backoff)، ولا تصعّد للمنسّق إلا الأخطاء التي ما تنحل محليًا. ولما تصعّد، لا تصعّد "فشلت" — صعّد حزمة سياق كاملة: نوع الفشل، الاستعلام الذي جرت محاولته، والنتائج الجزئية التي تجمّعت قبل الفشل. بهذا يقدر المنسّق يقرر بذكاء: يعيد باستعلام معدّل، يجرّب مصدرًا بديلًا، أو يكمل بالنتائج الجزئية ويعلّم الفجوة.

وهنا النقطة اللي يحبها واضعو الأسئلة: فشل الوصول شيء، والنتيجة الفارغة الصالحة شيء آخر تمامًا. مهلة انتهت أو خدمة سقطت = فشل وصول يحتاج قرار إعادة محاولة. استعلام نجح وما لقى تطابقات = نجاح حقيقي بنتيجة فارغة. اللي يخلط بينهما — يلتقط الخطأ ويرجّع قائمة فارغة موسومة "successful" — يدفن الفشل، فيبني المنسّق تقريرًا ناقصًا وهو ما يدري.

In multi-agent systems the rule is: handle transient errors locally inside the subagent (retry with backoff), and propagate to the coordinator only errors that cannot be resolved locally. And when you do escalate, do not escalate "failed" — escalate a full context package: the failure type, the query that was attempted, and the partial results accumulated before the failure. That lets the coordinator decide intelligently: retry with a modified query, try an alternative source, or proceed with partial results and annotate the gap.

And here is the point examiners love: an access failure is one thing; a valid empty result is another entirely. A timeout or downed service = an access failure needing a retry decision. A query that succeeded and found no matches = a genuine success with an empty result. Conflating them — catching the error and returning an empty list marked "successful" — buries the failure, and the coordinator unknowingly builds an incomplete report.

نصيحةTip

اجعل كل استجابة خطأ تحمل حقلي attempted (وش جرت محاولته بالضبط) وpartialResults (وش تجمّع قبل الفشل). هذان الحقلان هما الفرق بين منسّق يقرر بذكاء ومنسّق يبدأ من الصفر.

Make every error response carry attempted (exactly what was tried) and partialResults (what accumulated before the failure). Those two fields are the difference between a coordinator that decides intelligently and one that starts from zero.

تنبيهWarning

إعادة المحاولة الآلية ليست دائمًا حسنة: على خطأ business أو permission هي هدر صريح، وعلى validation لازم تصحّح المدخل قبل الإعادة — تكرار نفس المدخل الفاسد يعطيك نفس الرفض.

Automatic retry is not always a virtue: on a business or permission error it is pure waste, and on validation you must correct the input before retrying — resubmitting the same broken input yields the same rejection.

فخ الاختبارExam trap

  • "أعِد المحاولة تلقائيًا بـ backoff ثم أرجِع status عامًا": يخفي السياق عن المنسّق ويهدر محاولات على أخطاء عمل غير قابلة للإعادة. "Auto-retry with backoff, then return a generic status": hides context from the coordinator and wastes retries on non-retryable business errors.
  • "التقط الخطأ وأرجِع نتيجة فارغة كأنها نجاح": قمع للخطأ يمنع أي تعافٍ ويخاطر بمخرجات ناقصة. فشل الوصول لا يساوي نتيجة فارغة صالحة. "Catch the error and return an empty result marked successful": suppresses the error, prevents recovery, and risks incomplete outputs. An access failure does not equal a valid empty result.
  • "مرّر الاستثناء لمعالج علوي ينهي كامل سير العمل": إنهاء غير مبرّر بينما كان ممكنًا التعافي بنتائج جزئية. "Propagate the exception to a top-level handler that terminates the whole workflow": an unnecessary termination when recovery with partial results was possible.

مثال من الحياة: فرز الطوارئ في المستشفى Real-life example: hospital emergency triage

ممرضة الفرز في الطوارئ ما تقول للطبيب "عندنا مشكلة" وتسكت — تصنّف: هذا انتظاره ينفع (عابر: راجع بعد ساعة)، وهذا تعبئته غلط (تحقّق: ارجع عبّي النموذج صح وتعال)، وهذا التأمين ما يغطيه (عمل: ما ينفع تكرر الطلب، نشرح لك البديل بلطف)، وهذا يحتاج توقيع استشاري (صلاحية: نصعّد لصاحب القرار). ولو راجَع مريض وما وُجد ملفه في النظام، فرق كبير بين "النظام طايح ما قدرنا نبحث" (فشل وصول — نعيد المحاولة) و"بحثنا والمريض فعلًا ما عنده ملف" (نتيجة فارغة صالحة — نفتح له ملفًا جديدًا). الممرضة اللي تقول "ما فيه ملف" والنظام طايح، تسبّب قرارًا طبيًا خاطئًا — وهذا بالضبط خطر وسم الفشل كنجاح.

The ER triage nurse never tells the physician "we have a problem" and stops there — she classifies: this one can safely wait (transient: come back in an hour), this one filled the form wrong (validation: redo the form correctly, then return), this one is not covered by insurance (business: resubmitting will not help, we kindly explain the alternative), and this one needs a consultant's sign-off (permission: escalate to the decision-maker). And when a patient's record cannot be found, there is a world of difference between "the system is down, we could not search" (an access failure — retry) and "we searched and the patient truly has no record" (a valid empty result — open a new file). A nurse who reports "no record" while the system is down causes a wrong medical decision — exactly the danger of marking failure as success.

في الاختبارOn the exam

سيناريوهان يتكرران: (1) أداة ترجع "Operation failed" والوكيل يتصرف غلط، (2) وكيل فرعي في نظام بحث يفشل مصدره ويرجّع فراغًا موسومًا نجاحًا. طريقة الحل:

  • الجواب الصحيح دائمًا فيه ثلاثية: تصنيف (errorCategory) + قابلية إعادة (isRetryable) + سياق (وصف/attempted/نتائج جزئية).
  • لو الخطأ مخالفة سياسة: ابحث عن retriable: false + رسالة ودّية للعميل.
  • لو السيناريو متعدد الوكلاء: تعافٍ محلي للعابر، وتصعيد ما عجز عنه فقط — مع النتائج الجزئية وما جرت محاولته.
  • استبعد فورًا: النتيجة الفارغة كنجاح، الإنهاء الكامل، الإعادة اللانهائية، والـ backoff الأعمى بلا تصنيف.

Two recurring scenarios: (1) a tool returns "Operation failed" and the agent misbehaves, (2) a research subagent's source fails and it returns emptiness marked success. How to solve:

  • The correct answer always carries the triad: classification (errorCategory) + retryability (isRetryable) + context (description / attempted / partial results).
  • If the error is a policy violation: look for retriable: false + a customer-friendly message.
  • If the scenario is multi-agent: local recovery for transient, escalate only the unresolvable — with partial results and what was attempted.
  • Eliminate on sight: empty-as-success, full termination, infinite retry, and blind backoff with no classification.
