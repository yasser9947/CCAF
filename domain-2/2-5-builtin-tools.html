الأدوات المدمجة: Grep وGlob وRead وWrite وEdit Built-in Tools: Grep, Glob, Read, Write, Edit

ليش هالموضوع مهم؟ لأن نصف أسئلته تختبر تمييزًا واحدًا بسيطًا (محتوى أم مسار؟) والنصف الثاني يختبر منهجًا كاملًا: كيف تفهم قاعدة كود ضخمة بدون ما تحرق نافذة السياق. Why it matters: half its questions test one simple distinction (content or path?) and the other half test a whole method: understanding a huge codebase without burning the context window.

وش بتتعلمWhat you'll learn

  • التمييز الحاسم: Grep يبحث في محتوى الملفات (أسماء دوال، رسائل أخطاء، imports) وGlob يطابق مسارات وأسماء الملفات (**/*.test.tsx).The decisive distinction: Grep searches file contents (function names, error messages, imports) while Glob matches file paths and names (**/*.test.tsx).
  • Read/Write لعمليات الملف الكامل، وEdit للتعديل الموجّه بمطابقة نص فريد — ولما يفشل Edit لعدم التفرّد، البديل الموثوق Read + Write.Read/Write for full-file operations, Edit for targeted changes via unique text matching — and when Edit fails on non-uniqueness, the reliable fallback is Read + Write.
  • بناء فهم قاعدة الكود تدريجيًا: Grep لنقاط الدخول ثم Read لتتبّع الـ imports — بدل قراءة كل الملفات مقدمًا.Building codebase understanding incrementally: Grep for entry points, then Read to follow imports — instead of reading all files upfront.
  • تتبّع استخدام دالة عبر وحدات التغليف (wrapper modules): احصر الأسماء المُصدَّرة أولًا ثم ابحث عن كل اسم عبر قاعدة الكود.Tracing a function's usage across wrapper modules: identify all exported names first, then search for each name across the codebase.

1 خمس أدوات، خمسة أدوار — والسؤال الفاصلFive tools, five roles — and the deciding question

أدوات Claude Code المدمجة لكل واحدة دور محدد، والخلط بينها فخ الاختبار المفضل:

  • Grep — بحث في المحتوى: يفتش داخل الملفات عن أنماط — اسم دالة، رسالة خطأ، عبارة import.
  • Glob — مطابقة مسارات: يجد الملفات بأنماط الاسم/الامتداد مثل **/*.test.tsx — ما يقرأ ولا حرف من داخلها.
  • Read — قراءة ملف كامل لفهم التدفق وتتبّع الاعتماديات.
  • Write — كتابة ملف كامل (إنشاء أو استبدال).
  • Edit — تعديل موجّه عبر مطابقة نص فريد داخل الملف.

السؤال الفاصل اللي يحل نصف أسئلة الموضوع: "وش تدوّر بالضبط؟" — تدوّر على شيء داخل الملفات؟ Grep. تدوّر على ملفات باسمها أو امتدادها؟ Glob. تحتاج المحتوى الكامل بعد ما لقيت الملف؟ Read. تبي تعدّل؟ يعتمد على تفرّد النص (القسم الجاي).

Each of Claude Code's built-in tools has a specific role, and conflating them is the exam's favorite trap:

  • Grep — content search: digs inside files for patterns — a function name, an error message, an import statement.
  • Glob — path matching: finds files by name/extension patterns like **/*.test.tsx — it reads nothing inside them.
  • Read — read a full file to understand flow and trace dependencies.
  • Write — write a full file (create or replace).
  • Edit — a targeted modification via unique text matching within the file.

The deciding question that solves half this topic's questions: "what exactly are you looking for?" — something inside files? Grep. Files by name or extension? Glob. Need the full contents once found? Read. Want to modify? Depends on text uniqueness (next section).

2 Edit والتفرّد: متى تتراجع إلى Read + WriteEdit & uniqueness: when to fall back to Read + Write

قوة Edit في دقتها: تعطيها نصًا قديمًا ونصًا جديدًا، وتستبدل الأول بالثاني. لكن شرطها الصارم أن يكون النص القديم فريدًا في الملف — لو تكرر ("String appears 4 times")، ترفض الأداة التعديل لأنها ما تعرف أي نسخة تقصد. وهنا القاعدة الرسمية: لما يفشل Edit لعدم التفرّد، البديل الموثوق هو Read + Write — اقرأ الملف كاملًا، طبّق التغيير في مكانه الصحيح وأنت شايف السياق كله، ثم اكتب الملف كاملًا.

ليش ما نكرر Edit بنص أطول؟ توسيع النص القديم ليشمل سياقًا مميِّزًا حل وارد عمليًا، لكن سؤال الاختبار يستهدف القاعدة المنصوصة: Read + Write هو الموثوق الذي لا يفشل بسبب التفرّد إطلاقًا. المشتتات المعتادة: تكرار نفس الاستدعاء (بيفشل بنفس السبب)، أو حذف الملف وإعادة إنشائه من الذاكرة (مخاطرة بفقدان محتوى ما قرأته).

Edit's power is its precision: you give it old text and new text, and it swaps one for the other. But its strict condition is that the old text be unique in the file — if it repeats ("String appears 4 times"), the tool refuses because it cannot know which occurrence you mean. Hence the official rule: when Edit fails on non-uniqueness, the reliable fallback is Read + Write — read the whole file, apply the change in the right place with full context in view, then write the whole file back.

Why not retry Edit with a longer anchor? Widening the old text to include distinguishing context can work in practice, but the exam targets the stated rule: Read + Write is the reliable path that can never fail on uniqueness. The usual distractors: repeating the same call (fails for the same reason), or deleting the file and recreating it from memory (risking loss of content you never read).

سيناريو الفشل والبديل The failure scenario and the fallback 

# Goal: change the retry limit on ONE of the identical config lines
# config.yaml contains "timeout: 30" FOUR times (4 services)

# Attempt 1 — Edit
#   old_string: "timeout: 30"  ->  new_string: "timeout: 60"
#   FAILS: "String appears 4 times in the file" (not unique)

# The RELIABLE fallback (per the exam guide):
# 1. Read  config.yaml          -> full contents in context
# 2. Apply the change at the right occurrence (you can see all 4 now)
# 3. Write config.yaml          -> rewrite the full corrected file

# Anti-patterns the exam dangles:
#   - retry the exact same Edit  (fails again, same reason)
#   - delete + recreate from memory without reading (content loss risk)
#   - Glob for the text          (Glob matches paths, never contents)

تنبيهWarning

لا تكتب ملفًا بـ Write قبل ما تقرأه بـ Read — الكتابة الكاملة تستبدل الملف كله، ولو كتبت من الذاكرة بتفقد كل شيء ما كان في ذاكرتك. لهذا البديل دائمًا ثنائي: Read + Write — بالترتيب.

Never Write a file you have not Read — a full write replaces the entire file, and writing from memory loses everything that was not in your memory. That is why the fallback is always a pair: Read + Write — in that order.

3 الاستكشاف التدريجي — وتتبّع وحدات التغليفIncremental exploration — and tracing wrapper modules

أهم مهارة في الموضوع كله: بناء فهم قاعدة الكود تدريجيًا. المضادّ الصريح: "اقرأ كل الملفات مقدمًا ثم حلّل" — يستنزف نافذة السياق قبل ما تبدأ الشغل الحقيقي. المنهج الصحيح ثلاث خطوات تتكرر: (1) Grep عن نقطة الدخول (اسم الدالة، الـ endpoint، رسالة الخطأ)، (2) Read للملف اللي طلع، (3) اتبع الـ imports اللي شفتها — كل import مهم يفتح لك Grep أو Read جديدًا. تمشي في القاعدة مثل ما تمشي في خيوط خريطة، مو مثل ما تصوّر كل صفحة في الأطلس.

ومهارة متقدمة عليها سؤال في الدليل: تتبّع دالة عبر وحدات التغليف (wrapper modules). الدالة formatCurrency قد تُعاد تسميتها وتصديرها من ملف utils/index.ts باسم fmtMoney — فلو بحثت عن الاسم الأصلي فقط، فاتك نصف المستدعين. المنهج: (1) احصر كل الأسماء المُصدَّرة (exports) من الوحدة ووحدات تغليفها، ثم (2) Grep عن كل اسم عبر قاعدة الكود — فتلقى كل المستدعين حتى المتخفين خلف إعادة التصدير.

The most important skill in the whole topic: building codebase understanding incrementally. The explicit anti-pattern: "read all files upfront, then analyze" — it exhausts the context window before real work begins. The correct method is three repeating steps: (1) Grep for the entry point (the function name, the endpoint, the error message), (2) Read the file that surfaced, (3) follow the imports you saw — each significant import opens your next Grep or Read. You walk the codebase like following threads on a map, not like photographing every page of the atlas.

And an advanced skill the guide names: tracing a function across wrapper modules. A function formatCurrency may be re-exported from utils/index.ts under the name fmtMoney — search only the original name and you miss half the callers. The method: (1) identify all exported names from the module and its wrappers, then (2) Grep for each name across the codebase — surfacing every caller, even those hiding behind re-exports.

عمليًا: الاستكشاف التدريجي وتتبّع التغليف In practice: incremental exploration & wrapper tracing 

# Q: "Find every file that CONTAINS a call to processRefund"
#    -> searching file CONTENT -> Grep
grep -rn "processRefund(" src/

# Q: "Find every TEST FILE, wherever it lives in the tree"
#    -> matching a file-NAME pattern -> Glob: **/*.test.tsx

# Incremental understanding (never read everything upfront):
grep -rn "export function createOrder" src/   # 1. entry point
# 2. Read src/orders/create.ts  -> note its imports
# 3. Follow each import with the next Grep/Read

# Tracing usage across WRAPPER modules:
# 1. list every exported name (original + re-exports)
grep -n "export" src/utils/currency.ts src/utils/index.ts
#    -> formatCurrency, fmtMoney (re-export alias)
# 2. Grep EACH exported name across the codebase
grep -rn "formatCurrency\|fmtMoney" src/
#    -> every caller found, even behind the alias

مفهوم أساسيKey concept

نافذة السياق مورد تصميمي مثل الذاكرة والوقت. "اقرأ كل شيء ثم حلّل" مو خيارًا بطيئًا فقط — هو خيار يفشل: تمتلئ النافذة بملفات لا علاقة لها قبل الوصول للمهم. التدرّج (Grep ثم Read بالتتبّع) هو الإجابة الصحيحة كل مرة يظهر فيها هذا التقابل.

The context window is a design resource like memory and time. "Read everything, then analyze" is not merely slow — it fails: the window fills with irrelevant files before reaching what matters. Incrementality (Grep, then Read along the trace) is the correct answer every time this contrast appears.

فخ الاختبارExam trap

  • استخدام Glob للبحث عن محتوى: Glob يطابق المسارات، لا النصوص داخل الملفات. "أين تُستدعى الدالة؟" جوابها Grep دائمًا. Using Glob for content search: Glob matches paths, never text inside files. "Where is the function called?" is always answered by Grep.
  • الإصرار على Edit مع نص متكرر: بيفشل كل مرة لعدم التفرّد. البديل المنصوص: Read + Write. Insisting on Edit with repeated text: it fails every time on non-uniqueness. The stated fallback: Read + Write.
  • "اقرأ كل ملفات المشروع أولًا لفهم شامل": يبدو "دقيقًا وحريصًا" لكنه استنزاف للسياق — المشتت المفضل في أسئلة الاستكشاف. التدرّج هو الصح. "Read every project file first for full understanding": sounds "thorough and careful" but exhausts context — the favorite distractor in exploration questions. Incremental is correct.
  • البحث عن الاسم الأصلي فقط عند التغليف: يفوّت المستدعين عبر أسماء إعادة التصدير. احصر الـ exports أولًا ثم Grep لكل اسم. Searching only the original name across wrappers: misses callers using re-export aliases. List the exports first, then Grep each name.

مثال من الحياة: باحث في مكتبة ضخمة Real-life example: a researcher in a huge library

باحث دخل مكتبة فيها مليون كتاب يبي يفهم موضوعًا محددًا. فهرس العناوين على الحاسوب يطلّع له الكتب باسمها وتصنيفها — هذا Glob: تلقى الكتاب بدون ما تفتحه. أما الفهرس النصّي اللي يقول "مصطلحك مذكور في صفحة كذا من كتاب كذا" فهذا Grep: بحث في المحتوى نفسه. لما يسحب كتابًا ويقرأ فصلًا كاملًا فهذا Read، ولما يحتاج يصحح سطرًا في مسودته: لو العبارة فريدة يحط ملاحظة لاصقة مكانها بالضبط (Edit)، ولو العبارة متكررة في الصفحة أربع مرات ما ينفع اللصق الأعمى — ينسخ الصفحة كاملة من جديد بالتصحيح (Read + Write). والباحث الشاطر ما "يصوّر كل رفوف المكتبة" قبل ما يبدأ — يبدأ بمدخل واحد من الفهرس، يقرأ، يتتبّع المراجع في الحواشي (الـ imports)، وينتقل خيطًا بخيط. ولو اكتشف أن المؤلف ينشر أحيانًا باسم مستعار، يحصر كل أسمائه أولًا ثم يبحث عن كل اسم — هذا تتبّع وحدات التغليف.

A researcher enters a million-book library to understand one specific topic. The title catalog on the terminal surfaces books by name and classification — that is Glob: finding the book without opening it. The full-text index that says "your term appears on page N of book X" is Grep: a search through the content itself. Pulling a book and reading a full chapter is Read. Correcting a line in his draft: if the phrase is unique, he places a sticky note exactly there (Edit); if the phrase repeats four times on the page, blind sticking will not do — he recopies the whole page with the correction (Read + Write). And a good researcher never "photographs every shelf" before starting — he begins at one catalog entry, reads, follows the footnote references (the imports), moving thread by thread. And on discovering the author sometimes publishes under a pen name, he lists all the names first, then searches each one — that is wrapper-module tracing.

في الاختبارOn the exam

أسئلة 2.5 من أسرع ما يمكن حله لو ثبّتّ التمييزات:

  • اقرأ موضوع البحث في السؤال حرفيًا: "كل الملفات اللي تحتوي..." = Grep · "كل الملفات بامتداد/باسم..." = Glob.
  • ذكر السؤال فشل Edit بعبارة مثل "appears N times"؟ الجواب الجاهز: Read + Write.
  • سيناريو "افهم قاعدة كود ضخمة غير مألوفة"؟ الصح دائمًا التدرّج: Grep نقاط الدخول ثم Read بالتتبّع — واستبعد "اقرأ كل شيء أولًا" مهما بدا حريصًا.
  • "الدالة مُعاد تصديرها بأسماء مختلفة"؟ احصر الـ exports أولًا ثم Grep كل اسم.

2.5 questions are among the fastest to solve once the distinctions are locked in:

  • Read the question's search object literally: "all files that contain..." = Grep · "all files by extension/name..." = Glob.
  • Does the question mention Edit failing with "appears N times"? The ready answer: Read + Write.
  • A "understand a large unfamiliar codebase" scenario? Incremental is always right: Grep entry points, then Read along the trace — and eliminate "read everything first" however careful it sounds.
  • "The function is re-exported under different names"? List the exports first, then Grep each name.
