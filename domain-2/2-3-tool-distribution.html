توزيع الأدوات على الوكلاء وضبط tool_choice Distributing Tools Across Agents & Configuring tool_choice

ليش هالموضوع مهم؟ لأن الوكيل اللي بيده 18 أداة يتوه، واللي بيده أداة خارج تخصصه يسيء استخدامها — والتوزيع الصح يحسم النقاش قبل ما يبدأ. Why it matters: an agent holding 18 tools gets lost, and one holding an out-of-specialization tool misuses it — the right distribution settles the debate before it starts.

وش بتتعلمWhat you'll learn

  • ليش إعطاء وكيل 18 أداة بدل 4-5 يضعف موثوقية الاختيار برفع تعقيد القرار، وليش الأدوات خارج التخصص تُساء (وكيل التوليف يسوّي بحث ويب).Why giving an agent 18 tools instead of 4-5 degrades selection reliability by raising decision complexity, and why out-of-specialization tools get misused (a synthesis agent running web searches).
  • الوصول المُنطّق: أدوات الدور فقط + أدوات مشتركة محدودة للاحتياجات عالية التردد (verify_fact)، مع توجيه المعقّد عبر المنسّق.Scoped access: role tools only + limited cross-role tools for high-frequency needs (verify_fact), routing complex cases through the coordinator.
  • استبدال الأدوات العامة ببدائل مُقيّدة: fetch_url تصير load_document تتحقق من روابط المستندات.Replacing generic tools with constrained alternatives: fetch_url becomes load_document that validates document URLs.
  • إعدادات tool_choice الثلاثة: "auto" و"any" والإجبار بالاسم — ومتى تستخدم كل واحد (إجبار extract_metadata أولًا ثم أدوار لاحقة).The three tool_choice configurations: "auto", "any", and forced by name — and when to use each (forcing extract_metadata first, then follow-up turns).

1 كثرة الأدوات تضعف الاختيارToo many tools degrade selection

المبدأ الأول في هذا الموضوع رقمي وصريح: وكيل بيده 18 أداة يواجه تعقيد قرار أعلى بكثير من وكيل بيده 4-5 أدوات مركّزة — وكل أداة إضافية تزيد احتمال الالتباس بين المتشابهات. المشكلة مو بس التوهان: الوكيل اللي يملك أدوات خارج تخصصه يميل لإساءة استخدامها. المثال الكلاسيكي من السيناريو 3: وكيل التوليف (synthesis) اللي أُعطي أدوات بحث الويب صار أحيانًا "يتحمس" ويسوّي عمليات بحث بنفسه بدل ما يولّف نتائج الوكلاء الآخرين — فتطلع استشهادات متضاربة.

لاحظ الفرق الجوهري بين هذا الموضوع والموضوع 2.1: هناك كانت المشكلة وصفًا غامضًا والعلاج تحسين الوصف؛ هنا المشكلة حيازة أدوات ما كان المفروض يملكها أصلًا والعلاج إعادة التوزيع. سؤال الاختبار الذكي يعطيك أعراضًا متشابهة (استدعاء أداة غلط) ويشوف هل تشخّص السبب صح.

The first principle here is numeric and explicit: an agent holding 18 tools faces far higher decision complexity than one holding 4-5 focused tools — every extra tool raises the odds of confusion among lookalikes. And the problem is not just getting lost: an agent holding tools outside its specialization tends to misuse them. The classic Scenario 3 example: a synthesis agent that was handed web-search tools occasionally gets "enthusiastic" and runs its own searches instead of synthesizing the other agents' findings — producing inconsistent citations.

Note the essential difference from topic 2.1: there the problem was a vague description and the fix was improving it; here the problem is holding tools it should never have had and the fix is redistribution. A clever exam question gives you similar symptoms (a wrong tool call) and checks whether you diagnose the cause correctly.

لمحة سريعةQuick insight

قلّص عدد الأدوات، ترتفع جودة الاختيار — نفس منطق 2.1 من زاوية ثانية: هناك ترفع وضوح الخيارات، وهنا تقلّل عددها. الاثنان يخدمان نفس الهدف: قرار أسهل للنموذج.

Shrink the tool count and selection quality rises — the same logic as 2.1 from another angle: there you raise the clarity of options, here you cut their number. Both serve the same goal: an easier decision for the model.

2 الوصول المُنطّق وأدوات العبور المحدودةScoped access & limited cross-role tools

العلاج اسمه الوصول المُنطّق (scoped access): كل وكيل ياخذ أدوات دوره فقط — تطبيق مباشر لمبدأ أقل صلاحية. لكن الدليل يضيف لمسة مهمة: أدوات مشتركة محدودة للاحتياجات عالية التردد. المثال الذهبي: وكيل التوليف يحتاج كثيرًا يتحقق من حقيقة بسيطة (تاريخ، اسم، رقم). لو رجع للمنسّق في كل مرة صارت عنق زجاجة؛ ولو أعطيته كل أدوات البحث كسرنا التخصص. الحل الوسط: أداة verify_fact مُنطّقة تغطي التحققات البسيطة عالية التردد، بينما تظل الحالات المعقّدة تمر عبر المنسّق.

وفي نفس الروح، استبدل الأدوات العامة ببدائل مُقيّدة: أداة fetch_url اللي تجيب أي رابط في الإنترنت أوسع من حاجة وكيل تحليل المستندات — استبدلها بـ load_document اللي تتحقق أن الرابط رابط مستند مسموح. القيد صار جزءًا من عقد الأداة نفسه، فما عاد تعتمد على "حسن نية" النموذج.

The remedy is called scoped access: each agent gets only its role's tools — a direct application of least privilege. But the guide adds an important nuance: limited cross-role tools for high-frequency needs. The golden example: the synthesis agent frequently needs to verify a simple fact (a date, a name, a number). Returning to the coordinator every time becomes a bottleneck; handing it all the search tools breaks specialization. The middle path: a scoped verify_fact tool covering the simple high-frequency checks, while complex cases still route through the coordinator.

In the same spirit, replace generic tools with constrained alternatives: a fetch_url tool that fetches anything on the internet is broader than a document-analysis agent needs — replace it with load_document, which validates that the URL is an allowed document URL. The constraint becomes part of the tool's own contract, so you no longer rely on the model's "good intentions."

استبدال أداة عامة ببديل مُقيّد Replacing a generic tool with a constrained alternative 

// BEFORE: generic and over-broad for a document-analysis agent
{ "name": "fetch_url",
  "description": "Fetches the content of any URL" }

// AFTER: constrained to the agent's actual need, with validation
{ "name": "load_document",
  "description": "Load a document for analysis from an approved document URL (PDF, DOCX, TXT under docs.company.com or the research bucket). Validates the URL points to a document before fetching; rejects non-document URLs with a validation error. NOT a general web fetcher -> web research is the research agent's job.",
  "input_schema": {
    "type": "object",
    "properties": {
      "document_url": { "type": "string", "description": "URL of an approved document source" }
    },
    "required": ["document_url"]
  } }

لاحظ كيف اجتمع الموضوعان: البديل المُقيّد (2.3) مكتوب بوصف يحمل حدودًا صريحة (2.1). Notice the two topics meeting: the constrained alternative (2.3) is written with a description carrying explicit boundaries (2.1).

نصيحةTip

قاعدة سريعة لأسئلة التوزيع: الاحتياج بسيط ومتكرر؟ أعطِ الوكيل أداة مُنطّقة له. الاحتياج معقّد أو نادر؟ وجّهه عبر المنسّق. الإجابات المتطرفة (كل الأدوات / لا أدوات) شبه دائمًا مشتتات.

A quick rule for distribution questions: is the need simple and frequent? Give the agent a scoped tool for it. Is it complex or rare? Route it through the coordinator. The extreme answers (all tools / no tools) are almost always distractors.

3 ضبط tool_choice: من يقرر ومتىConfiguring tool_choice: who decides, and when

بعد ما وزّعت الأدوات صح، يبقى سؤال الدور الواحد: هل النموذج مُلزَم باستدعاء أداة في هذا الدور؟ هذا اللي يضبطه tool_choice بثلاث درجات:

  • "auto" (الافتراضي): النموذج حر — يستدعي أداة أو يرد نصًا حواريًا.
  • "any": يضمن استدعاء أداة ما — مستحيل يرجع نصًا حواريًا — لكن النموذج يختار أيّها. مثالي لما تبي مخرجًا منظّمًا مضمونًا ونوع المستند مجهول فيختار النموذج الـ schema المناسب.
  • {"type":"tool","name":"..."} (الإجبار): يفرض أداة محددة بالاسم. النمط الرسمي: إجبار extract_metadata أولًا على كل مرفق، ثم معالجة أدوات الإثراء في أدوار لاحقة.

Once tools are distributed correctly, the single-turn question remains: is the model obligated to call a tool this turn? That is what tool_choice governs, in three grades:

  • "auto" (default): the model is free — call a tool or answer with conversational text.
  • "any": guarantees some tool gets called — conversational text is impossible — but the model picks which. Ideal when you need guaranteed structured output and the document type is unknown, so the model chooses the fitting schema.
  • {"type":"tool","name":"..."} (forced): mandates a specific named tool. The official pattern: force extract_metadata first on each attachment, then process enrichment tools in follow-up turns.

الإعدادات الثلاثة في كود Python The three configurations in Python 

import anthropic
client = anthropic.Anthropic()

# 1) "auto" — model may answer in text OR call a tool (default).
client.messages.create(
    model="claude-sonnet-4-5", max_tokens=1024, tools=tools,
    tool_choice={"type": "auto"},
    messages=[{"role": "user", "content": "Summarize this ticket."}],
)

# 2) "any" — GUARANTEE a tool call (no conversational text);
#    the model still chooses which extraction schema fits an unknown doc.
client.messages.create(
    model="claude-sonnet-4-5", max_tokens=1024, tools=extraction_tools,
    tool_choice={"type": "any"},
    messages=[{"role": "user", "content": document}],
)

# 3) Forced — run a SPECIFIC tool first (metadata before enrichment),
#    then handle the remaining steps in follow-up turns.
client.messages.create(
    model="claude-sonnet-4-5", max_tokens=1024, tools=tools,
    tool_choice={"type": "tool", "name": "extract_metadata"},

مفهوم أساسيKey concept

"any" يضمن أن أداة ستُستدعى، والإجبار بالاسم يضمن أي أداة ستُستدعى. لو السؤال يطلب "ضمان تشغيل أداة محددة أولًا"، الجواب الإجبار بالاسم — و"any" مشتت مصمّم لمن حفظ نصف القاعدة.

"any" guarantees that a tool gets called; forcing by name guarantees which tool gets called. If the question asks to "guarantee a specific tool runs first," the answer is forced-by-name — and "any" is a distractor built for whoever memorized half the rule.

تنبيهWarning

tool_choice يشتغل في دور واحد. فرض تسلسل حتمي عبر عدة خطوات (تحقق قبل استرجاع مثلًا) يحتاج إنفاذًا برمجيًا (hook / بوابة مسبقة) — ذاك موضوع الدومين 1، لكنه يظهر هنا كمشتت. لا تخلط "توفّر الأداة في دور" مع "ترتيب الأدوات عبر الأدوار".

tool_choice operates within a single turn. Enforcing a deterministic sequence across steps (verify-before-refund, say) needs programmatic enforcement (a hook / prerequisite gate) — that is Domain 1 material, but it appears here as a distractor. Never conflate "tool availability in a turn" with "tool ordering across turns."

فخ الاختبارExam trap

  • "أعطِ وكيل التوليف كل أدوات البحث ليتعامل مع أي تحقق": إفراط في الصلاحيات يكسر فصل المسؤوليات. الصح: verify_fact مُنطّقة للبسيط المتكرر فقط. "Give the synthesis agent all web-search tools so it can handle any verification": over-provisioning that breaks separation of concerns. Right answer: a scoped verify_fact for the simple frequent cases only.
  • "اجمع كل احتياجات التحقق وأرسلها دفعة للمنسّق في النهاية": يخلق تبعيات حاجبة لأن خطوات التوليف تعتمد على حقائق مُتحقَّقة أثناء الشغل. "Batch all verification needs and send them to the coordinator at the end": creates blocking dependencies since synthesis steps depend on facts verified mid-work.
  • خلط "any" بالإجبار المحدد: "any" يضمن أداةً ما، لا أداة بعينها. تبي أداة معينة أولًا؟ الإجبار بالاسم. Confusing "any" with forced selection: "any" guarantees some tool, not a particular one. Need a specific tool first? Force it by name.

مثال من الحياة: محطات مطبخ المطعم Real-life example: restaurant kitchen stations

مطبخ مطعم محترف مقسّم محطات: الشوّاية، السلطات، الحلويات. كل محطة عندها عدّتها فقط — طباخ الشوّاية ما يلقى قدّامه 18 سكينًا لكل الأغراض، بل 4-5 أدوات تخصّه، فيمسك الصح بلا تفكير (التوزيع المُنطّق). طباخ الحلويات يحتاج أحيانًا رشّة ملح — بدل ما يمشي لمخزن التوابل المركزي كل مرة، عنده ملّاحة صغيرة في محطته (أداة العبور المُنطّقة verify_fact)، أما طلبية التوابل الكبيرة فتمر عبر الشيف التنفيذي (المنسّق). ولما يصيح الشيف "كل واحد يمسك أداة الحين!" فهذا "any" — لازم تمسك شيئًا لكن تختاره أنت؛ ولما يقول "أنت بالذات، امسك سكين الفيليه أولًا" فهذا الإجبار بالاسم. وسكين اللحم النيء المخصّصة (بدل سكين عامة لكل شيء) هي load_document بدل fetch_url — أداة مقيّدة بغرضها تمنع التلوث قبل حدوثه.

A professional kitchen is split into stations: grill, salads, pastry. Each station holds only its own kit — the grill cook does not face 18 all-purpose knives, but the 4-5 tools of his craft, so he grabs the right one without thinking (scoped distribution). The pastry cook occasionally needs a pinch of salt — rather than walking to the central spice store every time, she keeps a small salt shaker at her station (the scoped cross-role tool, verify_fact), while a full spice order still goes through the executive chef (the coordinator). When the chef shouts "everyone grab a utensil now!" that is "any" — you must hold something, but you choose what; when he says "you specifically, take the filleting knife first," that is forced-by-name. And the dedicated raw-meat knife (instead of one universal knife) is load_document replacing fetch_url — a purpose-constrained tool that prevents contamination before it can happen.

في الاختبارOn the exam

نمطان يتكرران: (1) وكيل يسيء استخدام أدوات خارج تخصصه، (2) مطلوب ضمان استدعاء أداة (ما / محددة). طريقة الحل:

  • مشكلة سوء استخدام؟ الجواب الصحيح يجمع: قصّ الأدوات على الدور + أداة عبور مُنطّقة للاحتياج البسيط المتكرر + توجيه المعقّد للمنسّق.
  • "يضمن استدعاء أداة" = "any" · "يضمن أداة محددة أولًا" = الإجبار بالاسم · "قد يرد نصًا" = "auto".
  • تعليمات الـ prompt ("ابدأ دائمًا بالميتاداتا") احتمالية — لا تضمن؛ الضمان الحتمي من tool_choice.
  • ترتيب عبر خطوات متعددة؟ هذا hook (دومين 1) — استبعد إجابات tool_choice.

Two recurring patterns: (1) an agent misusing out-of-specialization tools, (2) needing to guarantee a tool call (some / specific). How to solve:

  • A misuse problem? The correct answer combines: scope tools to the role + a scoped cross-role tool for the simple frequent need + routing complex cases through the coordinator.
  • "Guarantees a tool call" = "any" · "guarantees a specific tool first" = forced-by-name · "may answer in text" = "auto".
  • Prompt instructions ("always start with metadata") are probabilistic — no guarantee; the deterministic guarantee comes from tool_choice.
  • Ordering across multiple steps? That is a hook (Domain 1) — eliminate the tool_choice answers.

Per the guide's principle, what is the right move?

صحيح. المشكلة هنا حجم الطقم نفسه (18 مقابل 4-5) — التقليص حسب الدور هو العلاج المباشر لتعقيد القرار. "any" يجبر استدعاءً لكنه لا يحسّن الاختيار، وتطويل 18 وصفًا يحسّن الوضوح لكن يُبقي التعقيد العددي، والنموذج المراجع طبقة زائدة مكلفة. Correct. The problem here is the set size itself (18 vs 4-5) — cutting to the role is the direct fix for decision complexity. "any" forces a call without improving selection, lengthening 18 descriptions improves clarity but keeps the numeric complexity, and a reviewer model is an expensive extra layer.
غير دقيق. الإجابة الصحيحة: تقليص الطقم إلى 4-5 أدوات الدور. لما يذكر السؤال عددًا كبيرًا من الأدوات صراحة، فالسبب الجذري هو الحجم — مو الوصف ولا الإجبار. Not quite. The correct answer is cutting the set to the role's 4-5 tools. When the question explicitly cites a large tool count, the root cause is the size — not descriptions, not forcing.

خلاصةTakeaway

  • 18 أداة تضعف الاختيار مقابل 4-5 مركّزة؛ والأدوات خارج التخصص تُساء (وكيل توليف يسوّي بحث ويب).18 tools degrade selection versus 4-5 focused ones; out-of-specialization tools get misused (a synthesis agent running web searches).
  • وصول مُنطّق = أدوات الدور فقط + أداة عبور محدودة (verify_fact) للبسيط المتكرر، والمعقّد عبر المنسّق.Scoped access = role tools only + a limited cross-role tool (verify_fact) for the simple and frequent, with complex cases via the coordinator.
  • استبدل العام بالمُقيّد: fetch_url تصير load_document المتحقِّقة — القيد في عقد الأداة لا في النوايا.Replace generic with constrained: fetch_url becomes the validating load_document — the constraint lives in the tool contract, not in intentions.
  • auto = حر · any = أداة ما مضمونة · الإجبار بالاسم = أداة محددة أولًا ثم أدوار لاحقة.auto = free · any = some tool guaranteed · forced-by-name = a specific tool first, then follow-up turns.
  • tool_choice لدور واحد؛ التسلسل عبر الخطوات إنفاذ برمجي (hooks — دومين 1).tool_choice is single-turn; cross-step sequencing is programmatic enforcement (hooks — Domain 1).
