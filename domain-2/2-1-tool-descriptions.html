2.1

تصميم واجهات الأدوات: الأوصاف والحدود Tool Interfaces: Descriptions & Boundaries

ليش هالموضوع مهم؟ لأن النموذج ما يختار الأداة بالاسم ولا بالحظ — يختارها بالوصف. وصف ناقص يعني توجيه غلط، مهما كانت معماريتك ذكية. Why it matters: the model does not pick a tool by its name or by luck — it picks by the description. A thin description means misrouting, no matter how clever your architecture is.

1 الوصف هو آلية الاختيار — مو الاسمThe description is the selection mechanism — not the name

لما يوصل طلب المستخدم، النموذج يقرأ أوصاف كل الأدوات المتاحة ويقارنها بنيّة الطلب، ثم يختار. هذي هي اللحظة الحاسمة: وصف الأداة (description) هو الآلية الأساسية اللي يعتمد عليها النموذج. الاسم لوحده إشارة ضعيفة، والـ system prompt يوجّه السلوك العام لكنه ما يفرّق بين أداتين متشابهتين.

النتيجة المنطقية: الأوصاف المختصرة تنتج اختيارًا غير موثوق بين الأدوات المتشابهة. لو عندك search_code وfind_files وكل وحدة وصفها "Searches the repository"، النموذج ما عنده أي معلومة يفرّق فيها — فيتخبط. وهذا اللي يسمّيه دليل الاختبار سوء التوجيه (misrouting): استدعاء الأداة الغلط لأن وصفين متقاربين مثل analyze_content وanalyze_document ما يرسمان حدًا واضحًا بينهما.

When a user request arrives, the model reads the descriptions of every available tool, compares them against the request's intent, then selects. This is the decisive moment: the tool description is the primary mechanism the model relies on. The name alone is a weak signal, and the system prompt steers general behavior but cannot differentiate two similar tools.

The logical consequence: minimal descriptions produce unreliable selection among similar tools. If you have search_code and find_files both described as "Searches the repository," the model has no information to differentiate with — so it guesses. That is what the exam guide calls misrouting: calling the wrong tool because two near-identical descriptions like analyze_content and analyze_document draw no clear boundary between themselves.

MISROUTING

القرار كله يتوقف على سؤال واحد: هل الأوصاف ترسم حدودًا واضحة؟ لو لا، الاختيار يصير تخمينًا. The whole decision hinges on one question: do the descriptions draw clear boundaries? If not, selection becomes a guess.

لمحة سريعةQuick insight

النموذج يقرأ الأوصاف في كل دور من جديد — ما يتذكر "المرة الماضية اخترت صح". يعني الوصف الجيد استثمار يشتغل لك في كل استدعاء.

The model reads the descriptions fresh every turn — it does not remember "I picked correctly last time." A good description is an investment that works for you on every single call.

2 تشريح الوصف القوي: أربعة مكوناتAnatomy of a strong description: four components

الوصف القوي يجاوب على أربعة أسئلة قبل ما يسألها النموذج:

  1. صيغ المدخلات (input formats): وش شكل المدخل المقبول بالضبط؟ (مثال: رقم طلب بصيغة ORD-#####)
  2. أمثلة استعلامات (example queries): وش الطلبات اللي تناسب هذي الأداة؟ ("check my order #12345")
  3. الحالات الحدّية (edge cases): وش يصير لو الطلب ما وُجد؟ لو المدخل ناقص؟
  4. الحدود (boundaries): متى لا تستخدم هذي الأداة، وأي أداة تستخدم بدلها؟ ("NOT for customer lookup — use get_customer")

المكوّن الرابع هو الأهم والأكثر إهمالًا: الحد الصريح مقابل الأداة الجارة هو اللي يقطع سوء التوجيه من جذره.

A strong description answers four questions before the model has to ask them:

  1. Input formats: what exactly does an acceptable input look like? (e.g. an order number in the ORD-##### format)
  2. Example queries: which requests fit this tool? ("check my order #12345")
  3. Edge cases: what happens when the order does not exist? When the input is incomplete?
  4. Boundaries: when should this tool not be used, and which tool should be used instead? ("NOT for customer lookup — use get_customer")

The fourth component is the most important and the most neglected: the explicit boundary against the neighboring tool is what cuts misrouting at the root.

نفس الأداة، نفس الاسم — الفرق الوحيد كثافة المعلومات في الوصف، وهو الفرق بين تخمين وقرار. Same tool, same name — the only difference is information density in the description, and that is the difference between a guess and a decision.

الوصف القوي كاملًا (JSON) The full strong description (JSON) 

{
  "name": "lookup_order",
  "description": "Retrieve a single order by its order number (format: ORD-#####, e.g. 'ORD-12345'). Use for order-scoped queries: status, items, refund eligibility, shipping. Example queries: 'check my order #12345', 'is order ORD-88 delivered?'. NOT for looking up a customer by name or email -> use get_customer for that. Returns 'not_found' (valid empty result) when the order number does not exist.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_number": {
        "type": "string",
        "description": "Order number, format ORD-#####"
      }
    },
    "required": ["order_number"]
  }
}

لاحظ: حتى وصف المعامل داخل input_schema يعيد ذكر الصيغة — كل طبقة توثيق تخدم الاختيار. Note: even the parameter description inside input_schema restates the format — every documentation layer serves selection.

مفهوم أساسيKey concept

لما سؤال يصف "أدوات متشابهة بأوصاف مختصرة والنموذج يخلط بينها"، أول علاج دائمًا هو توسيع الأوصاف — مو طبقة توجيه، مو دمج الأدوات، مو أمثلة few-shot. توسيع الوصف يعالج السبب الجذري بأقل جهد وأعلى رافعة.

When a question describes "similar tools with minimal descriptions that the model confuses," the first fix is always to expand the descriptions — not a routing layer, not tool consolidation, not few-shot examples. Expanding the description addresses the root cause with the least effort and the highest leverage.

نصيحةTip

اكتب الوصف كأنك تشرح لموظف جديد أول يوم له: وش تسوي الأداة، وش تعطيها، وش ترجّع لك، ومتى تروح للأداة الثانية بدلها. لو موظف جديد بيفهمها، النموذج بيفهمها.

Write the description as if onboarding a new hire on day one: what the tool does, what you feed it, what it returns, and when to go to the other tool instead. If a new hire would get it, the model will get it.

3 سلّم العلاج: وسّع، أعد التسمية، قسّمThe fix ladder: expand, rename, split

لما تكتشف سوء توجيه، عندك ثلاث درجات علاج مرتّبة حسب الجهد. تبدأ بالأرخص، وتصعد فقط لو التداخل أعمق من مجرد وصف:

  • الدرجة 1 — وسّع الوصف: أضف صيغ المدخلات، أمثلة، حالات حدّية، وحدودًا. علاج معظم الحالات.
  • الدرجة 2 — أعد التسمية + حدّث الوصف: لو الاسم نفسه مضلّل ويتداخل وظيفيًا مع أداة ثانية. مثال الدليل: analyze_content تصير extract_web_results بوصف خاص بنتائج الويب — فينزاح التداخل مع analyze_document.
  • الدرجة 3 — قسّم الأداة العامة: لو أداة واحدة تسوّي أعمالًا مختلفة جوهريًا، قسّمها إلى أدوات محددة الغرض بعقود مدخلات/مخرجات معرّفة: analyze_document تتفكك إلى extract_data_points وsummarize_content وverify_claim_against_source.

When you discover misrouting, you have three escalating fixes ordered by effort. Start with the cheapest, and climb only if the overlap runs deeper than the description:

  • Rung 1 — expand the description: add input formats, examples, edge cases, and boundaries. Fixes most cases.
  • Rung 2 — rename + update the description: when the name itself misleads and functionally overlaps another tool. The guide's example: analyze_content becomes extract_web_results with a web-specific description — dissolving the overlap with analyze_document.
  • Rung 3 — split the generic tool: when one tool performs fundamentally different jobs, split it into purpose-specific tools with defined input/output contracts: analyze_document decomposes into extract_data_points, summarize_content, and verify_claim_against_source.

Rungs 2 and 3 are correct when the question states real functional overlap or fundamentally different jobs.

الدرجة 3 عمليًا: تقسيم أداة عامة Rung 3 in practice: splitting a generic tool 

// BEFORE: one vague tool doing three unrelated jobs
{ "name": "analyze_document", "description": "Analyzes a document" }

// AFTER: three tools, each with a defined input/output contract
[
  { "name": "extract_data_points",
    "description": "Extract structured numeric/tabular fields (amounts, dates, IDs) from a document. Returns a JSON object of typed fields; null when a field is absent." },
  { "name": "summarize_content",
    "description": "Produce a 3-5 sentence abstractive summary of a document's main points. Returns prose text; no numbers are computed." },
  { "name": "verify_claim_against_source",
    "description": "Check whether a specific claim is supported by a given source document. Returns { supported: bool, evidence_excerpt, confidence }." }
]

آخر قطعة في الموضوع، وأكثرها مكرًا: حتى مع أوصاف ممتازة، صياغة الـ system prompt حسّاسة للكلمات المفتاحية. تعليمة بريئة مثل "Always document your findings" فيها كلمة "document" — وقد تخلق ارتباطًا غير مقصود يسحب النموذج نحو أداة analyze_document في طلبات ما لها علاقة بالمستندات، متجاوزةً أوصاف الأدوات المكتوبة بعناية. لذلك من مهارات الدليل: راجع الـ system prompt بحثًا عن تعليمات حسّاسة للكلمات قد تتغلب على الأوصاف.

The final and sneakiest piece: even with excellent descriptions, system prompt wording is keyword-sensitive. An innocent instruction like "Always document your findings" contains the word "document" — and can create an unintended association that pulls the model toward analyze_document on requests that have nothing to do with documents, overriding well-written tool descriptions. Hence the guide's skill: review the system prompt for keyword-sensitive instructions that might override the descriptions.

مراجعة system prompt من الكلمات الحسّاسة Reviewing a system prompt for keyword sensitivity 

# RISKY system prompt (keyword pulls toward analyze_document)
"You are a research assistant. Always document your findings
 thoroughly and analyze content carefully."
  ^ "document" + "analyze content" = unintended tool associations

# SAFER wording (behavior stated without tool-name collisions)
"You are a research assistant. Record your findings thoroughly
 and examine sources carefully."

تنبيهWarning

لو وسّعت الأوصاف وما زال التوجيه غلط، لا تقفز مباشرة للحلول الثقيلة — افحص الـ system prompt أولًا. كلمة وحدة متصادمة مع اسم أداة تقدر تهدم أفضل أوصافك.

If you expanded the descriptions and routing is still wrong, do not jump to heavy solutions — inspect the system prompt first. A single word colliding with a tool name can defeat your best descriptions.

فخ الاختبارExam trap

  • فخ الـ few-shot: "أضف 5-8 أمثلة في الـ system prompt" يبدو معقولًا لكنه يزيد التوكنز بدون علاج السبب — الوصف الناقص. الوصف أولًا. The few-shot trap: "add 5-8 examples to the system prompt" sounds reasonable but adds token overhead without fixing the root cause — the thin description. Description first.
  • فخ طبقة التوجيه: "طبقة تحلّل المدخل وتختار الأداة بالكلمات المفتاحية" هندسة زائدة تتجاوز فهم اللغة الطبيعي عند النموذج. The routing-layer trap: "a layer that parses input and pre-selects the tool by keywords" is over-engineered and bypasses the model's natural-language understanding.
  • فخ الدمج: "ادمج الأداتين في أداة وحدة" خيار معماري صحيح أحيانًا، لكنه جهد أكبر من "خطوة أولى" لما تكون المشكلة مجرد أوصاف ضعيفة. The consolidation trap: "merge both into one tool" is sometimes a valid architectural choice, but it is more effort than a "first step" warrants when the real problem is just weak descriptions.

مثال من الحياة: صيدلية المستشفى Real-life example: the hospital pharmacy

تخيّل صيدلية مستشفى فيها دواءان علبتاهما متشابهتان، ومكتوب على كل وحدة "مسكّن ألم" وبس. الصيدلي الجديد بيمسك العلبة الغلط عاجلًا أم آجلًا — مو لأنه مهمل، لأن الملصق ما يعطيه معلومة يفرّق فيها. الملصق الصحيح يذكر: التركيز والجرعة (صيغة المدخل)، الحالات اللي يوصف لها (أمثلة الاستعلامات)، تحذيرات الاستخدام (الحالات الحدّية)، والأهم: "غير مناسب لمرضى الضغط — استخدم البديل X" (الحدود مقابل الأداة المشابهة). ولو علّقت في الصيدلية لوحة تقول "اصرف المسكّن بسرعة لكل مراجع"، صارت اللوحة نفسها تسحب الصيدلي نحو دواء معيّن حتى لو ملصقه ما ينطبق — هذي بالضبط حساسية الـ system prompt للكلمات المفتاحية.

Picture a hospital pharmacy with two near-identical medicine boxes, each labeled only "pain reliever." Sooner or later the new pharmacist grabs the wrong one — not from carelessness, but because the label gives nothing to differentiate with. A proper label states: concentration and dosage (input format), the conditions it treats (example queries), usage warnings (edge cases), and most importantly: "not for hypertensive patients — use alternative X" (the boundary against the similar tool). And if the pharmacy hangs a sign saying "dispense the pain reliever quickly for every visitor," the sign itself now pulls the pharmacist toward one specific medicine even when its label does not apply — that is exactly system-prompt keyword sensitivity.

في الاختبارOn the exam

السؤال النموذجي: نظام فيه أداتان متشابهتان، النموذج ينادي الغلط، ويسألك عن "أفضل خطوة أولى" أو "الإصلاح الجذري". طريقة الحل:

  • ابحث عن الخيار اللي يلمس الوصف نفسه (توسيع/توضيح حدود) — هذا الجواب في 90% من الصيغ.
  • استبعد فورًا: طبقة توجيه بالكلمات المفتاحية، حزم few-shot، الدمج "عشان يرتاح النموذج من الاختيار"، ورفع max_tokens.
  • لو السؤال يذكر أن الاسم نفسه مضلّل أو الأعمال مختلفة جوهريًا — اصعد درجة: أعد التسمية أو قسّم.
  • لو الأوصاف ممتازة والتوجيه لسه غلط والسؤال يذكر تعليمة في الـ system prompt — الجواب مراجعة صياغة الـ prompt من الكلمات الحسّاسة.

The typical question: a system with two similar tools, the model calls the wrong one, and you are asked for the "best first step" or the "root-cause fix." How to solve it:

  • Look for the option that touches the description itself (expanding / clarifying boundaries) — that is the answer in 90% of phrasings.
  • Eliminate immediately: keyword routing layers, few-shot bundles, merging "to spare the model the choice," and raising max_tokens.
  • If the question states the name itself misleads or the jobs are fundamentally different — climb a rung: rename or split.
  • If descriptions are excellent, routing is still wrong, and the question mentions a system-prompt instruction — the answer is reviewing the prompt wording for keyword sensitivity.

  • الوصف هو الآلية الأساسية لاختيار الأداة — وصف ناقص = اختيار غير موثوق بين الأدوات المتشابهة.The description is the primary mechanism of tool selection — a thin description = unreliable selection among similar tools.
  • الوصف القوي = صيغ مدخلات + أمثلة استعلامات + حالات حدّية + حدود مقابل الأداة المشابهة.A strong description = input formats + example queries + edge cases + boundaries versus the similar tool.
  • سلّم العلاج: وسّع الوصف (أولًا دائمًا) ← أعد التسمية (analyze_content → extract_web_results) ← قسّم (analyze_document إلى 3 أدوات).The fix ladder: expand the description (always first) — rename (analyze_content → extract_web_results) — split (analyze_document into 3 tools).
  • الـ system prompt حسّاس للكلمات المفتاحية — كلمة متصادمة مع اسم أداة تتجاوز أفضل الأوصاف؛ راجعه.The system prompt is keyword-sensitive — a word colliding with a tool name overrides the best descriptions; review it.
  • مشتتات ثابتة تستبعدها: طبقة توجيه، few-shot، دمج الأدوات، رفع max_tokens.Fixed distractors to eliminate: routing layers, few-shot, tool merging, raising max_tokens.
