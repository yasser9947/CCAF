2.4

دمج خوادم MCP في Claude Code وسير عمل الوكلاء Integrating MCP Servers into Claude Code & Agent Workflows

ليش هالموضوع مهم؟ لأن قرارين صغيرين — وين تحط ملف الإعداد، وكيف تمرر التوكن — يفصلان بين فريق كامل يشتغل من أول استنساخ، وسرّ مُسرّب في تاريخ Git للأبد. Why it matters: two small decisions — where the config file lives, and how the token gets passed — separate a whole team working from first clone, and a secret leaked into Git history forever.

  • نطاقا خوادم MCP: مستوى المشروع (.mcp.json) لعدّة الفريق المشتركة، ومستوى المستخدم (~/.claude.json) للخوادم الشخصية والتجريبية.The two MCP server scopes: project level (.mcp.json) for shared team tooling, and user level (~/.claude.json) for personal/experimental servers.
  • توسيع متغيرات البيئة (${GITHUB_TOKEN}) داخل .mcp.json لإدارة الاعتمادات بدون إيداع أي سر في المستودع.Environment-variable expansion (${GITHUB_TOKEN}) inside .mcp.json for credential management without committing any secret.
  • أن أدوات كل الخوادم المُعدّة تُكتشف وقت الاتصال وتتاح للوكيل في آنٍ واحد — وليش تجويد أوصاف أدوات MCP يمنع تفضيل Grep المدمجة عليها.That tools from all configured servers are discovered at connection time and available simultaneously — and why enhancing MCP tool descriptions stops the agent preferring built-in Grep over them.

1 النطاق أولًا: مشروع أم مستخدم؟Scope first: project or user?

أول قرار عند دمج خادم MCP هو نطاقه. القاعدة بسيطة: عدّة الفريق المشتركة توضع في .mcp.json على مستوى المشروع — الملف يُدار بالإصدار (version-controlled)، فيوصل الخادم لكل من يستنسخ المستودع تلقائيًا. أما خوادمك الشخصية والتجريبية فمكانها ~/.claude.json على مستوى المستخدم — تشتغل لك في كل مشاريعك، وما تُشارك مع أحد ولا تلوّث مستودع الفريق بتجاربك.

وثاني قرار: كيف تمرّر الاعتمادات (credentials)؟ الجواب: توسيع متغيرات البيئة داخل .mcp.json — تكتب ${GITHUB_TOKEN} بدل التوكن نفسه، والقيمة تُقرأ من بيئة كل مطوّر وقت التشغيل. النتيجة: ملف الإعداد يُشارك بأمان مع الفريق كله، وصفر أسرار في المستودع.

The first decision when integrating an MCP server is its scope. The rule is simple: shared team tooling goes in a project-level .mcp.json — the file is version-controlled, so the server reaches everyone who clones the repo automatically. Your personal and experimental servers belong in the user-level ~/.claude.json — they work for you across all your projects, are shared with no one, and never pollute the team repo with your experiments.

The second decision: how do credentials get passed? Answer: environment-variable expansion inside .mcp.json — you write ${GITHUB_TOKEN} instead of the token itself, and the value is read from each developer's environment at runtime. The result: the config file is safely shared with the whole team, and zero secrets live in the repo.

ملف .mcp.json بنطاق المشروع مع توسيع متغيرات البيئة A project-scoped .mcp.json with env-var expansion 

// .mcp.json  (committed to the repo, shared with the whole team)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        // Expanded from each developer's shell at runtime.
        // No secret is ever committed to version control.
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "jira": {
      // Prefer a community server for standard integrations.
      "command": "npx",
      "args": ["-y", "@company/mcp-jira"],
      "env": { "JIRA_API_TOKEN": "${JIRA_TOKEN}" }
    }
  }
}

فخ الاختبارExam trap

  • "أودِع التوكن في .mcp.json ليصل للفريق تلقائيًا": يبدو "عمليًا" لكنه تسريب سر في تاريخ Git. الصح دائمًا: توسيع ${VAR} من بيئة كل مطوّر. "Commit the token into .mcp.json so the team gets it automatically": sounds "practical" but leaks a secret into Git history. Always correct: ${VAR} expansion from each developer's environment.
  • "حط خادم الفريق في ~/.claude.json عند كل مطوّر يدويًا": يعمل نظريًا لكنه يفقد مزامنة الفريق — أي تحديث للخادم يتطلب تعديل كل جهاز يدويًا. نطاق المشروع وُجد بالضبط لهذا. "Put the team server in every developer's ~/.claude.json manually": technically works but loses team sync — any server update means touching every machine by hand. Project scope exists precisely for this.

2 الاكتشاف وقت الاتصال — وليش الوكيل يفضّل Grep أحيانًاDiscovery at connection time — and why the agent sometimes prefers Grep

حقيقة يحب الاختبار يتأكد أنك تعرفها: أدوات كل الخوادم المُعدّة تُكتشف وقت الاتصال، وتصير متاحة للوكيل كلها في آنٍ واحد. ما فيه "تفعيل يدوي" لكل خادم، وما فيه ترتيب أولوية بين خادم المشروع وخادم المستخدم — الكل ينضم لنفس قائمة الأدوات.

وهنا تظهر مشكلة شائعة: أدوات MCP تدخل نفس ساحة الاختيار مع الأدوات المدمجة، والنموذج يختار — كالعادة — بالوصف (رجعنا لمنطق 2.1). فلو كان وصف أداة MCP القوية مقتضبًا ("Searches code")، بيفضّل الوكيل أداة مدمجة يعرفها زي Grep على أداة الخادم الأقدر. العلاج من الدليل حرفيًا: جوّد وصف أداة MCP — فصّل قدراتها ومخرجاتها (بحث دلالي؟ يفهم بنية الكود؟ يرجّع مقاطع مرتبة بالصلة؟) حتى يعرف النموذج ليش يفضّلها. حذف Grep علاج عرَضي مرفوض.

وقاعدة البناء مقابل الشراء: اختر خوادم المجتمع الجاهزة للتكاملات القياسية (Jira، GitHub، Slack...) واحتفظ بجهد الخوادم المخصّصة لسير العمل الخاص بفريقك فعلًا. بناء خادم Jira من الصفر إعادة اختراع عجلة مصانة مجانًا.

A fact the exam loves to confirm you know: tools from all configured servers are discovered at connection time and become available to the agent simultaneously. There is no "manual activation" per server, and no priority ordering between project and user servers — everything joins the same tool list.

Which surfaces a common problem: MCP tools enter the same selection arena as the built-in tools, and the model chooses — as always — by description (back to 2.1's logic). If the powerful MCP tool's description is terse ("Searches code"), the agent will prefer a familiar built-in like Grep over the more capable server tool. The guide's remedy, verbatim: enhance the MCP tool's description — detail its capabilities and outputs (semantic search? understands code structure? returns relevance-ranked snippets?) so the model knows why to prefer it. Deleting Grep is a rejected symptom-level fix.

And the build-vs-buy rule: choose existing community servers for standard integrations (Jira, GitHub, Slack...), reserving custom-server effort for genuinely team-specific workflows. Building a Jira server from scratch reinvents a freely maintained wheel.

Notice how half of 2.4's problems trace back to lesson 2.1? An MCP tool with a neglected description loses to Grep for the same reason any vaguely described tool loses. The whole domain is one lesson recurring in different outfits.

تجويد وصف أداة MCP لتكسب المنافسة Enhancing an MCP tool description to win the competition 

// BEFORE: terse — the agent keeps picking built-in Grep instead
{ "name": "search_code",
  "description": "Searches code" }

// AFTER: capabilities + outputs detailed — now the agent knows
// exactly when this beats a plain text search
{ "name": "search_code",
  "description": "Semantic code search across the indexed GitHub org. Understands code structure: find definitions, references, and usages by symbol name even across renames and re-exports. Returns relevance-ranked snippets with file path, line numbers, and surrounding context. Prefer this over plain text search (Grep) when the query is about code MEANING (e.g. 'where is auth handled?'); use Grep for exact literal string matches." }

3 الموارد: كتالوجات تُغني عن الاستكشافResources: catalogs that replace exploration

MCP ما يقدّم أدوات فقط — يقدّم موارد (resources): محتوى يُعرض للوكيل مباشرة بدون استدعاء أداة. استخدامها الذكي: كتالوجات المحتوى. ملخصات التذاكر، تسلسل صفحات التوثيق، مخطط قاعدة البيانات (schemas) — لو ما كانت معروضة كموارد، بيحرق الوكيل استدعاءات أدوات استكشافية فقط ليعرف "وش الموجود أصلًا؟". المورد يعطيه الخريطة مقدمًا، فيصير كل استدعاء أداة بعدها موجّهًا نحو هدف معروف.

MCP does not only offer tools — it offers resources: content exposed to the agent directly, no tool call needed. Their smart use: content catalogs. Issue summaries, documentation hierarchies, database schemas — if these are not exposed as resources, the agent burns exploratory tool calls just to learn "what even exists?". A resource hands it the map upfront, so every subsequent tool call is aimed at a known target.

مخطط مقارنة: بدون موارد مقابل بموارد Comparison: without resources vs with resources

WITHOUT resources — blind exploration

call 1: list_tables() -> 42 tables

call 2: describe_table("users")

call 3: describe_table("orders")

call 4: describe_table("order_items")

call 5: describe_table("payments")...

5+ exploratory calls burned before the real question is even asked

WITH resources — the map is upfront

resource: db://schema (visible from the start)

users(id, email...) · orders(id, user_id, status...) · payments(id, order_id, amount...)

call 1: query("SELECT ... JOIN ...")

one aimed call — the schema catalog eliminated the exploration phase

المورد يجاوب "وش المتاح؟" قبل ما يُسأل — والأداة تتفرغ للفعل نفسه. The resource answers "what is available?" before it is asked — leaving tools free for the action itself.

مفهوم أساسيKey concept

الموارد للكتالوجات، والأدوات للأفعال. لو لاحظت وكيلًا يهدر استدعاءات ليكتشف "وش الموجود" (تذاكر؟ جداول؟ صفحات توثيق؟)، فالإجابة الصحيحة في الاختبار: اعرض الكتالوج كمورد MCP — مو "أضف أداة list أخرى" ولا "خلّه يستكشف".

Resources for catalogs, tools for actions. If you spot an agent wasting calls discovering "what exists" (issues? tables? doc pages?), the correct exam answer is: expose the catalog as an MCP resource — not "add another list tool" and not "let it explore."

تنبيهWarning

قبل ما تكتب سطر كود لخادم مخصّص، اسأل: "هل تكاملي قياسي؟" Jira وGitHub وSlack وأشباهها لها خوادم مجتمع مصانة. الخادم المخصّص استثمار مبرر فقط لسير عمل يخص فريقك فعلًا — وهذا تمييز يظهر في الاختبار.

Before writing a line of custom-server code, ask: "is my integration standard?" Jira, GitHub, Slack and their kin have maintained community servers. A custom server is justified investment only for genuinely team-specific workflows — a distinction the exam does test.

مثال من الحياة: مبنى شركة وخدماته Real-life example: an office building and its services

تخيّل مبنى شركتك: الخدمات المسجّلة في استقبال المبنى (قاعات الاجتماعات، البريد، الطابعات المركزية) متاحة لكل موظف من أول يوم — هذا نطاق المشروع .mcp.json. أما اشتراكاتك الشخصية (تطبيق القهوة اللي تحبه، نادي الرياضة) فتخصّك وحدك ولا تظهر في دليل الشركة — هذا ~/.claude.json. ودخولك للخدمات يكون ببطاقتك أنت (بصلاحياتك من بيئتك) — الاستقبال ما يعلّق كلمة مرور موحّدة على الجدار للجميع، وهذا بالضبط توسيع ${VAR} بدل إيداع التوكن. وأول ما تدخل المبنى تلقى لوحة الدليل في البهو: كل الطوابق والخدمات معروضة قدامك بلا ما تطرق كل باب تسأل "وش عندكم؟" — هذي هي الموارد ككتالوج. وأخيرًا: الشركة ما تبني مصعدًا من الصفر — تشتري مصعدًا قياسيًا مصانًا من مصنع معروف (خادم المجتمع)، وتفصّل فقط ديكور المدخل اللي يعبّر عن هويتها (الخادم المخصّص).

Picture your company's building: services registered at the building reception (meeting rooms, mail, central printers) are available to every employee from day one — that is project scope, .mcp.json. Your personal subscriptions (your favorite coffee app, your gym) are yours alone and never appear in the company directory — that is ~/.claude.json. Access happens with your own badge (your credentials from your environment) — reception does not tape a shared password to the wall, which is exactly ${VAR} expansion instead of committing a token. The moment you enter, the lobby directory board shows every floor and service without you knocking on doors asking "what do you offer?" — that is resources as a catalog. And finally: the company does not build an elevator from scratch — it buys a standard, maintained one from a known manufacturer (the community server), customizing only the lobby design that expresses its identity (the custom server).

في الاختبارOn the exam

السؤال النموذجي يجمع 2-3 قرارات في سيناريو واحد (فريق يبي خادم GitHub مشتركًا وموثّقًا وبأداة يفضّلها الوكيل). فكّكه:

  • "مشترك يوصل الجميع عند الاستنساخ" = .mcp.json بنطاق المشروع. "شخصي/تجريبي" = ~/.claude.json.
  • "موثّق بدون إيداع التوكن" = توسيع ${VAR}. أي خيار فيه توكن مكتوب في الملف = مستبعد فورًا.
  • "الوكيل يفضّل Grep على أداة MCP الأقدر" = جوّد وصف أداة MCP — حذف Grep مشتت علاج-العرَض.
  • "استدعاءات استكشافية كثيرة ليعرف المتاح" = اعرض كتالوجًا كمورد MCP.
  • "تكامل Jira" = خادم مجتمع جاهز؛ المخصّص فقط لما يخص الفريق.

The typical question packs 2-3 decisions into one scenario (a team wants a shared, authenticated GitHub server whose tool the agent actually prefers). Decompose it:

  • "Shared, reaches everyone on clone" = project-scoped .mcp.json. "Personal/experimental" = ~/.claude.json.
  • "Authenticated without committing the token" = ${VAR} expansion. Any option with a token written in the file = eliminated on sight.
  • "Agent prefers Grep over the more capable MCP tool" = enhance the MCP tool description — deleting Grep is the symptom-fix distractor.
  • "Many exploratory calls to learn what exists" = expose a catalog as an MCP resource.
  • "A Jira integration" = existing community server; custom only for team-specific needs.
