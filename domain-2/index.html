تصميم الأدوات وتكامل MCP Tool Design & MCP Integration

خمسة مواضيع تبني عندك حاسّة "عقد الواجهة النظيف": وصف أداة يوجّه النموذج صح، خطأ منظّم يقود قرار التعافي، توزيع أدوات بمبدأ أقل صلاحية، خوادم MCP بالنطاق الصحيح، وإتقان أدوات Claude Code المدمجة. ملخص الدومينDomain summary

هذا الدومين يقيس الطبقة اللي تربط تفكير النموذج بأنظمتك الخلفية: الأداة. من الوصف اللي يقرأه النموذج قبل ما يختار الأداة، إلى شكل الخطأ اللي ترجعه الأداة لما تفشل، إلى قرار "أي وكيل يمسك أي أداة"، وصولًا لدمج خوادم MCP بالنطاق الصحيح وبدون تسريب أسرار — وأخيرًا اختيار الأداة المدمجة الصح (Grep · Glob · Read · Write · Edit) في استكشاف قواعد الكود. وزنه 18% أي قرابة 11 سؤالًا من 60، وكل أسئلته سيناريوهات: نظام شغّال فيه عيب تصميم صغير، والمطلوب منك تحديد الإصلاح الصحيح.

العقلية اللي يكافئها الدومين: عالج السبب الجذري بأقل تدخل. وسّع الوصف قبل ما تبني طبقة توجيه، صنّف الخطأ قبل ما تعيد المحاولة، أعطِ كل وكيل أدوات دوره فقط (مبدأ أقل صلاحية)، واستخدم خادم المجتمع قبل ما تبني خادمًا مخصّصًا. القرارات هنا صغيرة لكنها عالية الرافعة — واجهة واضحة وعقد خطأ منظّم يصلحان أكثر مما تصلحه أي معمارية ذكية فوق واجهة غامضة.

This domain measures the layer that connects the model's reasoning to your backend systems: the tool. From the description the model reads before selecting a tool, to the shape of the error a tool returns when it fails, to the decision of which agent holds which tool, through integrating MCP servers at the right scope without leaking secrets — and finally choosing the right built-in tool (Grep · Glob · Read · Write · Edit) when exploring codebases. It weighs 18%, roughly 11 of 60 questions, and every question is a scenario: a working system with a small design flaw, and you must identify the correct fix.

The mindset it rewards: fix the root cause with the smallest intervention. Expand the description before building a routing layer, classify the error before retrying, give each agent only its role's tools (least privilege), and use a community server before building a custom one. The decisions here are small but high-leverage — a clear interface and a structured error contract fix more than any clever architecture built on top of a vague one.

كيف يظهر في الاختبارHow it shows up on the exam

المشتتات في هذا الدومين لها أنماط ثابتة — إذا حفظتها، نصف الأسئلة ينحل بالاستبعاد: Distractors in this domain follow fixed patterns — memorize them and half the questions solve themselves by elimination:

  • طُعم الهندسة الزائدة: طبقة توجيه بالكلمات المفتاحية، حزمة أمثلة few-shot، خادم MCP مخصّص لتكامل قياسي — الإجابة الصح غالبًا الإصلاح الجذري الأبسط (وسّع الوصف، استخدم خادم المجتمع). Over-engineering bait: keyword routing layers, batches of few-shot examples, a custom MCP server for a standard integration — the right answer is usually the simpler root-cause fix (expand the description, use the community server).
  • علاج العرَض بدل السبب: "احذف Grep عشان يستخدم أداة MCP"، "ادمج الأداتين عشان يوقف الخلط" — السبب الحقيقي وصف ضعيف، والعلاج تحسينه. Symptom over cause: "delete Grep so it uses the MCP tool," "merge the two tools so it stops confusing them" — the real cause is a weak description; the fix is improving it.
  • مضادّات أنماط الأخطاء: رسالة "Operation failed" عامة، نتيجة فارغة موسومة نجاحًا بعد مهلة، إنهاء كامل سير العمل، إعادة لا نهائية — الصح دائمًا: بيانات منظّمة + تعافٍ محلي + تصعيد بنتائج جزئية. Error anti-patterns: a generic "Operation failed," an empty result marked success after a timeout, terminating the whole workflow, infinite retries — the right answer is always: structured metadata + local recovery + escalation with partial results.
  • خلط tool_choice: "any" يضمن استدعاء أداة ما لا أداة محددة؛ الإجبار بالاسم يثبّت أداة في دور واحد؛ وفرض تسلسل عبر عدة خطوات شغل الـ hooks (دومين 1) لا tool_choice. tool_choice confusion: "any" guarantees some tool, not a specific one; forcing by name pins one tool for one turn; multi-step sequencing is hooks territory (Domain 1), not tool_choice.
  • خلط النطاق والأسرار: إيداع توكن داخل .mcp.json، أو حشر خادم الفريق في ~/.claude.json — النمط الصحيح: نطاق المشروع للفريق + توسيع ${VAR} للأسرار. Scope & secrets confusion: committing a token inside .mcp.json, or stuffing the team server into ~/.claude.json — the correct pattern: project scope for the team + ${VAR} expansion for secrets.

Topic 2.1

في أداة إنتاجية للمطوّرين، عندك أداتان search_code وfind_files، وكل وحدة وصفها "Searches the repository". لما يطلب المطوّر "جِد تعريف الدالة calculateTax"، ينادي الوكيل find_files بالخطأ. وش أفضل خطوة أولى؟ In a developer-productivity tool you have two tools, search_code and find_files, each described "Searches the repository." When a developer asks "find the definition of calculateTax," the agent wrongly calls find_files. What is the best first step?

صحيح. الوصف هو الآلية الأساسية للاختيار؛ توسيعه علاج منخفض الجهد عالي الرافعة للسبب الجذري. الدمج خيار معماري أثقل، وطبقة التوجيه هندسة زائدة، والـ few-shot يزيد التوكنز دون علاج الوصف الناقص. Correct. The description is the primary selection mechanism; expanding it is a low-effort, high-leverage fix for the root cause. Consolidation is heavier, a routing layer is over-engineered, and few-shot adds tokens without fixing the thin description.
غير دقيق. الإجابة الصحيحة: توسيع الأوصاف. المشكلة أن الوصفين متطابقان تقريبًا؛ الدمج والتوجيه والـ few-shot كلها أثقل أو تتجاوز السبب الجذري (الوصف الناقص). Not quite. The correct answer is expanding the descriptions. The two descriptions are near-identical; consolidation, routing, and few-shot are all heavier or sidestep the root cause (the thin description).

Topic 2.1

أداة واحدة analyze_document تُستخدم لثلاثة أعمال مختلفة جوهريًا: سحب حقول رقمية، تلخيص نصّي، والتحقق من مطابقة ادعاء لمصدر — والنتائج غير متسقة. وش أفضل إصلاح بنيوي؟ A single analyze_document tool is used for three fundamentally different jobs: pulling numeric fields, summarizing text, and verifying a claim against a source — and results are inconsistent. What is the best structural fix?

صحيح. ثلاثة أعمال مختلفة الغرض تُقسَّم إلى أدوات محددة الغرض بعقود واضحة؛ هذا يعطي النموذج حدودًا نظيفة للاختيار ومخرجات متسقة. معامل mode يبقي التداخل، والإجبار وmax_tokens ما يعالجان الغموض. Correct. Three purpose-different jobs get split into purpose-specific tools with clear contracts; this gives the model clean selection boundaries and consistent outputs. A mode param keeps the overlap; forcing and max_tokens do not address the ambiguity.
غير دقيق. الإجابة الصحيحة: التقسيم إلى ثلاث أدوات محددة الغرض. المعامل mode يُبقي أداة عامة مثقلة، والإجبار وmax_tokens لا علاقة لهما بالغموض الوظيفي. Not quite. The correct answer is splitting into three purpose-specific tools. A mode param keeps one overloaded generic tool; forcing and max_tokens are unrelated to the functional ambiguity.

Topic 2.2

في وكيل دعم العملاء، ترفض process_refund مبلغًا يتجاوز حد السياسة، وترجع حاليًا isError:true برسالة "Operation failed". الوكيل يعيد المحاولة مرارًا. وش التصميم الصحيح للاستجابة؟ In a customer-support agent, process_refund rejects an amount over the policy cap and currently returns isError:true with "Operation failed." The agent keeps retrying. What is the correct response design?

صحيح. مخالفة السياسة خطأ عمل غير قابل للإعادة؛ البيانات المنظّمة توقف الإعادة المهدورة وتمكّن الوكيل من الشرح للعميل. النتيجة الفارغة كنجاح تخفي الخطأ، والـ backoff يهدر محاولات، والتصعيد الأعمى إفراط. Correct. A policy violation is a non-retryable business error; structured metadata stops wasted retries and lets the agent explain to the customer. Empty-as-success hides the error, backoff wastes attempts, and blanket escalation is excessive.
غير دقيق. الإجابة الصحيحة: خطأ عمل منظّم غير قابل للإعادة برسالة ودّية. النتيجة الفارغة تخفي الخطأ، والـ backoff يعيد على خطأ لن يُحل، والتصعيد لكل الحالات إفراط بلا تصنيف. Not quite. The correct answer is a structured non-retryable business error with a friendly message. Empty-as-success hides the error, backoff retries an unresolvable error, and escalating everything is excessive without classification.

Topic 2.2

في نظام بحث متعدد الوكلاء، تنتهي مهلة مصدر بيانات وكيل تحليل المستندات، فيرجع قائمة فارغة موسومة "successful". وش المشكلة والإصلاح؟ In a multi-agent research system, the document-analysis subagent's data source times out, and it returns an empty list marked "successful." What is the problem and the fix?

صحيح. فشل الوصول لا يساوي نتيجة فارغة صالحة؛ وسم الفشل كنجاح مضادّ نمط يمنع التعافي. السياق المنظّم يمكّن المنسّق من إعادة باستعلام معدّل أو بديل أو المتابعة بنتائج جزئية مع تعليم الفجوة. Correct. An access failure is not a valid empty result; marking failure as success is an anti-pattern that blocks recovery. Structured context lets the coordinator retry with a modified query, try an alternative, or proceed with partial results and annotate the gap.
غير دقيق. الإجابة الصحيحة: أرجِع سياق خطأ منظّمًا. المهلة فشل وصول؛ وسمها نجاحًا يخفي الخطأ، وإنهاء السير كله أو الإعادة اللانهائية كلاهما مضادّ نمط. Not quite. The correct answer is return structured error context. A timeout is an access failure; marking it success hides the error, and terminating the whole workflow or retrying forever are both anti-patterns.

Topic 2.3

أُعطي وكيل التوليف كل الأدوات الـ18 بما فيها web_search وfetch_url وأدوات قاعدة البيانات. صار أحيانًا يشغّل عمليات بحث بنفسه بدل التوليف، فتتضارب الاستشهادات. وش أفضل إصلاح؟ The synthesis agent was given all 18 tools including web_search, fetch_url, and DB tools. It now sometimes runs its own searches instead of synthesizing, producing inconsistent citations. Best fix?

صحيح. كثرة الأدوات وخروجها عن التخصص سبب سوء الاستخدام؛ أقل صلاحية = أدوات دوره + verify_fact مُنطّقة للحالات البسيطة، مع إبقاء المعقّد عبر المنسّق. المزيد يفاقم، و"any" يجبر أداة ولا يحل التخصص، والنزع الكامل يعطّل التحقق البسيط. Correct. Too many out-of-specialization tools cause the misuse; least privilege = its role's tools + a scoped verify_fact for simple cases, keeping complex ones through the coordinator. More tools worsen it, "any" forces a call without fixing specialization, and removing all disables simple verification.
غير دقيق. الإجابة الصحيحة: قصّ الأدوات + verify_fact مُنطّقة. المزيد من الأدوات يزيد المشكلة، و"any" لا يعالج التخصص، والنزع الكامل مبالغة تعطّل الاحتياج المتكرر البسيط. Not quite. The correct answer is scope the tools + a scoped verify_fact. More tools worsen it, "any" does not fix specialization, and removing all is an overreach that kills the simple high-frequency need.

Topic 2.3

تعالج مرفقات تذاكر الدعم، وتبي تضمن تشغيل extract_metadata أولًا على كل مرفق قبل أي أداة إثراء. أي إعداد يحقق ذلك بأعلى ضمان؟ You process support-ticket attachments and want to guarantee extract_metadata runs first on each attachment before any enrichment tool. Which config guarantees this?

صحيح. الإجبار بالاسم يضمن تشغيل أداة محددة أولًا بشكل حتمي، ثم تُعالَج الخطوات التالية في أدوار لاحقة. "auto" قد يرجّع نصًا، و"any" يضمن أداةً ما لا أيّها، والـ prompt وحده احتمالي. Correct. Forcing by name deterministically guarantees a specific tool runs first, then subsequent steps are handled in follow-up turns. "auto" may return text, "any" guarantees some tool but not which, and the prompt alone is probabilistic.
غير دقيق. الإجابة الصحيحة: الإجبار بالاسم. "auto" قد يرجّع نصًا، و"any" لا يحدّد أي أداة، والتعليمة في الـ prompt وحدها احتمالية لا تضمن الترتيب. Not quite. The correct answer is forced selection by name. "auto" may return text, "any" does not pin which tool, and a prompt-only instruction is probabilistic and does not guarantee ordering.

Topic 2.4

يبي الفريق خادم GitHub MCP مشتركًا يوصل للجميع عند الاستنساخ، موثّقًا بدون إيداع التوكن، ولاحظوا أن الوكيل يفضّل Grep المدمجة على أداة بحث الكود الأقدر في الخادم. أي تركيبة صحيحة؟ The team wants a shared GitHub MCP server available to everyone on clone, authenticated without committing the token, and they notice the agent prefers built-in Grep over the server's more capable code-search tool. Which combination is correct?

صحيح. نطاق المشروع يشارك الخادم مع الفريق، وتوسيع المتغير يحمي السر، وتجويد الوصف يقود التبنّي بدل حذف أداة مدمجة. تضمين التوكن أو إيداعه تسريب، وحذف Grep علاج عرَضي. Correct. Project scope shares the server with the team, env expansion protects the secret, and enhancing the description drives adoption instead of deleting a built-in tool. Hardcoding or committing the token is a leak, and deleting Grep treats a symptom.
غير دقيق. الإجابة الصحيحة: نطاق المشروع + توسيع المتغير + تجويد الوصف. تضمين التوكن أو إيداعه تسريب سر، ونطاق المستخدم لا يشارك الفريق، وحذف Grep يعالج العرَض لا السبب (وصف MCP ضعيف). Not quite. The correct answer is project scope + env expansion + a better description. Hardcoding/committing the token leaks a secret, user scope does not share with the team, and deleting Grep treats the symptom, not the cause (a weak MCP description).

Topic 2.5

وكيل Claude Code يحاول تعديل سطر إعداد يتكرر نصّه 4 مرات متطابقة في نفس الملف، وأداة Edit تفشل برسالة عدم تفرّد النص. وش الأسلوب الموثوق؟ A Claude Code agent tries to modify a config line whose text appears 4 identical times in the same file, and Edit fails with a non-unique match error. What is the reliable approach?

صحيح. لما يفشل Edit لعدم تفرّد النص، البديل الموثوق حسب دليل الاختبار هو Read + Write. تكرار Edit بنفس النص بيفشل بنفس السبب، وGlob يطابق مسارات الملفات لا محتواها، وإعادة الإنشاء من الذاكرة تخاطر بفقدان محتوى. Correct. When Edit fails on non-unique text, the reliable fallback per the exam guide is Read + Write. Repeating Edit with the same anchor fails for the same reason, Glob matches file paths not contents, and recreating from memory risks losing content.
غير دقيق. الإجابة الصحيحة: Read + Write. فشل التفرّد ما ينحل بالتكرار، وGlob للمسارات لا للمحتوى، والحذف وإعادة الإنشاء من الذاكرة مخاطرة غير ضرورية. Not quite. The correct answer is Read + Write. A uniqueness failure will not resolve by repetition, Glob is for paths not contents, and delete-and-recreate from memory is an unnecessary risk.
