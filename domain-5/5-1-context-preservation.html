5.1

حفظ السياق عبر المحادثات الطويلة Context preservation across long interactions

ليش مهم؟ لأن المحادثة الطويلة ما تفشل بنفاد التوكنز — تفشل لما «تنسى» مبلغ 1,299 ريال اللي وعدت العميل فيه. Why it matters: a long conversation doesn't fail by running out of tokens — it fails when it "forgets" the 1,299 SAR you promised the customer.

وش بتتعلم في هذي الصفحة What you'll learn on this page

  • ليش progressive summarization يبلع الأرقام والنسب والتواريخ وتوقعات العميل المصرّح بها.Why progressive summarization swallows numbers, percentages, dates, and customer-stated expectations.

  • تأثير «الضياع في المنتصف» (lost in the middle) وكيف ترتّب المدخلات الطويلة ضده.The "lost in the middle" effect and how to order long inputs against it.

  • كيف تتراكم نتائج الأدوات (40+ حقلًا وأنت تحتاج 5) وكيف تقصّها قبل ما تدخل السياق.How tool results accumulate (40+ fields when you need 5) and how to trim them before they hit context.

  • بناء كتلة «حقائق القضية» الثابتة، وطبقة سياق منفصلة لكل قضية في الجلسات متعددة القضايا.Building a persistent "case facts" block, and a separate context layer per issue in multi-issue sessions.

  • إلزام الوكلاء الفرعيين بميتاداتا (تواريخ، مواقع المصادر، سياق منهجي) وبيانات منظّمة بدل سلاسل التفكير المطوّلة.Requiring subagents to return metadata (dates, source locations, methodological context) and structured data instead of verbose reasoning chains.

1 المصائد الأربع اللي تقتل المحادثة الطويلة The four traps that kill a long conversation

لما محادثة الدعم تطول (رجوع منتج، نزاع فوترة... 30 دورة)، الخطر الحقيقي مو نفاد التوكنز — الخطر إنك تفقد الحقيقة وأنت ما تدري. أربع مصائد يعيد الاختبار تدويرها بصيغ مختلفة:

  1. التلخيص التدريجي (progressive summarization) يكثّف القيم الرقمية والنسب والتواريخ وتوقعات العميل المصرّح بها إلى ملخصات مبهمة: «العميل يبي استرداد» بدل «العميل يبي استرداد كامل بمبلغ 1,299 SAR، ويرفض رصيد المتجر».
  2. الضياع في المنتصف: النموذج يعالج بداية ونهاية المدخل الطويل بثبات، لكنه قد يُسقِط نتائج من الوسط — يعني ترتيب المعلومة داخل المدخل قرار معماري، مو تفصيلة.
  3. تراكم نتائج الأدوات: كل استدعاء lookup_order يرمي 40+ حقلًا في السياق وأنت تحتاج 5 منها فقط — استهلاك توكنز غير متناسب مع الأهمية، وضجيج يزاحم الحقائق.
  4. كسر الترابط: لازم تمرّر كامل سجل المحادثة في كل طلب API لاحق. الحذف العشوائي لدورات قديمة يكسر الترابط — القصّ الذكي يكون في حجم نتائج الأدوات وفي فصل الحقائق، مو في رمي أجزاء من الحوار.

When a support conversation runs long (a return, a billing dispute... 30 turns), the real risk isn't running out of tokens — it's losing the truth without noticing. Four traps the exam recycles in different forms:

  1. Progressive summarization condenses numerical values, percentages, dates, and customer-stated expectations into vague summaries: "customer wants a refund" instead of "customer wants a full refund of 1,299 SAR and refuses store credit."
  2. Lost in the middle: models reliably process the beginning and end of a long input but may omit findings from the middle — so where information sits inside the input is an architectural decision, not a detail.
  3. Tool-result accumulation: every lookup_order call dumps 40+ fields into context when only 5 matter — token consumption disproportionate to relevance, and noise that crowds out the facts.
  4. Broken coherence: you must pass the complete conversation history in each subsequent API request. Arbitrarily dropping old turns breaks coherence — smart reduction targets the size of tool results and the separation of facts, not chunks of the dialogue.

النموذج «يشوف» البداية والنهاية بثبات — لذلك حط ملخص النتائج المفتاحية في البداية، ونظّم الوسط بعناوين أقسام صريحة. The model reliably "sees" the beginning and end — so put the key-findings summary first and organize the middle with explicit section headers.

لمحة سريعةQuick insight

البداية والنهاية «عقارات فاخرة» في المدخل الطويل. الشيء اللي لا يجوز نسيانه أبدًا — حطّه في البداية. آخر شيء تبيه حاضرًا وقت التوليد — قرّبه من النهاية. The beginning and end are the prime real estate of a long input. What must never be forgotten goes first; what you want freshest at generation time goes near the end.

2 كتلة «حقائق القضية» — طبقة سياق منفصلة The "case facts" block — a separate context layer

الحل المعماري الأول: استخرج الحقائق المعاملاتية — المبالغ، التواريخ، أرقام الطلبات، الحالات — في كتلة «حقائق قضية» ثابتة تُحقَن في كل برومبت، خارج السجل المُلخَّص. التلخيص يضغط الحوار براحته، لأن الحقائق صارت محفوظة في طبقة ما يوصل لها الضغط.

وفي الجلسة اللي فيها أكثر من قضية (رجوع طلب + نزاع فوترة لطلب ثاني)، لا تخلط: استخرج بيانات كل قضية (رقم الطلب، المبلغ، الحالة) في طبقة سياق منفصلة لكل قضية — الخلط بين مبلغين هو بالضبط الخطأ اللي يصطاده الاختبار.

The first architectural fix: extract transactional facts — amounts, dates, order numbers, statuses — into a persistent "case facts" block injected into every prompt, outside the summarized history. Summarization can then compress the dialogue freely, because the facts live in a layer compression never touches.

And in a session with multiple issues (a return on one order + a billing dispute on another), don't blend them: extract each issue's data (order ID, amount, status) into a separate context layer per issue — mixing two amounts up is exactly the failure the exam hunts for.

Context layering — what survives a long session

CASE FACTS (persistent) re-injected every turn · never summarized
ISSUE-2 FACTS (own layer) multi-issue session: one layer per issue
ROLLING SUMMARY safe to compress — facts live above
TRIMMED TOOL RESULTS 5 relevant fields, not 40+
next API request (full history preserved)

الطبقات من فوق لتحت: حقائق ثابتة لا تُلخَّص أبدًا، ثم ملخص قابل للضغط، ثم نتائج أدوات مقصوصة — وكلها تدخل الطلب التالي مع كامل السجل. Top to bottom: persistent facts that are never summarized, then a compressible summary, then trimmed tool results — all entering the next request with full history.

مثال — كتلة «حقائق القضية» الثابتة (وطبقة لكل قضية)Example — the persistent "case facts" block (one layer per issue)

python 
# CASE FACTS: compact, structured, re-injected into EVERY request,
# kept OUTSIDE the summarized history so numbers/dates never get lost.
# Multi-issue session: ONE facts block PER issue (separate context layers).
case_facts = {
    "issue-1-return": {
        "order_id":    "ORD-99155",
        "order_total": "1,299.00 SAR",     # the exact amount the refund depends on
        "order_date":  "2026-06-30",
        "status":      "delivered_damaged",
        "expectation": "full refund, not store credit",  # customer's words, verbatim
    },
    "issue-2-billing": {
        "order_id":    "ORD-97002",
        "disputed":    "duplicate charge 249.00 SAR",
        "charge_date": "2026-07-11",
        "status":      "under_review",
    },
}

def build_request(rolling_summary, latest_user_turn):
    return {
        "system": SYSTEM_PROMPT,
        "messages": [
            # 1) Facts FIRST: high-salience position, survives summarization
            {"role": "user",
             "content": "## CASE FACTS (authoritative)\n" + json.dumps(case_facts, indent=2)},
            # 2) Rolling summary of older turns (safe to compress — facts live above)
            {"role": "user", "content": "## CONVERSATION SUMMARY\n" + rolling_summary},
            # 3) The live turn (the full history is still passed each request)
            {"role": "user", "content": latest_user_turn},
        ],
    }

مفهوم أساسيKey concept

«حقائق القضية» ليست تلخيصًا — هي طبقة سياق منفصلة. التلخيص يضغط الحوار؛ حقائق القضية تُقتبَس حرفيًا وتبقى ثابتة. الفرق بين الاثنين هو الفرق بين «العميل يبي استرداد» و«استرداد كامل 1,299 ريال، يرفض رصيد المتجر». "Case facts" is not a summary — it's a separate context layer. Summaries compress dialogue; case facts are quoted verbatim and stay fixed. The difference between the two is the difference between "customer wants a refund" and "full refund of 1,299 SAR, refuses store credit."

3 قصّ نتائج الأدوات وترتيب المدخلات Trimming tool results and ordering inputs

نتيجة الأداة الخام «مصدر ضجيج» يتراكم كل دورة. القاعدة: قُصّ المخرَج للحقول ذات الصلة قبل ما يدخل السياق — في وكيل الاسترداد، من 40+ حقلًا تبقى 5 فقط (رقم الطلب، الإجمالي، العملة، الحالة، قابلية الاسترداد). وعند تجميع مخرجات عدة وكلاء في مدخل واحد طويل: حُطّ ملخص النتائج المفتاحية في البداية ونظّم التفاصيل بعناوين أقسام صريحة — هذا العلاج المباشر لتأثير الموضع.

A raw tool result is a noise source that accumulates every turn. The rule: trim the output to relevant fields before it enters context — in a refund agent, 40+ fields become just 5 (order ID, total, currency, status, refundability). And when aggregating several agents' outputs into one long input: put the key-findings summary at the beginning and organize details with explicit section headers — the direct treatment for position effects.

BAD — raw result into context

order_id, customer_id, total, currency,

status, refundable, billing_address{...},

shipping_address{...}, carrier_events[22],

tax_breakdown{...}, promo_codes[], gift_wrap,

warehouse_id, pick_path, loyalty_points,

...25 more irrelevant fields...

40+ fields x every turn = noise crowds the facts

GOOD — trimmed before context

order_id: "ORD-99155"

total: 1299.00

currency: "SAR"

status: "delivered_damaged"

refundable: true

5 return-relevant fields = ~90% fewer tokens

نفس الاستدعاء، فرق جذري في السياق: اليسار يراكم الضجيج، واليمين يبقي الإشارة فقط. Same call, radically different context: one accumulates noise, the other keeps only the signal.

مثال — قصّ نتيجة الأداة: 40+ حقلًا تصير 5 حقولExample — trimming a tool result: 40+ fields become 5

python 
# lookup_order returns 40+ fields; only 5 matter for a return/refund decision.
# Trim BEFORE the result ever lands in context (e.g. in a PostToolUse hook).

def trim_order(raw):                     # keep ONLY return-relevant fields
    return {
        "order_id":   raw["order_id"],
        "total":      raw["total"],
        "currency":   raw["currency"],
        "status":     raw["status"],
        "refundable": raw["refundable"],
    }

# 40+ fields -> 5 fields : ~90% fewer tokens accumulating every turn.
# Position-aware aggregation for long multi-agent inputs:
aggregated_input = (
    "## KEY FINDINGS (summary first — high-salience position)\n"
    + findings_summary
    + "\n\n## SECTION: web search results\n"   + web_results
    + "\n\n## SECTION: document analysis\n"    + doc_results
)  # explicit headers keep the middle navigable

نصيحةTip

اقصّ عند الحدود — قبل دخول النتيجة للسياق (مثل hook بعد الأداة) — مو بعد ما تتراكم. القصّ المتأخر ما يرجّع التوكنز اللي احترقت ولا يصلّح الانتباه اللي تشتّت. Trim at the boundary — before the result enters context (e.g. a post-tool hook) — not after it accumulates. Late trimming doesn't refund burned tokens or repair diluted attention.

4 تسليم منظّم بين الوكلاء — بيانات، لا سلاسل تفكير Structured handoffs between agents — data, not reasoning chains

في الأنظمة متعددة الوكلاء، وكيل التجميع النهائي يعيش على ميزانية سياق محدودة. لو كل وكيل بحث يرسل له نصوصًا مطوّلة وسلاسل تفكيره كاملة، الميزانية تنتهي قبل التجميع. الحل من طرفين:

  • ألزِم الوكلاء الفرعيين بالميتاداتا: كل نتيجة تتضمن التواريخ، مواقع المصادر، والسياق المنهجي — عشان التجميع اللاحق يكون دقيقًا وقابلًا للتتبع.
  • عدّل الوكيل الأعلى (upstream) ليرجع بيانات منظّمة: حقائق مفتاحية، اقتباسات، درجات صلة (relevance scores) — بدل محتوى مطوَّل وسلاسل استدلال، لما يكون الوكيل الأدنى محدود الميزانية.

In multi-agent systems, the final synthesis agent lives on a limited context budget. If every research agent sends it verbose prose plus full reasoning chains, the budget is gone before synthesis starts. The fix works from both ends:

  • Require metadata from subagents: every finding includes dates, source locations, and methodological context — so downstream synthesis is accurate and traceable.
  • Modify the upstream agent to return structured data — key facts, citations, relevance scores — instead of verbose content and reasoning chains, when the downstream agent has a limited context budget.

مثال — مخرَج وكيل فرعي منظّم (بدل نص مطوَّل)Example — structured subagent output (instead of verbose prose)

json 
{
  "finding": "AI adoption in film post-production grew 3x between 2023 and 2026",
  "key_facts": ["3x growth", "post-production segment", "2023-2026 window"],
  "citation": {
    "source": "MediaTech Annual Review",
    "location": "https://example.com/mtar-2026, section 4.2",
    "published": "2026-03-14",
    "method_note": "survey of 240 studios, self-reported budgets"
  },
  "relevance_score": 0.92
}

تنبيهWarning

لا تحاول علاج ضيق ميزانية الوكيل الأدنى بتكبير ميزانيته — عالِج المنبع: خلّ الوكيل الأعلى يرجّع بيانات منظّمة أصغر وأدق. تكبير الميزانية يؤجّل المشكلة ويرفع التكلفة. Don't treat the downstream agent's tight budget by enlarging it — fix the source: have the upstream agent return smaller, sharper structured data. Enlarging the budget postpones the problem and raises cost.

فخ الاختبارExam trap

  • «بدّل لنموذج بنافذة سياق أكبر» — السعة الأكبر لا تصلّح جودة الانتباه ولا الضياع في المنتصف؛ المشكلة تنظيمية لا سعوية."Switch to a larger context window" — more capacity doesn't fix attention quality or lost-in-the-middle; the problem is organization, not size.

  • «لخّص بقوة أكبر» — يزيد الطين بلّة: التلخيص الأشرس يبلع أرقامًا أكثر. الصح: افصل الحقائق في طبقة، لا تضغطها."Summarize more aggressively" — makes it worse: harsher summarization swallows more numbers. Right move: separate the facts into a layer, don't compress them.

  • «خزّن نتيجة الأداة كاملة عشان ما نفقد شيئًا» — الحقول الأربعون تزاحم المهم وتسرّع الضياع في المنتصف؛ قُصّ قبل السياق."Keep the full tool result so we lose nothing" — the 40 fields crowd out what matters and accelerate lost-in-the-middle; trim before context.

مثال من الحياة: المحقّق ولوحة القضيةReal-life example: the detective and the case board

محقّق يشتغل على قضية عمرها أسابيع. على الجدار لوحة قضية مثبّتة: الأسماء، التواريخ، المبالغ، أرقام الأدلة — مكتوبة بخط واضح وما تُمسح أبدًا. أما استجواباته اليومية فيلخّصها في دفتر. لو اعتمد على الدفتر الملخّص وحده، بينسى بالضبط كم كان المبلغ المسروق وأي يوم صار الحادث — وهذا حرفيًا اللي يسويه التلخيص التدريجي بالأرقام.

لوحة القضية = كتلة «حقائق القضية» الثابتة. الدفتر = الملخص المتدحرج. ولو عنده قضيتان في نفس الوقت؟ لوحة لكل قضية — عشان ما يركّب دليل قضية على متهم قضية ثانية.

A detective works a case that runs for weeks. On the wall hangs a case board: names, dates, amounts, evidence numbers — written clearly and never erased. His daily interviews he condenses into a notebook. If he relied on the summarized notebook alone, he'd forget exactly how much was stolen and on which day — which is literally what progressive summarization does to numbers.

The case board is the persistent "case facts" block. The notebook is the rolling summary. And if he's working two cases at once? One board per case — so he never pins one case's evidence on the other case's suspect.

في الاختبارOn the exam

السؤال النموذجي: وكيل دعم أو منسّق بحث «ينسى» رقمًا أو توقعًا مصرّحًا به بعد محادثة طويلة، أو تجميع يُسقط نتائج من منتصف مدخل مجمّع — ويطلب منك «أنسب حل معماري» أو «السبب الجذري».

الإجابة الفائزة دائمًا تنظيمية: طبقة حقائق ثابتة خارج الملخص + قصّ نتائج الأدوات + ملخص في البداية مع عناوين أقسام + بيانات منظّمة من الوكلاء الفرعيين.

The typical question: a support agent or research coordinator "forgets" a number or stated expectation after a long conversation, or synthesis drops findings from the middle of an aggregated input — and asks for the "best architectural fix" or "root cause."

The winning answer is always organizational: a persistent facts layer outside the summary + trimmed tool results + summary-first ordering with section headers + structured data from subagents.

مموِّهات تشيلها فورًا:Distractors to eliminate on sight:

نافذة سياق أكبر / نموذج أعلى فئة — سعة، مو تنظيم.Bigger context window / higher-tier model — capacity, not organization.

لا.No. تكبير الميزانية يؤجّل المشكلة، والتلخيص داخل وكيل التجميع يستهلك الميزانية نفسها اللي نحاول حمايتها، والقطع الأعمى يرمي معلومات حرجة. الصحيح: بيانات منظّمة من المنبع.Enlarging the budget postpones the problem, summarizing inside the synthesis agent burns the very budget we're protecting, and blind truncation drops critical information. Correct: structured data from upstream.

خلاصةTakeaway

  • حقائق القضية (مبالغ، تواريخ، أرقام طلبات، حالات) في كتلة ثابتة خارج الملخص، تُحقَن كل طلب — وطبقة منفصلة لكل قضية.Case facts (amounts, dates, order numbers, statuses) live in a persistent block outside the summary, injected every request — one layer per issue.

  • قُصّ نتائج الأدوات للحقول ذات الصلة قبل دخولها السياق (40+ حقلًا تصير 5).Trim tool results to relevant fields before they enter context (40+ fields become 5).

  • ضد الضياع في المنتصف: ملخص النتائج المفتاحية في البداية + عناوين أقسام صريحة.Against lost-in-the-middle: key-findings summary first + explicit section headers.

  • مرّر كامل سجل المحادثة في كل طلب API — الحذف العشوائي يكسر الترابط.Pass the complete conversation history in every API request — arbitrary trimming breaks coherence.

  • الوكلاء الفرعيون يرجعون بيانات منظّمة + ميتاداتا (تواريخ، مصادر، منهجية) — لا سلاسل تفكير مطوّلة.Subagents return structured data + metadata (dates, sources, methodology) — not verbose reasoning chains.
