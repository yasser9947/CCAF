3.5

التحسين التكراري Iterative refinement

النتيجة الممتازة نادراً ما تجي من أول برومبت — تجي من تكرار ذكي: أمثلة تحسم، اختبارات تقود، وأسئلة تكشف ما لم تفكر فيه. Great results rarely come from the first prompt — they come from smart iteration: examples that pin down, tests that steer, and questions that surface what you had not considered.

وش بتتعلمWhat you'll learn

  • تقديم 2–3 أمثلة input/output ملموسة حين يُفسَّر الوصف النثري بشكل غير متسقProviding 2–3 concrete input/output examples when prose descriptions are interpreted inconsistently
  • التكرار المقاد بالاختبارات: كتابة الاختبارات أولاً (سلوك، حالات حدية، أداء) ثم مشاركة الاختبارات الفاشلة لتوجيه التحسينTest-driven iteration: writing the tests first (behavior, edge cases, performance) then sharing failing tests to steer improvement
  • نمط المقابلة: جعل Claude يسألك قبل التنفيذ ليكشف اعتبارات لم تتوقعها (إبطال الكاش، أنماط الفشل)The interview pattern: having Claude question you before implementing, surfacing considerations you did not anticipate (cache invalidation, failure modes)
  • إصلاح الحالات الحدية بحالة اختبار محددة: مدخل مثال + مخرج متوقع (مثل قيم null في سكربتات الترحيل)Fixing edge cases with a specific test case: example input + expected output (e.g. null values in migration scripts)
  • قرار الرسالة الواحدة مقابل التتابع: المشكلات المتشابكة في رسالة واحدة مفصّلة، والمستقلة واحدة تلو الأخرىThe single-message vs sequential decision: interacting problems in one detailed message, independent ones one at a time

الأمثلة تحسم ما يعجز عنه النثر Examples pin down what prose cannot

حين تصف تحويلاً بالكلمات («نظّف الحقول بشكل معقول») ويعود التنفيذ مختلفاً كل مرة، الغريزة الشائعة هي تقوية النثر: «نظّف الحقول بدقة شديدة ودائماً». هذه الغريزة خاطئة — الصفات لا تحسم الغموض، الأمثلة تحسمه.

الدليل الرسمي صريح: 2–3 أمثلة input → output ملموسة هي أنجع وسيلة لتوصيل التحويل المتوقع حين يُفسَّر الوصف النثري بشكل غير متسق. المثال يجيب دفعة واحدة عن كل الأسئلة التي كان النثر يتركها مفتوحة: كيف تُعالج المسافات؟ ماذا عن الأرقام بصيغ مختلفة؟ وماذا نفعل بالمدخل الفارغ؟

ونفس المبدأ ينطبق على إصلاح الحالات الحدية: قيمة null تكسر سكربت الترحيل؟ لا تكتفِ بـ«عالج الحالات الفارغة» — أعطِ حالة اختبار محددة: هذا المدخل بالضبط، وهذا المخرج المتوقع بالضبط.

When you describe a transformation in words ("clean up the fields sensibly") and the implementation comes back different every time, the common instinct is to strengthen the prose: "clean the fields very precisely, always." That instinct is wrong — adjectives do not resolve ambiguity, examples do.

The official guide is explicit: 2–3 concrete input → output examples are the most effective way to communicate an expected transformation when prose is interpreted inconsistently. One example answers, in a single stroke, every question prose left open: how is whitespace handled? What about numbers in mixed formats? And what happens to an empty input?

The same principle fixes edge cases: a null value breaking your migration script? Do not settle for "handle empty cases" — give a specific test case: exactly this input, exactly this expected output.

مثال: تثبيت التحويل بأمثلة بدل الصفاتExample: pinning the transformation with examples, not adjectives
# Task: normalize customer records

Prose alone ("clean up the fields sensibly") is read inconsistently.
Pin it down with concrete input -> output examples:

## Examples
1. "  Ahmed  Al-Otaibi "          ->  "Ahmed Al-Otaibi"
2. "MOBILE: 0555-123-456"         ->  "+966555123456"
3. ""             (empty input)   ->  null   # never invent a value

## Edge case found later? Report it the same way:
- Input:    {"joined": null}
- Expected: {"joined": null}     # keep null, do NOT default to today
- Actual:   crash in migrate.py line 41
لمحة سريعةQuick insight
سؤال فيه «نتائج غير متسقة رغم وصف مفصّل» جوابه شبه المؤكد: أضف أمثلة ملموسة — لا «أعد صياغة الوصف بحزم أكبر» ولا «كرر التعليمات».
A question featuring "inconsistent results despite a detailed description" is almost certainly answered by add concrete examples — never "reword the description more forcefully" or "repeat the instructions."

التكرار المقاد بالاختبارات Test-driven iteration

بدل أن «تشعر» أن الحل تحسّن، اجعل التحسّن قابلاً للقياس: اكتب مجموعة اختبارات قبل التنفيذ تغطي السلوك المتوقع والحالات الحدية ومتطلبات الأداء، ثم كرّر بحلقة واضحة — شغّل الاختبارات، شارك الفاشل منها مع Claude، خذ الإصلاح، وأعد التشغيل حتى الأخضر الكامل. الاختبار الفاشل هو أدق «مثال ملموس» ممكن: مدخل محدد ومخرج متوقع وفجوة موثقة بينهما.

Instead of "feeling" that the solution improved, make improvement measurable: write a test suite before implementation covering expected behavior, edge cases, and performance requirements, then iterate in a tight loop — run the tests, share the failing ones with Claude, take the fix, rerun until fully green. A failing test is the most precise "concrete example" possible: a specific input, an expected output, and a documented gap between them.

الاختبارات تُكتب قبل التنفيذ، والفشل يُشارك حرفياً — فيصبح كل تكرار موجّهاً لا عشوائياً. Tests are written before implementation and failures are shared verbatim — every iteration is steered, never random.

مثال: مشاركة الفشل الموجِّه للتكرار التاليExample: sharing the failure that steers the next iteration
# tests written BEFORE implementation
def test_normalize_phone():
    assert normalize_phone("0555-123-456") == "+966555123456"

def test_null_joined_date_preserved():
    # edge case: null must stay null, never default to today
    assert migrate_record({"joined": None})["joined"] is None

# iteration message to Claude after a run:
#   "2 tests fail. test_null_joined_date_preserved:
#    expected None, got '2026-07-18'. Fix WITHOUT breaking
#    test_normalize_phone (currently passing)."

نمط المقابلة: خلّ Claude يسألك أولاً The interview pattern: let Claude question you first

حين تبني في مجال لا تعرفه جيداً، أخطر ما في طلبك ليس ما كتبته — بل ما لم يخطر لك أن تكتبه. نمط المقابلة يقلب الاتجاه: قبل التنفيذ، اطلب من Claude أن يطرح عليك أسئلة تكشف الاعتبارات الغائبة عن ذهنك.

مثال الدليل: تطلب «طبقة كاش للاستعلامات المتكررة»، فيسألك Claude قبل كتابة أي سطر: ما استراتيجية إبطال الكاش (cache invalidation) عند تغيّر البيانات؟ ماذا يحدث عند فشل مخزن الكاش — نعود للمصدر أم نفشل الطلب؟ هل النتائج المتقادمة مقبولة ولأي مدة؟ كل سؤال من هذه يوفّر عليك اكتشاف الثغرة في الإنتاج.

When building in a domain you do not know well, the most dangerous part of your request is not what you wrote — it is what never occurred to you to write. The interview pattern flips the direction: before implementing, ask Claude to interview you, surfacing the considerations missing from your head.

The guide's example: you ask for "a cache layer for repeated queries," and before writing a line Claude asks: what is the cache invalidation strategy when data changes? What happens on a cache-store failure — fall back to the source or fail the request? Are stale results acceptable, and for how long? Each of those questions saves you discovering the gap in production.

الأسئلة قبل الكود: القرارات الغائبة تُحسم في المقابلة، لا في حادثة إنتاج. Questions before code: the missing decisions get settled in the interview, not in a production incident.

نصيحةTip
أقوى توقيت لنمط المقابلة: مجال غير مألوف لك. لو كنت خبيراً بالكاش، غالباً كتبت المتطلبات كاملة من البداية — لكن في أرض جديدة، أسئلة Claude هي خبرتك المستعارة.
The interview pattern's highest-value moment: a domain unfamiliar to you. A caching expert would have written the full requirements upfront — but on new ground, Claude's questions are your borrowed expertise.

رسالة واحدة أم تتابع؟ One message or sequential?

عندك عدة مشاكل تريد إصلاحها — هل ترميها كلها في رسالة واحدة أم تعالجها واحدة واحدة؟ المعيار هو التشابك:

  • مشكلات متشابكة (إصلاح إحداها يؤثر على الأخرى — مثل خلل أداء وخلل صحة نتائج في نفس الدالة): رسالة واحدة مفصّلة تعرضها معاً، ليرى Claude التفاعل بينها ويوازن الحل بدل أن يكسر بإصلاحٍ ما أصلحه قبله.
  • مشكلات مستقلة (لا أثر متبادل — خطأ إملائي في رسالة، وخلل في وحدة أخرى): تكرار متتابع، مشكلة فمراجعة فمشكلة — أوضح وأسهل للتحقق خطوة بخطوة.

You have several problems to fix — dump them all in one message, or handle them one at a time? The criterion is interaction:

  • Interacting problems (fixing one affects another — say a performance flaw and a correctness flaw in the same function): one detailed message presenting them together, so Claude sees the interplay and balances the fix instead of breaking with one repair what the previous repair achieved.
  • Independent problems (no mutual effect — a typo in one message, a flaw in another module): sequential iteration, fix then verify then next — clearer and easier to check step by step.

مفهوم أساسيKey concept
تقنيات هذا الدرس كلها تطبيق لفكرة واحدة: حوّل الغموض إلى حقائق قابلة للفحص — مثال يثبّت التحويل، اختبار فاشل يثبّت الفجوة، سؤال مقابلة يثبّت القرار الغائب، ورسالة مجمّعة تثبّت التفاعل بين الإصلاحات.
Every technique in this lesson applies one idea: turn ambiguity into checkable facts — an example pins the transformation, a failing test pins the gap, an interview question pins the missing decision, and a combined message pins the interaction between fixes.

فخ الاختبارExam trap

  • الفخ: نتائج التحويل غير متسقة → «أعد صياغة الوصف بكلمات أقوى وأكثر تفصيلاً». الصح: 2–3 أمثلة input/output ملموسة — الأمثلة تحسم، لا النثر.
    Trap: inconsistent transformation results → "reword the description more forcefully and in more detail." Reality: 2–3 concrete input/output examples — examples decide it, not prose.
  • الفخ: رمي مشكلات متشابكة في رسائل متفرقة متتابعة (فيُصلح Claude واحدة ويكسر أخرى). الصح: المتشابكة معاً في رسالة واحدة مفصّلة؛ المستقلة فقط تُعالج بالتتابع.
    Trap: feeding interacting problems through separate sequential messages (so Claude fixes one and breaks another). Reality: interacting issues go together in one detailed message; only independent ones go sequentially.
  • الفخ: حالة حدية تكسر السكربت → «اطلب معالجة كل الحالات الغريبة بحذر». الصح: حالة اختبار محددة بمدخل مثال ومخرج متوقع (قيمة null بعينها وما يجب أن يحدث لها).
    Trap: an edge case breaks the script → "ask it to handle all strange cases carefully." Reality: a specific test case with an example input and expected output (the exact null value and what must happen to it).

مثال من الحياة: الخياط الشاطرReal-life example: the master tailor

تطلب ثوباً «مريحاً وأنيقاً» — كلام فضفاض يفسّره كل خياط بمزاجه. الخياط الشاطر يطلب منك ثوبك المفضل القديم ليقيس عليه: هذا هو المثال الملموس (input/output example) الذي يحسم ما عجزت الكلمات عنه.

ثم لا يخيط الثوب كاملاً ويسلّمك إياه — بل يشلّخه بالدبابيس وتجرّبه قبل الخياطة النهائية، وكل ملاحظة («الكم أطول بسنتيمترين») هي اختبار فاشل محدد يوجّه التعديل التالي (التكرار المقاد بالاختبارات). والخياط الممتاز أصلاً يسألك قبل أن يقص القماش: للصيف أم للشتاء؟ للدوام أم للمناسبات؟ تكوي بنفسك أم بالمغسلة؟ — أسئلة تكشف قرارات ما كانت في بالك (نمط المقابلة). وأخيراً: لو قلت «وسّع الصدر وضيّق الخصر» فهذان تعديلان متشابكان يُنفَّذان معاً في جلسة واحدة — لا كل واحد في زيارة منفصلة تنقض ما قبلها.

You ask for a thobe that is "comfortable and elegant" — loose words every tailor interprets his own way. The master tailor asks for your favorite old thobe to measure against: that is the concrete input/output example deciding what words never could.

He also does not sew the whole garment and hand it over — he pins it and has you try it on before final stitching, and every note ("sleeve two centimeters long") is a specific failing test steering the next adjustment (test-driven iteration). The excellent tailor even questions you before cutting the fabric: summer or winter? Office or occasions? Home-ironed or dry-cleaned? — questions surfacing decisions you had not considered (the interview pattern). Finally: "widen the chest and take in the waist" are two interacting alterations done together in one sitting — not in separate visits where each undoes the last.

في الاختبارOn the exam

كيف يجي السؤالHow it is asked
  • «الوصف مفصّل لكن النتائج غير متسقة» → أضف 2–3 أمثلة input/output."The description is detailed but results are inconsistent" → add 2–3 input/output examples.
  • «كيف تضمن تحسناً قابلاً للقياس؟» → اختبارات أولاً ثم شارك الفشل. «مجال غير مألوف؟» → نمط المقابلة."How do you guarantee measurable improvement?" → tests first, then share failures. "Unfamiliar domain?" → the interview pattern.
  • «عدة مشاكل — رسالة واحدة أم تتابع؟» → اسأل نفسك أولاً: هل تتفاعل الإصلاحات؟"Several problems — one message or sequential?" → first ask: do the fixes interact?
إجابات فخ تستبعدها فوراًTrap answers to eliminate
  • «أعد الصياغة بحزم أكبر / أضف تحذيرات بالخط العريض» — نثر إضافي لمشكلة يحلها مثال."Reword more forcefully / add bold warnings" — extra prose for a problem an example solves.
  • «اكتب الكود أولاً ثم أضف الاختبارات لاحقاً» حين يسأل عن التكرار المقاد بالاختبارات."Write the code first, add tests later" when the question targets test-driven iteration.
  • قاعدة عمياء «دائماً رسالة واحدة» أو «دائماً بالتتابع» — المعيار هو تشابك المشكلات.A blind "always one message" or "always sequential" rule — the criterion is whether the problems interact.

صحيح. السؤال ينص على التشابك («أي إصلاح يؤثر على الاثنين الآخرين») — وهذه حالة الرسالة الواحدة المفصّلة بالضبط: يرى Claude التفاعل الثلاثي ويصمم حلاً متوازناً. التتابع (A وC) يجعله يُصلح التسريب فيكسر إعادة المحاولة والعكس، وإعادة التوليد (D) مقامرة بلا توجيه.
Correct. The question states the interaction ("any fix affects the other two") — exactly the single-detailed-message case: Claude sees the three-way interplay and designs a balanced repair. Sequencing (A and C) has it fixing the leak while breaking the retry and vice versa, and regeneration (D) is an unguided gamble.

  • الحالة الحدية تُصلَح بمدخل كاسر محدد + مخرج متوقع محدد.An edge case is fixed with the exact breaking input + the exact expected output.
  • مشكلات متشابكة → رسالة واحدة مفصّلة؛ مستقلة → تتابع خطوة بخطوة.Interacting problems → one detailed message; independent → step-by-step sequence.
