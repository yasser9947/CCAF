دمج Claude Code في CI/CD Integrating Claude Code into CI/CD

في خط الأنابيب ما فيه إنسان يجاوب الأسئلة: تشغيل غير تفاعلي، إخراج تفهمه الآلة، ومراجِع مستقل عن المولِّد. In a pipeline there is no human to answer prompts: non-interactive runs, machine-readable output, and a reviewer independent of the generator.

وش بتتعلمWhat you'll learn

  • تشغيل Claude Code في الأتمتة بالعلم -p (أو --print) — الوضع غير التفاعلي الذي يمنع تعليق الوظيفةRunning Claude Code in automation with the -p (or --print) flag — the non-interactive mode that stops jobs hanging
  • فرض إخراج منظّم قابل للتحليل الآلي بـ --output-format json مع --json-schema — لنشر النتائج تعليقاتٍ مضمّنة على الـ PREnforcing machine-parseable structured output with --output-format json plus --json-schema — for posting findings as inline PR comments
  • تزويد Claude في الـ CI بسياق المشروع عبر CLAUDE.md: معايير الاختبار، اتفاقيات الـ fixtures، ومعايير المراجعةFeeding CI-invoked Claude project context via CLAUDE.md: testing standards, fixture conventions, review criteria
  • عزل الجلسات: لماذا الجلسة التي ولّدت الكود أضعف في مراجعته من نسخة مستقلة بلا سياق التوليدSession isolation: why the session that generated the code reviews it worse than an independent instance without the generation context
  • منع التكرار: تضمين نتائج المراجعة السابقة عند إعادة التشغيل (الجديد وغير المعالَج فقط)، وتوفير ملفات الاختبار الموجودة كي لا تُقترح سيناريوهات مكررةPreventing duplication: including prior review findings on re-runs (new or unaddressed only), and providing existing test files so duplicate scenarios are not suggested

الوضع غير التفاعلي: العلم -p Non-interactive mode: the -p flag

المشهد الكلاسيكي في أسئلة الاختبار: سكربت CI يشغّل claude "Analyze this pull request..." والوظيفة تتعلق إلى ما لا نهاية — والسجلات تكشف أن Claude Code ينتظر إدخالاً تفاعلياً لن يأتي أبداً، لأن ما من إنسان على الطرف الآخر.

التصحيح الموثّق واحد: العلم -p (أو --print). به يعالج Claude Code الطلب، يطبع النتيجة إلى stdout، ويخرج — بلا أي انتظار لإدخال. هذا هو نمط التشغيل الوحيد الصالح داخل أي خط أنابيب آلي.

واحذر الخيارات المزيفة التي تحوم حول هذا السؤال: متغير بيئة CLAUDE_HEADLESS=true غير موجود، وعلم --batch غير موجود، وتحويل الإدخال بـ < /dev/null حيلة نظام تشغيل لا تعالج صيغة أمر Claude Code نفسها.

The classic exam scene: a CI script runs claude "Analyze this pull request..." and the job hangs indefinitely — logs reveal Claude Code waiting for interactive input that will never come, because there is no human on the other end.

The documented fix is singular: the -p (or --print) flag. With it, Claude Code processes the prompt, prints the result to stdout, and exits — never waiting for input. It is the only correct run mode inside any automated pipeline.

And beware the fake options circling this question: a CLAUDE_HEADLESS=true environment variable does not exist, a --batch flag does not exist, and redirecting stdin with < /dev/null is an OS workaround that never addresses Claude Code's own command syntax.

كل حلقة في السلسلة لها علمها: -p يمنع التعليق، والمخطط يضمن شكل الإخراج، فيُنشر آلياً بثقة. Each link has its flag: -p prevents the hang, the schema guarantees the output shape, so posting is automated with confidence.

مثال: خطوة المراجعة في GitHub ActionsExample: the review step in GitHub Actions
name: AI Code Review
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run Claude Code review (non-interactive)
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          # -p prevents the pipeline from hanging on interactive input.
          # --json-schema forces machine-parseable, structured findings.
          # CLAUDE.md in the repo supplies review criteria + test standards.
          claude -p "Review the changes in this PR against our checklist.
                     Prior findings are in prior-findings.json: report ONLY
                     new or still-unaddressed issues." \
            --output-format json \
            --json-schema review-schema.json > findings.json

      - name: Post findings as inline PR comments
        run: node scripts/post-review.js findings.json
لمحة سريعةQuick insight
ثلاث عبارات تحسم ثلاثة أجوبة: «الوظيفة تنتظر إدخالاً» = -p. «نشر آلي للنتائج» = --output-format json + --json-schema. «المراجعة ضعيفة على كودها» = نسخة مراجعة مستقلة.
Three phrases settle three answers: "job waiting for input" = -p. "automated posting of findings" = --output-format json + --json-schema. "weak review of its own code" = an independent review instance.

إخراج تفهمه الآلة: json و json-schema Output machines understand: json & json-schema

مخرجات المراجعة في CI لا يقرؤها إنسان أولاً — يقرؤها سكربت ينشرها تعليقات مضمّنة على الـ PR. النص الحر يجعل هذا التحليل هشاً وينكسر مع كل تغيير صياغة. الحل من علمين متكاملين:

  • --output-format json — يجعل الإخراج بنية JSON بدل نص حر.
  • --json-schema review-schema.json — يفرض شكل تلك البنية: الحقول وأنواعها وقيم الـ enum المسموحة، فيضمن أن كل نتيجة فيها file وline وseverity وmessage — جاهزة للنشر الآلي مباشرة.

CI review output is not read by a human first — it is read by a script that posts it as inline PR comments. Free text makes that parsing brittle, breaking with every phrasing change. The fix is two complementary flags:

  • --output-format json — makes the output JSON structure instead of free text.
  • --json-schema review-schema.json — enforces that structure's shape: fields, types, and allowed enum values, guaranteeing every finding carries file, line, severity, and message — ready for direct automated posting.
مثال: review-schema.jsonExample: review-schema.json
{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "file":     { "type": "string" },
          "line":     { "type": "integer" },
          "severity": { "type": "string", "enum": ["blocker", "warning", "nit"] },
          "message":  { "type": "string" }
        },
        "required": ["file", "line", "severity", "message"]
      }
    }
  },
  "required": ["findings"]
}

تنبيهWarning
لا تخلط بين تشغيل claude -p في CI وبين Message Batches API: الدفعات توفّر 50% لكنها قد تستغرق حتى 24 ساعة بلا ضمان زمني — مناسبة للتقارير الليلية المتسامحة مع التأخير، وغير مناسبة أبداً لفحص pre-merge يحجب الدمج وينتظره المطورون. طابق الأداة مع متطلبات الزمن: حاجز يحجب = استدعاء متزامن، تحليل ليلي = دفعات.
Do not confuse running claude -p in CI with the Message Batches API: batches save 50% but may take up to 24 hours with no latency SLA — right for overnight, delay-tolerant reports and never right for a blocking pre-merge check developers wait on. Match the tool to the latency requirement: blocking gate = synchronous call, overnight analysis = batches.

السياق والعزل: من يراجع، وماذا يعرف؟ Context & isolation: who reviews, and what do they know?

ثلاثة قرارات سياق تصنع جودة المراجعة والتوليد في CI:

  • عزل الجلسات: الجلسة التي ولّدت الكود تحمل سياق تبريراتها، فهي أقل ميلاً للتشكيك في قراراتها عند مراجعة تغييراتها. نسخة مستقلة بلا سياق التوليد تراجع بموضوعية أعلى وتلتقط ما تحيّزت عنه المولِّدة.
  • إعادة التشغيل بلا تكرار: عند المراجعة بعد commits جديدة، ضمّن نتائج المراجعة السابقة في السياق واطلب الإبلاغ عن الجديد أو غير المعالَج فقط — وإلا أغرق البوت الـ PR بنفس التعليقات في كل تشغيل.
  • توليد اختبارات بلا تكرار: وفّر ملفات الاختبار الموجودة في السياق كي لا تُقترح سيناريوهات مغطاة أصلاً، ووثّق في CLAUDE.md معايير الاختبار ومعايير «الاختبار القيّم» والـ fixtures المتاحة — فترتفع جودة التوليد وتقل الاختبارات منخفضة القيمة.

Three context decisions make or break CI review and generation quality:

  • Session isolation: the session that generated the code carries its own reasoning context, so it is less likely to question its own decisions when reviewing its changes. An independent instance without the generation context reviews more objectively and catches what the generator was biased past.
  • Re-runs without duplication: when reviewing after new commits, include the prior review findings in context and instruct Claude to report only new or still-unaddressed issues — otherwise the bot floods the PR with the same comments every run.
  • Test generation without duplication: provide the existing test files in context so already-covered scenarios are not re-suggested, and document in CLAUDE.md the testing standards, what makes a test valuable, and the available fixtures — raising generation quality and cutting low-value tests.

مفهوم أساسيKey concept
جودة Claude في CI = تشغيل صحيح + إخراج منظّم + سياق صحيح. التشغيل بـ -p، والإخراج بـ json + schema، والسياق ثلاثي: CLAUDE.md للمعايير، النتائج السابقة لمنع التكرار، والاختبارات الموجودة لمنع الاقتراحات المكررة — مع مراجعٍ معزول عن المولِّد.
Claude quality in CI = correct invocation + structured output + correct context. Invocation via -p, output via json + schema, and three-part context: CLAUDE.md for standards, prior findings to prevent duplicates, and existing tests to prevent repeated suggestions — with a reviewer isolated from the generator.

فخ الاختبارExam trap

  • الفخ: حلّ التعليق بـ CLAUDE_HEADLESS=true أو --batch أو < /dev/null. الصح: -p — الأول والثاني غير موجودين أصلاً، والثالث حيلة نظام لا تعالج صيغة الأمر.
    Trap: fixing the hang with CLAUDE_HEADLESS=true, --batch, or < /dev/null. Reality: -p — the first two do not exist, and the third is an OS workaround that never addresses the command syntax.
  • الفخ: «اجعل نفس الجلسة المولِّدة تراجع لأنها تعرف الكود أفضل». الصح: معرفتها هي انحيازها — النسخة المستقلة بلا سياق التوليد تراجع أدق.
    Trap: "have the generating session review since it knows the code best." Reality: its knowledge is its bias — the independent instance without generation context reviews more sharply.
  • الفخ: مراجعة 14 ملفاً بنتائج متناقضة → «نموذج أكبر بنافذة أكبر» أو «إجماع 2 من 3 تشغيلات» أو «ألزم المطورين بتقسيم الـ PR». الصح: قسّم المراجعة نفسها: تمريرة لكل ملف للمشاكل المحلية + تمريرة تكامل للتدفق العابر للملفات — النافذة الأكبر لا تصلح تخفف الانتباه، والإجماع يكتم الأخطاء الملتقطة تقطعاً.
    Trap: a 14-file review with contradictory results → "a bigger model with a larger window", "2-of-3 run consensus", or "force developers to split PRs". Reality: split the review itself: a per-file pass for local issues + an integration pass for cross-file flow — a larger window does not fix attention dilution, and consensus suppresses intermittently-caught real bugs.

مثال من الحياة: المدقق الخارجي وماكينة البيعReal-life example: the external auditor and the vending machine

ما في شركة محترمة تخلي محاسبها يدقق دفاتره بنفسه — اللي كتب القيود عنده ألف مبرر جاهز لكل رقم فيها. التدقيق الحقيقي يجي من مدقق خارجي ما شارك في كتابتها ولا يجامل قراراتها: هذا هو عزل جلسة المراجعة عن جلسة التوليد. والمدقق ما يسلّمك خواطر إنشائية — يعبّي نموذجاً معتمداً ببنود محددة (الملف، البند، درجة الخطورة، الملاحظة): هذا هو --json-schema.

أما تشغيل Claude في الخط الآلي بـ -p فهو ماكينة البيع الذاتية: تضغط، تستلم، تمشي. البديل موظف يسألك «تبي الحجم الكبير؟» — والطابور خلفك (الـ pipeline) واقف ينتظر جواباً لن يأتي. وفي المراجعة الشهرية التالية، المدقق الشاطر يفتح تقرير الشهر الماضي أولاً ويعلّق فقط على الجديد وغير المعالَج — ما يعيد كتابة نفس الملاحظات كل شهر.

No serious company lets its accountant audit their own books — whoever wrote the entries has a ready justification for every number. Real assurance comes from an external auditor who took no part in writing them and owes their decisions nothing: that is isolating the review session from the generation session. And the auditor does not hand you free-form musings — they fill in an approved form with fixed fields (file, item, severity, note): that is --json-schema.

Running Claude in the automated line with -p is the vending machine: press, collect, go. The alternative is a clerk asking "want the large size?" — with the queue behind you (the pipeline) stuck waiting for an answer that will never come. And at next month's review, the sharp auditor opens last month's report first and comments only on what is new or still unfixed — never rewriting the same notes every month.

سير عملكم يجعل جلسة Claude Code التي ولّدت الكود تراجع تغييراتها بنفسها في نهاية المهمة، لكن المراجعات نادراً ما تكتشف مشاكل حقيقية رغم وجودها. ما التفسير والحل الأصح؟ Your workflow has the Claude Code session that generated the code review its own changes at the end of the task, but the reviews rarely catch real issues even when they exist. What is the correct diagnosis and fix?

صحيح. هذا مبدأ عزل الجلسات في الدليل: الجلسة التي ولّدت الكود تحتفظ بسياق استدلالها فتكون أقل ميلاً للتشكيك في قراراتها — والنسخة المستقلة تراجع أدق. المشكلة ليست قدرة النموذج (A) ولا حزم الصياغة (B — تعليمات «شكك في كل شيء» لا تزيل انحياز السياق)، وتكبير النافذة (D) يعمّق المشكلة بإبقاء سياق التوليد حاضراً.
Correct. This is the guide's session-isolation principle: the session that generated the code retains its reasoning context and is less likely to question its own decisions — an independent instance reviews more sharply. The problem is not model capability (A) nor prompt sternness (B — "question everything" instructions do not remove context bias), and a bigger window (D) deepens the problem by keeping the generation context present.
الإجابة الصحيحة C. «المراجعة الذاتية ضعيفة» عرض لسبب واحد في هذا الدومين: سياق التوليد يحابي قراراته. العلاج معماري لا صياغي — نسخة مراجعة مستقلة بلا ذلك السياق.
The correct answer is C. "Weak self-review" is a symptom with one cause in this domain: the generation context favors its own decisions. The cure is architectural, not phrasing — an independent review instance without that context.
