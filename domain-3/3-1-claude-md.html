تدرّج CLAUDE.md والتنظيم المعياري CLAUDE.md hierarchy & modular organization

أكثر أسئلة الدومين شيوعاً تبدأ من هنا: إعداد في المستوى الغلط يعني فريقاً كاملاً يشتغل بدون معاييره. The domain's most common questions start here: configuration at the wrong level means a whole team working without its standards.

ثلاثة مستويات تتراكم ولا تتصادم Three levels that stack, not clash

ملفات CLAUDE.md هي «الذاكرة» التي يقرأها Claude Code تلقائياً في بداية كل جلسة. تتدرّج على ثلاثة مستويات، وكل مستوى يُضاف إلى ما قبله — لا يستبدله:

  • مستوى المستخدم — ~/.claude/CLAUDE.md: تفضيلاتك الشخصية على جهازك أنت. خارج المستودع تماماً، فلا يتتبعه Git ولا يراه زملاؤك أبداً.
  • مستوى المشروع — .claude/CLAUDE.md أو CLAUDE.md في الجذر: معايير الفريق المشتركة. يدخل التحكم بالإصدارات، فيستلمه كل من يستنسخ المستودع أو يسحب آخر التغييرات.
  • مستوى المجلد — ملف CLAUDE.md داخل مجلد فرعي (مثل frontend/): يُحمَّل عند العمل داخل ذلك المجلد فقط، فيحمل اتفاقيات تلك المنطقة تحديداً.

هذا التصميم يعني أن سؤال «وين أكتب هذا الإعداد؟» له إجابة واحدة صحيحة دائماً بحسب من يجب أن يستفيد منه — وهذا بالضبط ما يختبره الدومين.

CLAUDE.md files are the "memory" Claude Code reads automatically at the start of every session. They cascade across three levels, and each level adds to — never replaces — the ones above it:

  • User level — ~/.claude/CLAUDE.md: your personal preferences on your own machine. Entirely outside the repository, so Git never tracks it and teammates never see it.
  • Project level — .claude/CLAUDE.md or a root CLAUDE.md: shared team standards. Version-controlled, so everyone who clones or pulls receives it.
  • Directory level — a CLAUDE.md inside a subdirectory (e.g. frontend/): loaded only when working within that directory, carrying that area's specific conventions.

This design means "where do I write this instruction?" always has exactly one right answer, determined by who must benefit from it — which is precisely what this domain tests.

المستويات تتراكم في سياق الجلسة — الأعمق يضيف تخصيصاً، ولا يمسح ما فوقه. Levels accumulate into session context — deeper levels add specificity, never erasing what is above.

مفهوم أساسيKey concept
القاعدة الذهبية: ما يجب أن يشاركه الفريق = مستوى المشروع (داخل Git). ما يخصّك أنت وحدك = مستوى المستخدم (~/.claude/). الخلط بينهما هو مصدر سيناريو «كل شي يشتغل عندي، وما شي يشتغل عند الزميل الجديد».
Golden rule: what the team must share = project level (in Git). What is yours alone = user level (~/.claude/). Confusing the two is the source of every "works on my machine, not for the new teammate" scenario.

التقسيم المعياري: @import و .claude/rules/ Modular organization: @import & .claude/rules/

مع نمو المشروع، ملف CLAUDE.md الواحد يتحوّل بسرعة إلى وحش من 2,000 سطر لا أحد يجرؤ على تعديله. عندك أداتان للتقسيم:

  • @import: يسحب ملفات خارجية داخل CLAUDE.md. قوته في الانتقائية — في الـ monorepo، كل حزمة تستورد ملفات المعايير التي تخصّها فقط، بناءً على معرفة مشرف الحزمة بمجاله، بدل تحميل كل شيء للجميع.
  • .claude/rules/: مجلد ملفات موضوعية مركّزة (testing.md، api-conventions.md، deployment.md) بديلاً عن الملف الواحد المتضخّم. كل ملف مسؤول عن موضوع واحد، فيسهل تعديله ومراجعته في PR مستقل.

الفرق الجوهري بينهما: @import تركيبٌ داخل ملف يحدد ما يُسحب له، بينما .claude/rules/ بنية مجلد تنظّم القواعد بالموضوع — وفي الدرس 3.3 بتشوف كيف تكتسب ملفات rules قوة إضافية بترويسة paths.

As a project grows, a single CLAUDE.md quickly becomes a 2,000-line monster nobody dares touch. You have two splitting tools:

  • @import: pulls external files into CLAUDE.md. Its power is selectivity — in a monorepo, each package imports only the standards files relevant to it, based on the maintainer's domain knowledge, instead of loading everything for everyone.
  • .claude/rules/: a directory of focused topic files (testing.md, api-conventions.md, deployment.md) replacing one bloated file. Each file owns one topic, so it is easy to edit and review in its own PR.

The core difference: @import is syntax inside a file choosing what gets pulled in, while .claude/rules/ is a directory structure organizing rules by topic — and in lesson 3.3 you will see rules files gain extra power through paths frontmatter.

مثال: CLAUDE.md معياري بـ @importExample: modular CLAUDE.md with @import
# Payments Service — Project Standards

## Team-wide rules (always apply)
- TypeScript strict mode across every package.
- Never commit directly to `main`; open a PR.
- Money is always integer cents, never floats.

## Modular imports (pull in only what this package needs)
@./.claude/rules/api-conventions.md
@./docs/error-handling-standards.md
@../shared/logging-standards.md

# Each maintainer imports the standards relevant to their domain,
# keeping this file small instead of a 2,000-line monolith.
لمحة سريعةQuick insight
لما يقول السؤال «الأكثر قابلية للصيانة / most maintainable» عن معايير كثيرة متنوعة، فالإجابة نادراً ما تكون «ملف واحد كبير» — التقسيم بـ @import أو .claude/rules/ هو النمط المكافأ.
When a question says "most maintainable" about many varied standards, the answer is rarely "one big file" — splitting via @import or .claude/rules/ is the rewarded pattern.

التشخيص: /memory وأعطال التدرّج Diagnosis: /memory & hierarchy failures

عطلان يتكرران في الأسئلة (وفي الواقع):

  • «الزميل الجديد ما تطبّق أداته المعايير»: التشخيص الأول دائماً — هل المعايير في ~/.claude/CLAUDE.md (مستوى المستخدم)؟ إذا نعم فهي ببساطة غير موجودة في المستودع أصلاً. العلاج: انقلها لمستوى المشروع. لا الملف تالف، ولا يحتاج /clear، ولا مشكلة صلاحيات.
  • «السلوك غير متسق بين الجلسات أو الأجهزة»: شغّل /memory لعرض ملفات الذاكرة المُحمَّلة فعلاً في هذه الجلسة. غالباً بتكتشف أن جلسةً تحمّل ملف مجلد فرعي وجلسةً أخرى لا، أو أن ملفاً شخصياً يضيف تعليمات عند مطوّر دون الآخر.

انتبه: /memory أداة عرض وتشخيص — تريك ما هو محمَّل، ولا «تزامن» شيئاً بين الأجهزة ولا تصلح شيئاً بنفسها.

Two failures recur in questions (and in real life):

  • "The new teammate's tool does not apply the standards": the first diagnostic is always — are the standards in ~/.claude/CLAUDE.md (user level)? If so, they simply do not exist in the repository at all. The cure: move them to project level. The file is not corrupt, /clear will not help, and it is not a permissions issue.
  • "Behavior is inconsistent across sessions or machines": run /memory to display which memory files are actually loaded in this session. You will often find one session loading a subdirectory file another does not, or a personal file adding instructions for one developer only.

Note carefully: /memory is a viewer and diagnostic — it shows what is loaded; it never "syncs" anything across machines and fixes nothing by itself.

تنبيهWarning
لا تخلط بين /memory (يعرض ملفات الذاكرة المُحمَّلة) و/compact (يضغط سياق المحادثة الطويلة). في أسئلة التشخيص، /compact إجابة فخ لأنه لا علاقة له بالإعدادات إطلاقاً.
Do not confuse /memory (shows loaded memory files) with /compact (compresses long conversation context). In diagnosis questions, /compact is a trap answer with no relation to configuration at all.

فخ الاختبارExam trap

  • الفخ: «الزميل الجديد ما يستلم المعايير → الملف تالف / يحتاج إعادة تثبيت / شغّل /clear». الصح: المعايير في مستوى المستخدم الذي لا يتتبعه Git — انقلها إلى مستوى المشروع.
    Trap: "new teammate is not getting the standards → the file is corrupt / reinstall / run /clear." Reality: the standards sit at user level, which Git never tracks — move them to project level.
  • الفخ: اعتبار /memory أمر «مزامنة» ينقل الذاكرة بين الأجهزة. الصح: هو عارض تشخيصي فقط — يريك أي ملفات محمَّلة الآن.
    Trap: treating /memory as a "sync" command that moves memory between machines. Reality: it is a diagnostic viewer only — it shows which files are loaded right now.
  • الفخ: حشر كل المعايير في ملف CLAUDE.md واحد عملاق «ليكون كل شيء في مكان واحد». الصح: قسّم بـ @import أو .claude/rules/ لتبقى المعايير قابلة للصيانة والمراجعة.
    Trap: cramming every standard into one giant CLAUDE.md "so everything is in one place." Reality: split with @import or .claude/rules/ so standards stay maintainable and reviewable.

مثال من الحياة: المكتب الهندسيReal-life example: the engineering office

تخيّل مكتباً هندسياً. CLAUDE.md في مستوى المشروع هو دليل المعايير المعلّق على جدار قاعة المشروع: أي مهندس ينضم يشوفه فوراً ويلتزم به — لأنه جزء من القاعة نفسها (المستودع). أما ~/.claude/CLAUDE.md فهو دفتر ملاحظاتك الشخصي في دُرج مكتبك: مفيد لك، لكن المهندس الجديد ما يعرف بوجوده أصلاً.

ولما يكبر دليل المعايير، ما يصير كتاباً واحداً بألف صفحة — يتوزّع إلى فصول مستقلة (سلامة، كهرباء، تشطيبات = .claude/rules/)، وكل قسم في المكتب يستعير الفصول التي تخصّه فقط (@import). وسؤال «أي فصول موجودة على طاولتك الآن؟» يجاوبه أمين المكتبة: /memory.

Picture an engineering office. A project-level CLAUDE.md is the standards manual pinned to the project-room wall: any engineer who joins sees it immediately and follows it — because it belongs to the room itself (the repository). But ~/.claude/CLAUDE.md is your personal notebook in your desk drawer: useful to you, invisible to the new engineer who never knew it existed.

And when the manual grows, it does not become one thousand-page book — it splits into independent chapters (safety, electrical, finishing = .claude/rules/), and each department borrows only the chapters that concern it (@import). As for "which chapters are on your desk right now?" — the librarian answers that: /memory.

إجابات فخ تستبعدها فوراًTrap answers to eliminate
  • «شغّل /memory ليزامن» أو «شغّل /compact ليعيد التحميل» — الأول عارض والثاني ضاغط سياق."Run /memory to sync" or "run /compact to reload" — one is a viewer, the other compresses context.
  • «انسخ الملف يدوياً لكل زميل» — يشتغل مرة ثم ينحرف؛ ليس حلاً جذرياً يُدار بالإصدارات."Copy the file manually to each teammate" — works once then drifts; not a version-controlled root fix.

Correct. A cross-project personal preference = user level ~/.claude/CLAUDE.md: it applies in all her sessions and never enters any repository, so it is imposed on nobody. Every other option lives in the repo and reaches the whole team.

ملف CLAUDE.md في مشروعكم وصل إلى 2,000 سطر تخلط معايير الاختبار باتفاقيات الـ API بإجراءات النشر، وصار كل تعديل عليه مغامرة. ما الحل الأكثر قابلية للصيانة؟ Your project's CLAUDE.md has hit 2,000 lines mixing testing standards, API conventions, and deployment procedures, and every edit has become an adventure. What is the most maintainable fix?

صحيح. .claude/rules/ هو البديل المصمَّم للملف المتضخّم: كل موضوع في ملف مستقل يسهل تعديله ومراجعته. إعادة الترتيب (A) تجميل لا يعالج التضخم، والنسخ (B) يضاعف مشكلة الصيانة، والمهارات (D) للاستدعاء عند الطلب — لكن هذه معايير دائمة يجب أن تبقى محمَّلة تلقائياً.
Correct. .claude/rules/ is the designed alternative to a bloated file: each topic in its own file, easy to edit and review. Reorganizing (A) is cosmetic and leaves the bloat, duplicating (B) multiplies the maintenance problem, and skills (D) are for on-demand invocation — but these are always-on standards that must stay automatically loaded.
الإجابة الصحيحة C. الدليل الرسمي يذكر هذا النمط حرفياً: تقسيم CLAUDE.md الكبير إلى ملفات موضوعية في .claude/rules/. المعايير الدائمة لا تتحول لمهارات (تُستدعى يدوياً)، والنسخ المكرر ينحرف مع الوقت.
The correct answer is C. The official guide names this pattern explicitly: splitting a large CLAUDE.md into topic files under .claude/rules/. Always-on standards should not become skills (manually invoked), and duplicated copies drift over time.

يشتكي مطوّر أن Claude Code يطبّق معايير الاختبار في بعض الجلسات ويتجاهلها في أخرى داخل نفس المشروع. ما الخطوة التشخيصية الأولى؟ A developer complains Claude Code applies the testing standards in some sessions and ignores them in others within the same project. What is the first diagnostic step?

صحيح. /memory هو أداة التشخيص المخصصة لهذا بالضبط: يعرض الملفات المُحمَّلة في الجلسة الحالية، فيكشف فرقاً مثل جلسة بدأت داخل مجلد فرعي فحمّلت ملفه وأخرى لا. الضغط (/compact) وإعادة الصياغة وإعادة التثبيت كلها تخمين قبل التشخيص.
Correct. /memory is the diagnostic built for exactly this: it lists the files loaded in the current session, revealing differences such as one session starting inside a subdirectory (loading its file) while another did not. Compacting, rewording, and reinstalling are all guesses made before diagnosing.
الإجابة الصحيحة D. «سلوك غير متسق بين الجلسات» هي الإشارة المعيارية لأمر /memory: تحقّق أولاً أي ملفات ذاكرة محمَّلة، ثم عالج السبب. لا تقفز لحلول عمياء قبل معرفة ما هو محمَّل فعلاً.
The correct answer is D. "Inconsistent behavior across sessions" is the canonical cue for /memory: first verify which memory files are loaded, then fix the cause. Never jump to blind fixes before knowing what is actually loaded.
