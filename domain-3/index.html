ملخص الدومين Domain summary

هذا الدومين يقيس شيئاً واحداً في جوهره: هل تعرف وين يعيش كل إعداد، ومتى يُحمَّل، ومن يستفيد منه؟ معايير الفريق في مستوى المشروع (تدخل Git)، تفضيلاتك الشخصية في مستوى المستخدم (~/.claude/)، الاتفاقيات المنتشرة عبر المجلدات في قواعد glob، وسير العمل عند الطلب في أوامر ومهارات. فوقها قرارات التشغيل: وضع التخطيط للمهام المعمارية، التنفيذ المباشر للتغييرات الواضحة، و-p مع إخراج منظّم داخل الـ CI.

العقلية التي يكافئها الاختبار: الحتمية قبل الاحتمالية، والنطاق الصحيح قبل الحل الأذكى. السؤال يعطيك موقفاً واقعياً (زميل جديد ما تستلم أدواته المعايير، وظيفة CI معلّقة، ترحيل يمس 45 ملفاً) وأربعة خيارات كلها «تبدو منطقية» — الإجابة الصحيحة دائماً هي الآلية المصمَّمة لهذا الغرض بالضبط، لا الحل الالتفافي ولا الآلية غير الموجودة أصلاً.

At its core this domain measures one thing: do you know where each piece of configuration lives, when it loads, and who benefits from it? Team standards belong at project level (in Git), personal preferences at user level (~/.claude/), conventions spread across directories in glob rules, and on-demand workflows in commands and skills. On top of that sit the operational decisions: plan mode for architectural tasks, direct execution for well-scoped changes, and -p with structured output inside CI.

The mindset it rewards: determinism over probability, and correct scope over clever workaround. Each question hands you a realistic situation (a new teammate whose tool ignores the standards, a hanging CI job, a migration touching 45 files) and four options that all "sound reasonable" — the right answer is always the mechanism designed for exactly that purpose, never the workaround and never a mechanism that does not exist.

كيف يظهر في الاختبار How it shows up on the exam

أنماط الإجابات الفخ المتكررة في هذا الدومين — لو ميّزتها، نصف السؤال انحل:
The recurring distractor patterns in this domain — recognize them and half the question is solved:
  • النطاق الغلط: إعداد للفريق محطوط في مستوى المستخدم (~/.claude/) — أصل مشكلة «يشتغل عندي وما يشتغل عند الزميل الجديد». الحل دائماً: انقله لمستوى المشروع.
    Wrong scope: team configuration placed at user level (~/.claude/) — the root of "works on my machine, not for the new teammate." The fix is always: move it to project level.
  • آليات غير موجودة: خيارات مثل .claude/config.json بمصفوفة أوامر، أو CLAUDE_HEADLESS=true، أو علم --batch — تبدو معقولة لكنها مخترعة. احفظ الآليات الحقيقية واستبعد الباقي.
    Nonexistent mechanisms: options like a .claude/config.json commands array, CLAUDE_HEADLESS=true, or a --batch flag — plausible-sounding but invented. Know the real mechanisms and eliminate the rest.
  • احتمالي بدل حتمي: «خلّ Claude يستنتج القسم المناسب من العناوين» أو «سوّ مهارة لكل نوع كود» حين يطلب السؤال تطبيقاً تلقائياً — قواعد glob الصريحة هي الحتمية.
    Probabilistic over deterministic: "let Claude infer the right section from headers" or "make a skill per code type" when the question demands automatic application — explicit glob rules are the deterministic answer.
  • تأجيل التخطيط: «ابدأ مباشرة وبدّل لوضع التخطيط لو ظهر تعقيد» — بينما التعقيد مذكور أصلاً في المتطلبات (عشرات الملفات، حدود خدمات). التعقيد المعلوم يعني: خطّط من البداية.
    Deferred planning: "start direct and switch to plan mode if complexity emerges" — when the complexity is already stated in the requirements (dozens of files, service boundaries). Known complexity means: plan from the start.
  • فخاخ الـ CI: نفس الجلسة تراجع كودها («لأنها تعرف الكود»)، حِيَل مثل < /dev/null بدل -p، وتحليل نص حر بدل --output-format json مع --json-schema.
    CI traps: the same session reviewing its own code ("because it knows the code"), workarounds like < /dev/null instead of -p, and parsing free text instead of --output-format json with --json-schema.

3.2

فريقك يريد أمر /security-check يشغّل قائمة الفحص الأمني الموحّدة، ويكون متاحاً تلقائياً لأي مطوّر يستنسخ المستودع أو يسحب آخر التغييرات. وين تنشئ ملف الأمر؟ Your team wants a /security-check command that runs the standard security checklist, automatically available to every developer who clones the repo or pulls the latest changes. Where do you create the command file?

صحيح. أوامر المشروع في .claude/commands/ تدخل التحكم بالإصدارات، فتصل تلقائياً لكل من يستنسخ أو يسحب. ~/.claude/commands/ شخصي ولا يُشارَك، وCLAUDE.md للتعليمات والسياق لا لتعريف الأوامر، ومصفوفة commands في config.json آلية غير موجودة أصلاً.
Correct. Project commands in .claude/commands/ are version-controlled, so they reach everyone automatically on clone/pull. ~/.claude/commands/ is personal and unshared, CLAUDE.md is for instructions and context rather than command definitions, and a commands array in config.json is a mechanism that does not exist.
الإجابة الصحيحة B. كلمة «يستنسخ المستودع» مفتاح السؤال: المطلوب مشاركة عبر Git، وهذا بالضبط دور .claude/commands/ داخل المشروع. المجلد الشخصي ~/.claude/commands/ لا يُشارَك، وCLAUDE.md لا يعرّف أوامر، وconfig.json بمصفوفة أوامر آلية مخترعة.
The correct answer is B. "Clones the repo" is the key phrase: you need sharing via Git, which is exactly what .claude/commands/ inside the project provides. The personal ~/.claude/commands/ is not shared, CLAUDE.md does not define commands, and a config.json commands array is invented.

3.4

كُلّفت بإعادة هيكلة تطبيق المدفوعات الموحّد (monolith) إلى ثلاث خدمات مصغّرة. التغيير يمس عشرات الملفات ويتطلب قرارات حول حدود الخدمات وتبعيات الوحدات. كيف تبدأ؟ You are assigned to restructure the monolithic payments application into three microservices. The change touches dozens of files and requires decisions about service boundaries and module dependencies. How do you start?

صحيح. تغيير واسع + قرارات معمارية + مقاربات متعددة = وضع التخطيط بالضبط. الاستكشاف والتصميم قبل الالتزام يمنعان إعادة عمل مكلفة. الخيار A يخاطر باكتشاف التبعيات متأخراً، وB يفترض أنك تعرف البنية الصحيحة بدون استكشاف، وD يتجاهل أن التعقيد مذكور في المتطلبات أصلاً — ليس مفاجأة محتملة.
Correct. Large-scale change + architectural decisions + multiple approaches = exactly what plan mode is for. Exploring and designing before committing prevents costly rework. Option A risks discovering dependencies late, B assumes you already know the right structure without exploring, and D ignores that the complexity is already stated in the requirements — it is not a possible surprise.
الإجابة الصحيحة C. المؤشرات الثلاثة كلها حاضرة: عشرات الملفات، قرارات حدود خدمات، ومقاربات متعددة صالحة — هذا تعريف مهمة وضع التخطيط. «ابدأ وبدّل لاحقاً» فخ كلاسيكي: التعقيد معلوم مسبقاً، فالتخطيط يبدأ من أول خطوة لا بعد ما تتورّط.
The correct answer is C. All three signals are present: dozens of files, service-boundary decisions, and multiple valid approaches — the definition of a plan-mode task. "Start and switch later" is the classic trap: the complexity is known upfront, so planning starts at step one, not after you are already committed.

3.1

زميل جديد استنسخ المستودع، لكن Claude Code عنده يتجاهل معايير الترميز التي تعمل عندك بشكل ممتاز. تكتشف أن المعايير كلها مكتوبة في ~/.claude/CLAUDE.md على جهازك. ما الحل الجذري؟ A new teammate cloned the repo, but their Claude Code ignores the coding standards that work perfectly for you. You discover the standards all live in ~/.claude/CLAUDE.md on your machine. What is the root-cause fix?

صحيح. المشكلة نطاق، لا عطل: مستوى المستخدم لا يتتبعه Git فلا يصل للزملاء أبداً. النقل لمستوى المشروع يجعل المعايير تُدار بالإصدارات وتصل لكل مستنسخ. /memory أداة عرض تشخيصية لا مزامنة، والنسخ اليدوي (B) يحل مؤقتاً لكنه يتكرر مع كل زميل جديد وينحرف مع الوقت، و/compact يضغط سياق الجلسة ولا علاقة له بالإعدادات.
Correct. This is a scoping problem, not a malfunction: user level is never tracked by Git, so it can never reach teammates. Moving to project level makes the standards version-controlled and delivered to every clone. /memory is a diagnostic viewer, not a sync; manual copying (B) works once but repeats for every new teammate and drifts over time; /compact compresses session context and has nothing to do with configuration.
الإجابة الصحيحة C. القاعدة الذهبية: ما يخص الفريق يعيش في مستوى المشروع (داخل Git)، وما يخصك أنت في مستوى المستخدم. /memory يعرض الملفات المحمَّلة فقط (تشخيص)، والنسخ اليدوي حل هش لا يُدار بالإصدارات، و/compact لضغط السياق لا للإعدادات.
The correct answer is C. Golden rule: what belongs to the team lives at project level (in Git); what is yours alone lives at user level. /memory only shows which files are loaded (a diagnostic), manual copying is fragile and unversioned, and /compact compresses context, not configuration.

3.3

ملفات ترحيل قواعد البيانات (*.sql) منتشرة داخل كل خدمة في المستودع (services/*/db/migrations/)، وتريد أن تُطبَّق اتفاقياتها تلقائياً عند تحرير أي ملف منها فقط — دون تحميلها في بقية الجلسات. ما الأنسب؟ Database migration files (*.sql) are spread inside every service in the repo (services/*/db/migrations/), and you want their conventions applied automatically only when editing one of them — without loading them in every other session. What fits best?

صحيح. الاتفاقية موزّعة عبر مجلدات كثيرة والمطلوب تطبيق «تلقائي» — هذا بالضبط دور قواعد glob: تُحمَّل فقط عند مطابقة الملف المحرَّر، فتوفّر السياق والـ tokens. النسخ المتكررة (B) عبء صيانة، والمهارة (C) استدعاء يدوي يناقض «تلقائياً»، والاستنتاج من العناوين (D) احتمالي غير مضمون.
Correct. The convention spans many directories and must apply "automatically" — exactly what glob rules do: they load only when the edited file matches, saving context and tokens. Duplicated copies (B) are a maintenance burden, a skill (C) needs manual invocation which contradicts "automatically", and header inference (D) is probabilistic and unreliable.
الإجابة الصحيحة A. إشارتا السؤال: «منتشرة» + «تلقائياً» = قاعدة مسارات بنمط glob. CLAUDE.md المجلدي مقيّد بموقعه ويتطلب نسخة في كل مجلد، والمهارات تُستدعى يدوياً، واستنتاج الأقسام غير حتمي.
The correct answer is A. The question's two signals — "spread" + "automatically" — point to a glob path rule. A directory CLAUDE.md is location-bound and needs a copy per folder, skills are manually invoked, and section inference is non-deterministic.

3.2

مهارة codebase-inventory تمسح مئات الملفات وتغرق المحادثة الرئيسية بمخرجاتها، وتريد أيضاً ضمان أنها لا تنفّذ أوامر Bash أبداً. أي تركيبة frontmatter تحقق الهدفين؟ A codebase-inventory skill scans hundreds of files and floods the main conversation with output, and you also want to guarantee it never runs Bash commands. Which frontmatter combination achieves both?

صحيح. حقلان مستقلان لمشكلتين مختلفتين: context: fork يعزل السياق (المخرجات الطويلة تبقى في الفرع ويرجع الملخص فقط)، وallowed-tools يقيّد الصلاحيات (استبعاد Bash). أحدهما لا يغني عن الآخر أبداً.
Correct. Two independent fields for two different problems: context: fork isolates context (verbose output stays in the fork, only the summary returns), while allowed-tools restricts privileges (excluding Bash). Neither ever substitutes for the other.
الإجابة الصحيحة D. الفخ الشائع خلط الحقلين: fork يحل تلوّث السياق ولا يمنع أي أداة، وallowed-tools يمنع الأدوات ولا يعزل المخرجات، وargument-hint مجرد تذكير بالمعطى المطلوب — لا علاقة له بالأمان أو السياق.
The correct answer is D. The common trap is conflating the two fields: fork solves context pollution and blocks no tools, allowed-tools blocks tools and isolates no output, and argument-hint merely prompts for a missing parameter — unrelated to safety or context.

3.6

سكربت في خط CI يشغّل claude "Review this PR for security issues" لكن الوظيفة تتعلق إلى ما لا نهاية، والسجلات تُظهر أن Claude Code ينتظر إدخالاً تفاعلياً. ما التصحيح الموثّق؟ A CI pipeline script runs claude "Review this PR for security issues" but the job hangs indefinitely, and logs show Claude Code waiting for interactive input. What is the documented fix?

صحيح. -p (أو --print) هو الوضع غير التفاعلي الموثّق: يعالج الطلب، يطبع النتيجة إلى stdout، ويخرج. CLAUDE_HEADLESS و--batch غير موجودين أصلاً، و< /dev/null حيلة نظام تشغيل لا تعالج صيغة أمر Claude Code.
Correct. -p (or --print) is the documented non-interactive mode: it processes the prompt, prints to stdout, and exits. CLAUDE_HEADLESS and --batch simply do not exist, and < /dev/null is an OS workaround that does not address Claude Code's command syntax.
الإجابة الصحيحة B. عبارة «ينتظر إدخالاً تفاعلياً» في أسئلة CI تعني دائماً العلم -p / --print. متغير CLAUDE_HEADLESS وعلم --batch مخترعان، وإعادة توجيه stdin حيلة لا تصلح صيغة الأمر.
The correct answer is B. "Waiting for interactive input" in a CI question always means the -p / --print flag. CLAUDE_HEADLESS and --batch are invented, and redirecting stdin is a workaround that does not fix the command syntax.

3.6

مراجعة CI تعمل عند كل commit جديد على الـ PR، لكنها تعيد نشر نفس الملاحظات القديمة في كل تشغيل فيغرق الـ PR بتعليقات مكررة. ما أفضل معالجة؟ Your CI review runs on every new commit to the PR, but it re-posts the same old findings on every run, flooding the PR with duplicate comments. What is the best fix?

صحيح. هذا النمط الموصى به: عند إعادة التشغيل بعد commits جديدة، مرّر النتائج السابقة واطلب «الجديد أو غير المعالَج فقط». الخيار A يفوّت مشاكل الكود الجديد كلياً، وC يخلط العشوائية بالسبب الحقيقي (غياب سياق المراجعة السابقة)، وD هش — نفس الملاحظة بصياغة مختلفة تفلت من المطابقة النصية، وهو يعالج العرَض لا السبب.
Correct. This is the recommended pattern: on re-runs after new commits, pass the prior findings and ask for "only new or still-unaddressed issues." Option A misses problems in the new code entirely, C confuses randomness with the real cause (missing prior-review context), and D is brittle — the same finding reworded slips past string matching, and it treats the symptom rather than the cause.
الإجابة الصحيحة B. المراجعة تكرّر الملاحظات لأنها لا تعرف ما قيل سابقاً — فأعطها المعرفة: ضمّن النتائج السابقة في السياق واطلب الجديد وغير المعالَج فقط. تعطيل المراجعة أو خفض العشوائية أو الترشيح النصي كلها لا تعالج غياب السياق.
The correct answer is B. The review repeats findings because it does not know what was already said — so give it that knowledge: include prior findings in context and request only new or unaddressed issues. Disabling re-runs, lowering temperature, or string filtering all fail to address the missing context.
